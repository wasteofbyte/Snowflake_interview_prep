MODULE 04 · DATA INGESTION

Land it once.
Land it right.

Module 02 showed the basics: PUT a file to a stage, then COPY INTO a table. Real platforms go much further. Files arrive every few seconds from hundreds of systems, some rows are broken, some files are duplicates, some data must stay in the lake for Spark, and the business wants dashboards that are minutes (or seconds) old. This module goes deep on every way data gets into Snowflake and what really happens in the backend.

We keep the restaurant from earlier modules. Today we meet the people who deal with deliveries:

STAGE
The loading dock

Boxes (files) are dropped here first. Nobody cooks on the dock: it's just a safe place to keep boxes until a chef unpacks them into the pantry (a table).

COPY INTO
The weekly truck

One big delivery on a schedule. A team of chefs (the warehouse) unpacks every box at once, then goes home. Cheap per box, but food is only as fresh as the last truck.

SNOWPIPE
The doorbell courier

Every time a parcel lands, the doorbell rings (an event notification) and a concierge (serverless compute) unpacks it within a minute or so. No chef has to wait at the door.

STREAMING
The conveyor belt

No boxes at all: items roll straight from the farm onto the kitchen counter, one by one, in seconds. Snowpipe Streaming writes rows without staging files.

AND ONE MORE
External and Iceberg tables are like cooking with ingredients that stay in the shared community fridge (your own data lake). Snowflake reads them where they are, and other kitchens (Spark, Trino) can use the same fridge.
CHAPTER 01

Ingestion patterns map · latency vs cost vs complexity

01 · WHAT IS IT

There are four main ways to get data into (or in front of) Snowflake:

  • Batch: COPY INTO on your own warehouse, usually run by a task, Airflow or dbt every hour or every night.
  • Continuous micro-batch: Snowpipe. A COPY statement wrapped in a PIPE object that Snowflake runs automatically on serverless compute whenever new files land.
  • Streaming: Snowpipe Streaming (Ingest SDK, Kafka connector). Rows go straight into tables with no files in between.
  • Query in place: external tables and Apache Iceberg tables. The data stays in your cloud storage; Snowflake reads it there.
02 · WHY IT MATTERS

Interviewers love "how would you ingest X?" because there's no single right answer. Each pattern trades three things:

  • Latency: how old the data is when people query it.
  • Cost: idle warehouse time, per-file overhead, or always-on clients.
  • Complexity: cloud notifications, IAM, SDK code, offset handling.

A senior answer names the requirement first ("dashboards need data within 5 minutes"), then picks the cheapest pattern that meets it.

03 · HOW TO CHOOSE · TRY THE PATTERN PICKER

Pick the requirement. The map highlights the pattern that fits, and explains what runs in the backend. Bubble size = relative cost at moderate volume (illustrative model, not a benchmark).

CHAPTER 02

Stages & storage integrations · the loading dock and its key card

01 · WHAT IS IT

A stage is a named pointer to a place where files live. Internal stages keep the files in Snowflake-managed storage. External stages point at your bucket or container (S3, Azure Blob/ADLS Gen2, GCS).

A storage integration is an account-level object that holds the identity Snowflake uses to reach your cloud storage, plus a list of allowed locations. Stages reference it, so no access keys ever appear in SQL.

A file format tells COPY how to parse the bytes: CSV, JSON, Parquet, Avro, ORC or XML.

02 · WHY WE USE IT
  • Security: with CREDENTIALS=(AWS_KEY_ID=…) in a CREATE STAGE, the secret sits in DDL, history and scripts. An integration uses role assumption with short-lived credentials instead.
  • Separation of duties: a cloud admin creates the IAM role, an ACCOUNTADMIN creates the integration once, and engineers just get USAGE on it.
  • Guard rails: STORAGE_ALLOWED_LOCATIONS stops anyone pointing a stage at a bucket they shouldn't.
  • Reuse: named file formats and stages keep parsing rules in one place instead of repeating them in every COPY.
03 · HOW IT WORKS · PICK A STAGE TYPE

How Snowflake gets into your S3 bucket without a password

File formats: the parsing rules

CSV

FIELD_DELIMITER, SKIP_HEADER=1 or PARSE_HEADER=TRUE (use column names, needed for INFER_SCHEMA and MATCH_BY_COLUMN_NAME), FIELD_OPTIONALLY_ENCLOSED_BY='"', NULL_IF=('','NULL'), EMPTY_FIELD_AS_NULL, ERROR_ON_COLUMN_COUNT_MISMATCH, TRIM_SPACE, DATE_FORMAT, ENCODING, COMPRESSION=AUTO.

JSON

Loads into a VARIANT column (or columns via MATCH_BY_COLUMN_NAME). STRIP_OUTER_ARRAY=TRUE turns one big [ {...}, {...} ] into one row per element, which also avoids the per-value size limit on VARIANT. STRIP_NULL_VALUES drops null keys.

Parquet · Avro · ORC

Self-describing binary formats with a schema inside the file. Query fields as $1:col_name, load by name with MATCH_BY_COLUMN_NAME, or detect columns with INFER_SCHEMA. Parquet is the usual lake format.

XML

Loads into VARIANT. Options like STRIP_OUTER_ELEMENT help split a big root element into rows. XML is load-only: you can't unload to XML.

Unload formats

COPY INTO @stage writes CSV, JSON or Parquet only.

Directory tables (recap)

From Module 02: DIRECTORY=(ENABLE=TRUE) adds a file catalog to a stage. Useful for listing and auditing files, and for streams on new files, not just for unstructured data.

INTERVIEW TRAP
"Why does LIST @s3_orders fail with an access-denied error right after you created the integration?" Usually the IAM role's trust policy was never updated with the STORAGE_AWS_IAM_USER_ARN and STORAGE_AWS_EXTERNAL_ID from DESC INTEGRATION. Also: running CREATE OR REPLACE STORAGE INTEGRATION can generate a new external ID, which breaks the trust policy again.
SENIOR ANGLE
Give the IAM role least privilege: s3:GetObject, s3:GetObjectVersion and s3:ListBucket on one prefix for loading; add s3:PutObject / s3:DeleteObject only if you unload or use PURGE. Use one integration per environment (dev / prod buckets) so dev can never read prod.
CHAPTER 03

COPY INTO deep dive · errors, validation, reloads, transforms

Module 02 covered the happy path (PUT then COPY INTO, and the 64-day load metadata). Here we look at what senior engineers actually tune: what happens when rows are bad, how to test a load without loading, and how to reshape data on the way in.

01 · WHAT IS IT

COPY INTO <table> is a bulk load statement: it reads staged files, parses them with a file format, optionally transforms columns with a SELECT, and writes micro-partitions to the table in one transaction. Its copy options decide what happens with bad data and with files that were loaded before:

  • ON_ERROR: ABORT_STATEMENT (default for bulk COPY), CONTINUE, SKIP_FILE (default for Snowpipe), SKIP_FILE_n, 'SKIP_FILE_n%'.
  • VALIDATION_MODE: RETURN_n_ROWS, RETURN_ERRORS, RETURN_ALL_ERRORS. A dry run: nothing is loaded.
  • FORCE, LOAD_UNCERTAIN_FILES, PURGE, PATTERN, FILES, MATCH_BY_COLUMN_NAME.
02 · WHY THESE OPTIONS MATTER
  • Bad rows are normal. A vendor sends "N/A" in an amount column. Do you fail the whole night's load, drop that file, or keep the good rows and log the bad ones? That is a business decision, and ON_ERROR encodes it.
  • Idempotency. Load metadata makes reruns safe. FORCE breaks that on purpose, so you need to know when it's appropriate.
  • Fewer moving parts. Light transformations during load (cast, reorder, add the file name) save a whole staging step.
03 · HOW IT WORKS · BACKEND

1. List and filter: cloud services lists the stage path, applies PATTERN / FILES, then removes files already in the table's load metadata (file name + ETag/checksum, kept 64 days) unless FORCE=TRUE. 2. Distribute: remaining files are spread across the warehouse's threads; one file is read by one thread. 3. Parse and convert: each row is parsed and cast to the column types; failures are counted per file. 4. Decide: ON_ERROR rules decide, per file, whether to keep its good rows, drop the file or abort everything. 5. Commit: new micro-partitions are registered atomically and load metadata is updated for every file that loaded (fully or partly). Files that failed are not recorded as loaded, so the next COPY tries them again.

Transforming during load

COPY INTO orders (order_id, amount, order_ts, src_file, src_row) FROM ( SELECT $1::NUMBER, TRY_TO_DECIMAL($2, 10, 2), TO_TIMESTAMP_NTZ($3, 'YYYY-MM-DD HH24:MI:SS'), METADATA$FILENAME, METADATA$FILE_ROW_NUMBER FROM @raw_stage/orders/ ) FILE_FORMAT = (FORMAT_NAME = 'csv_std') PATTERN = '.*orders_[0-9]+[.]csv[.]gz';
  • $1, $2… are the positional fields of the file (for Parquet/JSON: $1:field).
  • Allowed: column reorder, omit columns, casts, simple functions such as TRY_TO_DECIMAL or CURRENT_TIMESTAMP(). Not allowed: joins, WHERE filters, GROUP BY, FLATTEN.
  • METADATA$FILENAME and METADATA$FILE_ROW_NUMBER give you lineage: every row knows which file and line it came from. Also available: METADATA$FILE_LAST_MODIFIED, METADATA$START_SCAN_TIME, METADATA$FILE_CONTENT_KEY.
  • PATTERN is a regular expression matched against the path, not a shell glob.
VALIDATION_MODE vs VALIDATE()

VALIDATION_MODE checks files before loading and loads nothing. SELECT * FROM TABLE(VALIDATE(orders, JOB_ID => '_last')) returns the rows rejected by a COPY that already ran (for example with CONTINUE). Neither works with COPY statements that transform data.

FORCE vs LOAD_UNCERTAIN_FILES

FORCE=TRUE reloads everything matched, even files loaded yesterday, so it creates duplicates. LOAD_UNCERTAIN_FILES=TRUE only adds files whose status is unknown because they are older than the 64-day metadata window; files known to be loaded are still skipped.

MATCH_BY_COLUMN_NAME

CASE_INSENSITIVE / CASE_SENSITIVE: map file columns to table columns by name instead of position. Works for Parquet, Avro, ORC and JSON, and for CSV when the file format has PARSE_HEADER=TRUE. Required for schema evolution (chapter 08).

INTERVIEW TRAP
"The COPY used ON_ERROR = CONTINUE and returned success, so the data is complete, right?" Not necessarily. Check the result columns ERRORS_SEEN and STATUS = PARTIALLY_LOADED, or query VALIDATE() / COPY_HISTORY. Silent row loss is the classic production bug with CONTINUE.
SENIOR ANGLE
A robust pattern: load raw files into a landing table with every column as VARCHAR (or one VARIANT) plus METADATA$FILENAME, so the load practically never fails. Then cast with TRY_CAST in the next layer, and route rows that fail the cast to a quarantine table. You keep 100% of the evidence and the load never pages anyone at 3 a.m.
CHAPTER 04

File sizing & parallelism · why 100–250 MB?

01 · WHAT IS IT

Snowflake's guidance is to aim for data files of roughly 100–250 MB compressed for loading (with COPY or Snowpipe). The size and number of files decide how well the warehouse's parallel threads are used and how much fixed per-file overhead you pay.

02 · WHY IT MATTERS
  • Tiny files (a few KB each, often from streaming jobs that flush every second): each file has fixed costs (listing, opening, metadata, commit bookkeeping). With Snowpipe, file count has historically also affected the bill.
  • Giant files (10 GB+): one thread works while the others sit idle, a single bad row with ABORT_STATEMENT throws away hours of work, and retries are expensive.
03 · HOW IT WORKS · BACKEND

A warehouse is a cluster of nodes, and each node runs several load threads. During COPY, files are the unit of work: each file is handed to one thread (a gzip stream can't be split in the middle). So a load can never run with more parallel threads than it has files. With 1 file, an X-Large warehouse is as fast as an X-Small for that load, while you pay X-Large rates. Split big exports into many medium files, and merge tiny ones before loading.

INTERVIEW TRAP
"Loads are slow, so let's use a bigger warehouse." If the load is one 20 GB file, a bigger warehouse changes nothing: one file = one thread. Fix the files first (split to ~100–250 MB), then size the warehouse to the number of files.
SENIOR ANGLE
Upstream fixes beat Snowflake tuning: configure Spark (maxRecordsPerFile / repartition), Firehose buffering (size and interval), or the Kafka connector flush settings so files arrive at a sensible size. For Snowpipe, Snowflake suggests staging files about once a minute rather than every second.
CHAPTER 05

Snowpipe · continuous, serverless file loading

01 · WHAT IS IT

A pipe is a named object that wraps one COPY INTO statement. Snowflake runs that COPY for you, on serverless compute, every time new files are reported. Two ways to report files:

  • Auto-ingest (AUTO_INGEST=TRUE): cloud storage sends event notifications. S3 → SQS queue (Snowflake provides it; you can also route through SNS), Azure → Event Grid → storage queue (via a notification integration), GCS → Pub/Sub subscription (via a notification integration).
  • REST API: your application calls the insertFiles endpoint with the list of file names (key-pair auth), and can check insertReport / loadHistoryScan.
02 · WHY WE USE IT
  • Freshness without babysitting: data is usually queryable about a minute after the file lands, without a scheduler.
  • No warehouse to manage: no idle time, no 60-second minimum per resume. Snowflake sizes the compute.
  • Built-in deduplication: each pipe remembers which files it loaded, so the same notification twice doesn't duplicate data.
03 · HOW IT WORKS · BACKEND

Each notification adds the file path to the pipe's internal queue. Snowflake batches queued files and runs the pipe's COPY on Snowflake-managed compute. Before loading, it checks the pipe's load history (kept per pipe, about 14 days; check docs for current details) and skips file names it has already loaded. The default ON_ERROR for pipes is SKIP_FILE, so a bad file is dropped and reported, not loaded half-way. Billing: serverless compute charged to the account (historically compute time plus a small per-file overhead; Snowflake has been moving pipes to a simpler volume-based price, so check the current pricing guide).

Operating a pipe

SYSTEM$PIPE_STATUS

Returns JSON with executionState (RUNNING, PAUSED, …), pendingFileCount, lastIngestedTimestamp, lastIngestedFilePath, plus notification-channel info and recent errors. First thing to check when "data stopped arriving".

COPY_HISTORY

INFORMATION_SCHEMA.COPY_HISTORY() (last 14 days, per table) and ACCOUNT_USAGE.COPY_HISTORY (up to a year, some latency) show both bulk COPY and Snowpipe loads: file, status, rows, first error. The older LOAD_HISTORY view covers bulk COPY only, not Snowpipe.

Pause, resume, refresh

ALTER PIPE p SET PIPE_EXECUTION_PAUSED = TRUE stops loading (notifications keep queueing). ALTER PIPE p REFRESH queues files already in the stage that were staged within the last 7 days, for example after creating the pipe or after an outage.

Changing the COPY

You can't edit a pipe's COPY statement in place; you recreate the pipe. A recreated pipe has fresh load history, so pause, recreate, then use REFRESH carefully (or the table's own load metadata) to avoid reloading files.

Error notifications

Set ERROR_INTEGRATION = my_notif_int on an auto-ingest pipe to push failures to SNS, Event Grid or Pub/Sub, instead of polling COPY_HISTORY.

Cost views

ACCOUNT_USAGE.PIPE_USAGE_HISTORY (or the PIPE_USAGE_HISTORY() table function) shows credits and bytes / files per pipe.

INTERVIEW TRAP
Order and replays. Snowpipe does not guarantee files load in the order they arrived. And if a producer overwrites a file with the same name, the pipe treats it as already loaded and skips it (within its load history window). Use unique file names (timestamp or UUID in the path) and never rely on arrival order; deduplicate or order downstream (for example with a MERGE on a business key and event timestamp).
SENIOR ANGLE
One S3 bucket can only send a given event type for overlapping prefixes to one destination. If several pipes (or other consumers) need the same bucket, route S3 events through an SNS topic and subscribe each SQS queue, or split pipes by prefix. Mention this when designing multi-tenant ingestion.
CHAPTER 06

Snowpipe Streaming · rows in seconds, no files

01 · WHAT IS IT

Snowpipe Streaming lets a client write rows straight into Snowflake tables. There are no staged files and no COPY. You use it through:

  • the Snowflake Ingest SDK (Java; newer SDKs add more languages), called from your own app, or
  • the Snowflake Connector for Kafka with snowflake.ingestion.method = SNOWPIPE_STREAMING (the older default mode writes files and uses Snowpipe).

The client opens a channel to a table and sends rows, each batch tagged with an offset token. Rows are usually queryable within seconds.

02 · WHY WE USE IT
  • Latency: seconds instead of the minute-plus of file-based Snowpipe.
  • No tiny-file problem: a Kafka topic with steady traffic would otherwise produce thousands of small files.
  • Exactly-once delivery when combined with a replayable source such as Kafka, thanks to offset tokens.
  • Often cheaper than file-based Snowpipe at high event rates, because there is no per-file work (check current pricing).
03 · HOW IT WORKS · BACKEND

Client → opens a channel (one channel per Kafka partition in the connector) → buffers rows in memory → flushes compressed batches to Snowflake every second or so, with the latest offset token. Snowflake → writes the batch to Snowflake-managed storage, registers it with the table and stores the channel's committed offset token atomically with the data. In the classic architecture, a background process later optimizes these batches into regular micro-partitions. Ordering is guaranteed within a channel, not across channels. Snowflake has also introduced a newer high-performance architecture (it uses a PIPE object as the entry point and has its own SDKs and throughput-based pricing). Treat feature and pricing details as version-specific and check the docs.

INTERVIEW TRAP
"Exactly-once is automatic." Only if your client uses the token correctly: on start-up it must call getLatestCommittedOffsetToken() for the channel and resume the source from the next offset. If it simply replays from the beginning, or from its own unsaved bookmark, you get duplicates or gaps. The Kafka connector does this for you.
SENIOR ANGLE
A common modern design is Kafka → Snowpipe Streaming → raw table → dynamic tables (Module 05) for the transformation layers. The streaming part gives seconds of latency; the dynamic tables give declarative, incremental modelling with a target lag that matches what the business actually needs.
CHAPTER 07

External tables vs Apache Iceberg tables · query the lake in place

01 · WHAT IS IT

External table: a read-only table over files in an external stage. Snowflake stores only metadata about the files; each row has a VALUE VARIANT column plus METADATA$FILENAME, and you define virtual columns and partition columns derived from the file path.

Apache Iceberg table: a table in the open Iceberg format (Parquet data files + Iceberg metadata/manifest files) stored in your cloud storage through an EXTERNAL VOLUME. The catalog (who tracks the current snapshot) is either Snowflake or an external catalog (AWS Glue, an Iceberg REST catalog such as Snowflake Open Catalog / Apache Polaris, or object storage) via a CATALOG INTEGRATION.

02 · WHY WE USE IT
  • One copy of data shared by Snowflake, Spark, Trino, Flink: no duplicate pipelines, no vendor lock-in on the storage format.
  • Data that must stay in your account for legal or cost reasons: you pay your cloud provider for storage, not Snowflake.
  • External tables are a quick way to explore or occasionally query raw files without loading them.
  • Snowflake-managed Iceberg gives near-native features (full DML, Time Travel, clustering) on open files.
03 · HOW IT WORKS · BACKEND

External table: Snowflake keeps a file list. It's updated by AUTO_REFRESH=TRUE (cloud event notifications, like Snowpipe) or ALTER EXTERNAL TABLE … REFRESH. At query time the warehouse reads the raw files; filters on partition columns skip whole folders. No micro-partition statistics, so it's slower than native tables. Materialized views on external tables can speed up hot queries. Iceberg (Snowflake catalog): Snowflake writes Parquet data files and Iceberg metadata into your bucket and commits each snapshot itself; Spark and other engines can read the same table through a catalog API (for example Snowflake Horizon's Iceberg REST endpoint or a sync to Open Catalog). Iceberg (external catalog): another engine owns the writes; Snowflake reads the snapshot that the catalog points to, refreshed manually or automatically. Write support from Snowflake into externally managed catalogs has been expanding; check current docs before promising it.

INTERVIEW TRAP
"External tables and Iceberg tables are the same thing." No. External tables are read-only views over raw files with only a file list as metadata. Iceberg tables have a real table format (snapshots, schema, manifests with column statistics), so they support pruning, ACID commits and, when Snowflake is the catalog, full DML.
SENIOR ANGLE
For an Iceberg-based lakehouse, decide the catalog first: who commits writes, how other engines discover the table, and how access control is enforced across engines. File layout (target file size, partitioning, compaction) matters just as much as for native tables.
CHAPTER 08

Schema detection, evolution & unloading · when the file changes shape

01 · WHAT IS IT
  • INFER_SCHEMA: a table function that reads staged files (Parquet, Avro, ORC, JSON, CSV) and returns column names, types and nullability.
  • CREATE TABLE … USING TEMPLATE: creates a table from that output in one statement.
  • ENABLE_SCHEMA_EVOLUTION = TRUE: a table property that lets loads add new columns and drop NOT NULL on columns missing from new files.
  • COPY INTO @stage: the reverse of loading. It unloads query results to files (CSV, JSON, Parquet).
02 · WHY WE USE IT

Sources change: a product team adds coupon_code to an event, or a vendor drops a column. Without detection and evolution, someone writes DDL by hand for 200 columns, and every upstream change breaks the pipeline. Unloading is how you hand data to partners, other systems or the lake.

03 · HOW IT WORKS · BACKEND

INFER_SCHEMA runs on your warehouse: it reads file footers (Parquet/ORC), embedded schemas (Avro) or samples records (JSON, CSV with PARSE_HEADER=TRUE) and merges types across files. Schema evolution works with loads that map by name (MATCH_BY_COLUMN_NAME in COPY or Snowpipe, and Snowpipe Streaming / Kafka). The role needs ownership or the EVOLVE SCHEMA privilege on the table. Snowflake limits how many columns one load can add, so check the docs for the current limit. Unload runs the query on your warehouse; each thread writes its own files in parallel (default target size about 16 MB each), unless you ask for SINGLE=TRUE.

Data quality at the door

Land raw, validate next

Load into a permissive landing table (VARCHAR / VARIANT + file name + load time), then cast with TRY_CAST and send failures to a quarantine table.

Reconcile counts

Compare rows in the file (or a manifest / control file from the source) with ROWS_LOADED from COPY_HISTORY. Alert on any gap.

Data metric functions

Attach system DMFs such as NULL_COUNT, DUPLICATE_COUNT or FRESHNESS (or your own) to tables on a schedule to catch quality drift (availability depends on edition).

Dry runs

Use VALIDATION_MODE = RETURN_ERRORS on new vendor files before turning on the pipe.

Idempotent keys

Keep a business key + event time so downstream MERGE logic can drop duplicates from FORCE reloads, replays or at-least-once producers.

Alert, don't poll

Error integrations on pipes, Snowflake alerts on COPY_HISTORY failures, and a freshness check on MAX(load_ts).

INTERVIEW TRAP
"Schema evolution will fix type changes too." No. It adds columns and relaxes NOT NULL. If amount changes from a number to text like "12.50 USD", the load fails (or rows are rejected) just like before. Type drift needs a landing layer or a deliberate migration.
SENIOR ANGLE
Unload with PARTITION BY to Parquet in date folders, a sensible MAX_FILE_SIZE, and HEADER=TRUE for Parquet so column names are kept. For recurring partner feeds, consider Secure Data Sharing (Module 10) instead: no files, no copies, always fresh.
