MODULE 11 · SNOWPARK & CORTEX AI

Bring the code
to the data.

The first ten modules were mostly about SQL: loading, tuning, protecting and sharing data. This module is about everything that isn't plain SQL: Python DataFrames that turn into SQL, Python functions running next to your tables, containers with GPUs, and AI models you call like a SQL function. They all follow one idea: don't pull the data out to your code; push your code in to the data.

Four characters for this module, using a library as the analogy:

SNOWPARK DATAFRAME
A written request slip

You fill in a slip ("all shipped orders, totals by region"). Nobody fetches anything until you hand it to the desk. Then the librarians (the warehouse) do all the work inside the building.

UDF / PROCEDURE
A specialist who works on-site

Instead of carrying 10,000 books home to check them, you hire a specialist who sits in the reading room and checks each book there.

CONTAINER SERVICES
Renting a private study room

Bring your own equipment (any software, even GPUs) and set it up in a room inside the library, still behind the library's doors.

CORTEX AI
The in-house expert reader

An expert who reads, summarises, translates and answers questions about the books, and never takes a book out of the building.

01 · WHAT IS IT

"Code to data" means the computation runs where the data lives (inside Snowflake, on a warehouse or a compute pool) instead of copying rows out to a laptop, a Spark cluster or an external ML server.

Snowflake gives you several ways to do that: Snowpark (DataFrame API + Python/Java/Scala functions), Snowpark Container Services (your own containers), Cortex AI (managed LLM and ML functions) and Snowflake ML (feature store, model registry, ML functions).

02 · WHY WE USE IT
  • Speed: moving terabytes over a network is slow; returning a 20-row answer is instant.
  • Security and governance: data never leaves Snowflake, so RBAC, masking policies and auditing still apply. No forgotten CSV copies on laptops.
  • Scale: warehouses scale up and out; your laptop doesn't.
  • Fewer systems: one platform instead of Snowflake + Spark cluster + model server + vector database.

The classic beginner pattern is pd.read_sql("SELECT * FROM orders") and then pandas on a laptop. Move the slider and compare it with pushing the same logic down to Snowflake.

CHAPTER 01

Snowpark DataFrames · Python that becomes SQL

01 · WHAT IS IT

Snowpark is Snowflake's developer framework for Python, Java and Scala. Its main piece is the DataFrame API: you write df.filter(...).group_by(...).agg(...), and Snowpark translates it into SQL that runs on a Snowflake warehouse.

Everything starts with a Session, your connection plus context (role, warehouse, database, schema): Session.builder.configs({...}).create(). Inside a stored procedure, Snowflake hands you a session automatically.

It feels like PySpark (same style of API), but there is no cluster to manage: the "cluster" is your virtual warehouse.

02 · WHY WE USE IT
  • Python developers and data scientists can work in Python without pulling data out.
  • Complex pipelines become testable, reusable code (functions, classes, unit tests, CI/CD) instead of 800-line SQL strings.
  • The generated SQL gets the full Snowflake optimizer: pruning, result cache, elastic warehouses.
  • A common migration path for Spark jobs: similar API, no cluster tuning.
03 · HOW IT WORKS · LAZY EVALUATION

A DataFrame is not data. It is a recipe (a logical plan) kept in your Python process. Each transformation (filter, select, join, group_by, with_column, sort) just returns a new, bigger recipe. Nothing is sent to Snowflake.

When you call an action (collect(), show(), count(), to_pandas(), write.save_as_table()), Snowpark compiles the whole recipe into SQL, sends it through the connector to cloud services (which parses, optimizes and plans it like any query), and a warehouse executes it. You can see the SQL with df.queries or df.explain(), and every Snowpark query shows up in Query History.

Client side (your Python process)

Builds the plan, generates SQL, receives results. DataFrame code runs here only to describe work. No rows are processed on the client unless you collect() or to_pandas() them.

Server side (Snowflake)

Cloud services compiles, the warehouse executes. Your UDF and stored procedure code (next chapter) also runs here, inside a secure Python sandbox on the warehouse nodes.

INTERVIEW TRAP
Every action re-runs the query. Call df.count() and then df.show() and you have run the full pipeline twice (the result cache may help only if the SQL and data are identical). If you reuse an expensive intermediate result, call df.cache_result(), which materializes it into a temporary table and returns a DataFrame over it.
SENIOR ANGLE
The anti-pattern to name in interviews: for row in df.collect(): ... or df.to_pandas() on a 50M-row table. It drags everything into client memory and makes Python do the work row by row. Keep the logic in DataFrame operations (pushed down as SQL) and only collect small, final results. Snowflake also offers a pandas-compatible API (Snowpark pandas on Modin) that pushes pandas-style code down as SQL; check current docs for supported operations.
CHAPTER 02

UDFs, UDTFs, vectorized UDFs & procedures · Python on the server

01 · WHAT IS IT

When SQL alone can't express your logic, you write it in Python (or Java, Scala, JavaScript, SQL) and register it in Snowflake:

  • Scalar UDF: one row in, one value out. SELECT clean_phone(phone) FROM customers.
  • UDTF (table function): rows in, zero or many rows out. A handler class with process() (per row) and optional end_partition(). Called as TABLE(my_udtf(col)) OVER (PARTITION BY ...).
  • Vectorized UDF: the handler receives a batch of rows as a pandas DataFrame and returns a batch of results. Same SQL call, much less per-row overhead.
  • Stored procedure: run with CALL; the handler gets a Snowpark session and can run DML/DDL (Module 02 covered procedures in depth).
02 · WHY WE USE IT
  • Use the Python ecosystem (regex, scikit-learn, XGBoost, NLP libraries) inside SQL queries.
  • Score ML models on millions of rows where the data lives.
  • Share one tested implementation: analysts call it from SQL, engineers from Snowpark.
  • Governed: UDFs run under Snowflake RBAC, and the sandbox has no internet access unless you grant an external access integration.
03 · HOW IT WORKS · BACKEND
Packages

PACKAGES = ('pandas','scikit-learn') are resolved from Snowflake's Anaconda channel (an org admin must accept the Anaconda terms once). List what's available with SELECT * FROM INFORMATION_SCHEMA.PACKAGES WHERE language = 'python'. Pin versions for reproducibility.

Imports from stages

IMPORTS = ('@ml_stage/model.joblib', '@code/utils.zip') copies files from a stage onto the nodes. Your code finds them via sys._xoptions["snowflake_import_directory"]. Load models once at module level, not inside the handler.

Execution

The query runs on the warehouse. Each node starts Python worker processes in a secure sandbox; Snowflake sends rows to them in batches and collects results. A scalar UDF still pays a Python function call per row; a vectorized UDF gets a whole pandas batch per call.

Snowpark-optimized warehouses (WAREHOUSE_TYPE = 'SNOWPARK-OPTIMIZED') give each node much more memory than a standard warehouse, for memory-hungry work such as training a model inside a stored procedure or loading a large model into a UDF. They cost more per hour, so use them only when standard warehouses run out of memory. Check current docs for the exact memory multiples and supported sizes.

INTERVIEW TRAP
"Our Python UDF is slow, so we moved to a 4XL warehouse and it barely helped." Bigger warehouses add nodes, but if the handler loads a model on every call or processes one row at a time with pure-Python loops, the overhead scales with it. Fix the code first: load once at module level, switch to a vectorized UDF with numpy/pandas operations, and check whether plain SQL could do it (built-in functions beat any UDF).
SENIOR ANGLE
UDF vs procedure in one sentence: a UDF is a calculation used inside a query (read-only, runs per row or batch, parallel across nodes); a procedure is an action you CALL (runs once, gets a session, can run DML/DDL and orchestrate many queries). A Python procedure that does session.table(...).to_pandas() and loops in pandas runs on one node and loses the warehouse's parallelism; push the work into DataFrame operations or UDFs instead.
CHAPTER 03

Snowpark Container Services · your own containers inside Snowflake

01 · WHAT IS IT

Snowpark Container Services (SPCS) is a managed runtime for OCI/Docker container images inside Snowflake. You build an image with any language, libraries and runtime, push it to Snowflake, and run it on Snowflake-managed nodes, including GPU nodes.

  • Image repository: an OCI registry that lives in a schema. You docker push to its URL.
  • Compute pool: a group of VM nodes of one instance family (CPU or GPU sizes), with MIN_NODES / MAX_NODES.
  • Service: long-running containers (an API, a web app, a model server) described by a YAML specification, optionally with public endpoints.
  • Job service: runs to completion (EXECUTE JOB SERVICE), e.g. a batch training job.
  • Service function: a SQL function that calls a service endpoint, so SQL users can use your container like a UDF.
02 · WHY WE USE IT
  • GPUs for deep learning training, fine-tuning or running open-source models.
  • Custom runtimes: libraries not in the Anaconda channel, system packages, other languages, long-running processes.
  • Full apps (React front ends, APIs, notebooks) hosted next to the data, behind Snowflake authentication.
  • Still governed: data access uses Snowflake roles; outbound internet needs an external access integration.
03 · HOW IT WORKS
1 · Repository

CREATE IMAGE REPOSITORY, then docker login, docker tag and docker push to the repository URL shown by SHOW IMAGE REPOSITORIES.

2 · Compute pool

CREATE COMPUTE POOL with an INSTANCE_FAMILY (e.g. a CPU or GPU family) and node limits. Billed for nodes while the pool is running, busy or idle. Set auto-suspend.

3 · Service

CREATE SERVICE ... IN COMPUTE POOL ... FROM SPECIFICATION (YAML: containers, image, env, resources, endpoints, volumes). Snowflake schedules and restarts the containers for you.

4 · Use it

Call it from SQL through a service function, open a public endpoint (Snowflake login required), or run it as a job. Logs are available through the event table / SYSTEM$GET_SERVICE_LOGS.

SPCS features, instance families and regional availability evolve quickly. Treat this chapter as the concept; check current docs for exact instance names and limits.

"We'll use SPCS for everything." A compute pool bills for its nodes while running, even if no requests come in, and you own the image, patching and scaling settings. If a vectorized UDF or a Cortex function does the job, it is usually simpler and cheaper. Reach for containers when you genuinely need GPUs, a custom runtime or a long-running service.
CHAPTER 04

Cortex AI SQL functions · LLMs you call like SUM()

01 · WHAT IS IT

Snowflake Cortex is Snowflake's managed AI layer. Its AI SQL functions let you run large language models on table columns with plain SQL. No API keys, no GPUs, no Python required. The current family uses the AI_ prefix (older equivalents live under SNOWFLAKE.CORTEX.*, e.g. COMPLETE, SENTIMENT, SUMMARIZE, TRANSLATE):

AI_COMPLETEFree-form generation with a chosen model and prompt
AI_CLASSIFYAssign one (or more) of your labels
AI_FILTERTRUE/FALSE for a natural-language condition (use in WHERE / JOIN)
AI_SENTIMENTOverall and per-aspect sentiment
AI_AGG / AI_SUMMARIZE_AGGAggregate functions: insight or summary across many rows (GROUP BY)
AI_EMBED / AI_SIMILARITYText (or image) to vector; similarity score between two inputs
AI_TRANSLATETranslate between supported languages

Function names, signatures, models and regions change often. Phrase it in interviews as "the AI SQL functions such as AI_COMPLETE and AI_CLASSIFY" and check current docs before relying on a specific model.

02 · WHY WE USE IT
  • Analysts can do AI: classify 2 million support tickets with one SELECT.
  • Data stays in Snowflake: models run inside Snowflake's security boundary, so RBAC and masking apply, and no data goes to a third-party API you manage.
  • Batch scale: run over whole tables, schedule with tasks or dynamic tables.
  • Choice of models (Snowflake, Meta, Mistral, Anthropic, OpenAI and others, depending on region) without hosting any of them.
03 · HOW IT WORKS · BACKEND & BILLING
Execution

Your query runs on your warehouse. Each AI function call is sent to Snowflake-hosted model inference and the result returns as a value in the row. A bigger warehouse doesn't make the model faster; Snowflake recommends a MEDIUM or smaller warehouse for Cortex queries.

Tokens

Billed per token (roughly 4 characters of English text). Generative functions count input + output tokens; some count input only. Rates differ by function and model (see Snowflake's Service Consumption Table). Track spend in ACCOUNT_USAGE Cortex usage views.

Governance

Access via the SNOWFLAKE.CORTEX_USER database role (granted to PUBLIC by default; revoke it to lock down). Admins can restrict models with an allowlist parameter and enable cross-region inference when a model isn't in your region; check current docs for parameter names.

INTERVIEW TRAP
"We put AI_COMPLETE in a view and the bill exploded." Every query on that view re-calls the model for every row. AI results are not free like a SUM: compute them once into a table (incrementally, with a stream + task or a dynamic table), then let dashboards read the stored results. SENIOR ANGLE
Pick the smallest function and model that work. Task-specific functions (AI_CLASSIFY, AI_SENTIMENT, AI_FILTER) are simpler to govern and usually cheaper than a free-form AI_COMPLETE prompt. For COMPLETE, try a small model first, constrain output (short answers, structured JSON output where supported), and measure quality on a labelled sample before scaling up.
CHAPTER 05

Vectors & RAG · search by meaning, answer with your data

01 · WHAT IS IT

An embedding is a list of numbers (e.g. 768 or 1024 of them) that represents the meaning of a piece of text. Texts with similar meanings get vectors that point in similar directions, even with different words ("refund" ≈ "money back").

Snowflake has a native VECTOR(FLOAT, n) data type (also INT elements; check docs for the maximum dimension), embedding functions (AI_EMBED, older SNOWFLAKE.CORTEX.EMBED_TEXT_768/1024) and distance functions: VECTOR_COSINE_SIMILARITY, VECTOR_INNER_PRODUCT, VECTOR_L2_DISTANCE.

RAG (retrieval-augmented generation) = find the most relevant chunks of your documents, paste them into the prompt, and let the LLM answer from them.

02 · WHY WE USE IT
  • LLMs don't know your private policies, contracts or tickets, and they hallucinate when they guess. RAG grounds them in your data.
  • Keyword search misses synonyms; vector search finds meaning. Hybrid search combines both.
  • Keeping vectors in Snowflake means no separate vector database to sync and secure.
03 · HOW IT WORKS · THE RAG FLOW
1 · Chunk

Split documents into small passages (Module 02's chunking visualizer).

2 · Embed

Turn every chunk into a vector with an embedding model.

3 · Index

Store vectors (a VECTOR column) or let Cortex Search build a managed index.

4 · Retrieve

Embed the question with the same model, find the top-k nearest chunks.

5 · Generate

Prompt = instructions + retrieved chunks + question → AI_COMPLETE.

Cortex Search is a managed service: CREATE CORTEX SEARCH SERVICE ... ON text_col ATTRIBUTES ... WAREHOUSE = ... TARGET_LAG = '1 hour' AS (SELECT ...). Snowflake embeds the text, builds a hybrid index (vector + keyword, with semantic re-ranking), and refreshes it incrementally when the source changes, within the target lag (like a dynamic table). Apps query it through the Python API, REST API, or SNOWFLAKE.CORTEX.SEARCH_PREVIEW in SQL for testing, with filters on ATTRIBUTES columns.

INTERVIEW TRAP
Mixing embedding models. Vectors from different models (or different dimensions) live in different "spaces" and can't be compared. The question must be embedded with the same model as the documents, and if you switch models you must re-embed everything. Also: ORDER BY VECTOR_COSINE_SIMILARITY(...) over a table is a full scan; fine for thousands or a few million rows, but for large, low-latency apps use Cortex Search.
SENIOR ANGLE
RAG quality is mostly retrieval quality. Tune chunk size (Snowflake suggests chunks of roughly 512 tokens or less for Cortex Search), keep useful metadata as ATTRIBUTES for filtering (region, product, doc date), use hybrid search for codes and names that embeddings handle poorly, and evaluate with a set of real questions and expected sources. Tell the model to answer only from the context and to say "I don't know" otherwise.
CHAPTER 06

Cortex Analyst & semantic models · ask your data in English

01 · WHAT IS IT

Cortex Analyst is a managed natural-language-to-SQL service. A business user asks "What was revenue by region last quarter?", Analyst generates SQL against your tables, runs it, and returns the answer plus the SQL it used. Apps call it through a REST API (e.g. from a Streamlit chat app).

It relies on a semantic model: a YAML file on a stage, or a semantic view object in the database (CREATE SEMANTIC VIEW). It describes tables, relationships, dimensions (things you group by), facts/measures and metrics (things you add up), synonyms, and verified queries.

02 · WHY A SEMANTIC LAYER?
  • Raw schemas are ambiguous to an LLM: is revenue AMOUNT, NET_AMT or AMOUNT - DISCOUNT? Which date is "last quarter" based on?
  • The semantic model encodes business definitions once, so every answer uses the same metric logic.
  • Verified queries (question + trusted SQL) are reused or used as examples for similar questions, which raises accuracy.
  • Generated SQL runs with the user's role, so RBAC, row access and masking policies still apply.
03 · HOW IT WORKS · STEP THROUGH A QUESTION
Setup:
A minimal semantic view (syntax evolves; check current docs)
CREATE OR REPLACE SEMANTIC VIEW sales_sv TABLES ( orders AS sales_db.public.orders PRIMARY KEY (order_id), customers AS sales_db.public.customers PRIMARY KEY (customer_id) ) RELATIONSHIPS ( orders_to_customers AS orders (customer_id) REFERENCES customers ) FACTS ( orders.net_amount AS amount - discount ) DIMENSIONS ( customers.region AS region, orders.order_date AS order_date ) METRICS ( orders.total_revenue AS SUM(orders.net_amount) );
Snowflake Intelligence & Cortex Agents

Newer layers build on these pieces: an agent plans a multi-step answer and calls tools such as Cortex Analyst (structured data → SQL) and Cortex Search (documents → RAG), then combines the results. Snowflake Intelligence is the end-user chat experience on top. These products are evolving fast; describe the concept and check current availability.

INTERVIEW TRAP
"Can't we just give the LLM our schema?" It works for demos, but real schemas have cryptic names, many similar columns and business rules the LLM can't guess. Without a semantic layer you get confident, plausible, wrong SQL. The semantic model is where data engineers add real value.
CHAPTER 07

Snowflake ML · features, models and MLOps in one place

01 · WHAT IS IT

Snowflake ML is a set of tools for the whole ML lifecycle, mostly through the snowflake-ml-python library:

  • Feature Store: define entities (customer, product) and feature views (feature SQL/DataFrames, refreshed on a schedule, typically backed by dynamic tables), then generate point-in-time-correct training data.
  • Model Registry: log models (scikit-learn, XGBoost, PyTorch and others) with versions and metadata, then run inference from Python or SQL, on a warehouse or in Container Services.
  • ML Functions: SQL-only ML for common jobs, such as SNOWFLAKE.ML.FORECAST and SNOWFLAKE.ML.ANOMALY_DETECTION (also classification and top-insights functions).
  • Plus notebooks, distributed training/processing APIs and ML jobs (newer; check docs).
02 · WHY WE USE IT
  • Train and serve models without exporting data to a separate ML platform.
  • The same features for training and inference, so you avoid training/serving skew.
  • Versioned, governed models: who can use which version is controlled with RBAC.
  • Analysts can forecast or detect anomalies with two SQL statements.
03 · HOW IT WORKS · MLOPS IN SNOWFLAKE
1 · Features

Feature views over raw tables, refreshed incrementally.

2 · Train

Snowpark-optimized warehouse, notebook or GPU compute pool.

3 · Register

reg.log_model(model, model_name=..., version_name=...).

4 · Infer

mv.run(df, function_name="predict") or SQL on the model; batch via a task.

5 · Monitor

Track drift and accuracy; promote or roll back versions.

ML Functions are schema objects: CREATE SNOWFLAKE.ML.FORECAST my_model(INPUT_DATA => SYSTEM$REFERENCE('VIEW','daily_sales_v'), TIMESTAMP_COLNAME => 'ts', TARGET_COLNAME => 'revenue') trains a model (gradient boosting-based, per Snowflake docs) and CALL my_model!FORECAST(FORECASTING_PERIODS => 14) predicts with intervals. Training uses your warehouse.

INTERVIEW TRAP
Point-in-time correctness. When building training data you must join features as they were at the label's timestamp, not today's values; otherwise the model "sees the future" (leakage) and looks great offline but fails in production. The Feature Store's training-set generation handles this with timestamp-aware joins.
SENIOR ANGLE
Know when not to build a custom model: an ML Function forecast or a Cortex function may be good enough, and is much cheaper to maintain. When you do build one, the Snowflake-native story is: features in the Feature Store, training in Snowpark/notebooks, model in the Registry, batch inference scheduled by a task, all governed by roles. That's a strong system-design answer.
