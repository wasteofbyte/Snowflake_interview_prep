Module 15

External Integrations

How Snowflake connects to the broader data ecosystem: streaming with Kafka, batch processing with Spark, real-time CDC with Debezium, and bidirectional REST API calls via External Functions. The integration layer is where most production complexity lives.

Chapter 01

Snowflake Kafka Connector

01

What is it

A Kafka Connect sink connector that reads records from Kafka topics and writes them to Snowflake tables using Snowpipe under the hood. Available as an open-source plugin from Snowflake on GitHub/Confluent Hub.

02

Why it matters

Kafka is the dominant streaming backbone in enterprise data engineering. The Kafka Connector is the standard way to get event streams from Kafka into Snowflake without writing custom pipeline code.

03

How it works

The connector buffers Kafka records into micro-batch files (Avro, JSON, or Protobuf), uploads them to an internal stage, and triggers Snowpipe to ingest. Each Kafka topic maps to a Snowflake table.

Table format: RECORD_CONTENT and RECORD_METADATA

By default, the connector creates a two-column table: RECORD_CONTENT VARIANT (the message payload) and RECORD_METADATA VARIANT (Kafka metadata: topic, partition, offset, timestamp).

-- What the auto-created table looks like
DESCRIBE TABLE my_kafka_topic;
-- RECORD_CONTENT  VARIANT
-- RECORD_METADATA VARIANT

-- Query the topic data
SELECT
  RECORD_METADATA:offset::INT        AS kafka_offset,
  RECORD_METADATA:partition::INT     AS kafka_partition,
  RECORD_METADATA:CreateTime::INT    AS kafka_ts_ms,
  RECORD_CONTENT:event_type::STRING  AS event_type,
  RECORD_CONTENT:user_id::INT        AS user_id,
  RECORD_CONTENT:amount::FLOAT       AS amount
FROM orders_kafka_topic
ORDER BY kafka_ts_ms DESC
LIMIT 100;

Schema evolution handling

Because the payload lands in a VARIANT column, adding new fields to the Kafka message requires no schema change in Snowflake — the new keys just appear in RECORD_CONTENT. The curated downstream table needs an ALTER TABLE ... ADD COLUMN and an updated transform.

Interview trap — buffer sizing

If buffer.flush.time is too high (e.g., 600s), Kafka offsets are not committed until the buffer flushes, which means consumer lag appears inflated and a Connect worker restart may replay 10 minutes of messages. Tune to your latency SLA: 30s is typical for near-real-time, 120s for batch-style ingestion.

Senior angle — key-pair authentication

The Kafka Connector does not support username/password auth — it requires RSA key-pair authentication. Generate a 2048-bit RSA key pair, assign the public key to the Snowflake service account user (ALTER USER ... SET RSA_PUBLIC_KEY='...'), and pass the private key PEM string (without headers) in the connector config. Store it in Kubernetes Secrets or HashiCorp Vault — never in the Kafka Connect config file in plaintext.

Chapter 02

Snowflake Spark Connector

01

What is it

A Spark DataSource (v2 API) that lets Apache Spark read from and write to Snowflake tables. It serialises data to Parquet, stages it in S3/ADLS/GCS, and uses COPY INTO to load — bypassing JDBC row-at-a-time overhead.

02

Why it matters

Many enterprises run ML/data science workloads in Spark (Databricks, EMR, GCP Dataproc) but store governed data in Snowflake. The connector lets both sides coexist without manual ETL scripts.

03

How it works

Reads: Snowflake executes the query pushdown, exports result as Parquet to a stage, Spark reads the Parquet. Writes: Spark writes Parquet to a stage, Snowflake COPY INTO reads it. No row-at-a-time serialization.

Reading from Snowflake in PySpark

# spark-submit --packages net.snowflake:spark-snowflake_2.12:2.12.0-spark_3.3,\
#                            net.snowflake:snowflake-jdbc:3.13.30

SNOWFLAKE_SOURCE_NAME = "net.snowflake.spark.snowflake"

sfOptions = {
  "sfURL":       "myaccount.snowflakecomputing.com",
  "sfUser":      "spark_svc",
  "sfPassword":  "<password>",   # prefer pem_private_key
  "sfDatabase":  "ANALYTICS",
  "sfSchema":    "GOLD",
  "sfWarehouse": "SPARK_WH",
  "sfRole":      "SPARK_ROLE",
}

# Read a full table
df = spark.read \
  .format(SNOWFLAKE_SOURCE_NAME) \
  .options(**sfOptions) \
  .option("dbtable", "GOLD.SALES_FACT") \
  .load()

# Read using a custom query (Snowflake executes this, returns Parquet)
df = spark.read \
  .format(SNOWFLAKE_SOURCE_NAME) \
  .options(**sfOptions) \
  .option("query", "SELECT * FROM SALES_FACT WHERE sale_date >= '2024-01-01'") \
  .load()

df.printSchema()
df.show(5)

Writing to Snowflake from PySpark

# Write a Spark DataFrame back to Snowflake
df_result.write \
  .format(SNOWFLAKE_SOURCE_NAME) \
  .options(**sfOptions) \
  .option("dbtable", "GOLD.ML_PREDICTIONS") \
  .mode("overwrite") \   # or "append", "errorifexists", "ignore"
  .save()

# Merge mode — use Snowflake's COPY + MERGE via a staging table
df_result.write \
  .format(SNOWFLAKE_SOURCE_NAME) \
  .options(**sfOptions) \
  .option("dbtable", "STAGE.ML_PREDICTIONS_STAGE") \
  .mode("overwrite") \
  .save()
# Then trigger a Snowflake Task or stored procedure to MERGE from staging → gold

Query pushdown

The Spark connector pushes filter and projection operations down to Snowflake. If you call df.filter("region = 'EAST'"), Snowflake adds that predicate to its export query — only the filtered rows leave Snowflake. Enable explicitly if needed:

# Pushdown is on by default; verify or force via:
sfOptions["autopushdown"] = "on"

# To debug what SQL is pushed down, check the Snowflake QUERY_HISTORY
# after running the Spark job — look for queries from user spark_svc

Interview trap — Spark mode vs Snowflake truncate

Spark's .mode("overwrite") does NOT run TRUNCATE TABLE. It drops and recreates the target table, which loses your column masking policies, tags, grants, and clustering keys. For a safe overwrite, write to a staging table, then do an INSERT OVERWRITE or MERGE in Snowflake. Alternatively, use Snowpark for Python instead of the Spark connector — it runs entirely within Snowflake.

Chapter 03

CDC Pipeline: Debezium → Kafka → Snowpipe Streaming

01

What is it

An end-to-end change data capture (CDC) architecture that captures row-level changes from an OLTP database (MySQL, Postgres, Oracle) in real time and delivers them to Snowflake with sub-second latency.

02

Why it matters

Traditional ETL from OLTP databases is batch (nightly dumps). CDC captures every INSERT, UPDATE, DELETE as it happens — enabling real-time analytics, event-driven pipelines, and audit trails without touching the source.

03

How it works

Debezium reads the database transaction log (binlog / WAL). Each change event is published to a Kafka topic. The Snowflake Kafka Connector or Snowpipe Streaming SDK consumes the topic and writes to Snowflake.

Full architecture

MySQL binlog
→
Debezium (Kafka Connect source)
→
Kafka Topic (orders.changes)
→
Snowflake Kafka Connector or Snowpipe Streaming
→
Snowflake RAW table (VARIANT)
→
Stream + Task MERGE → CURATED

Debezium event envelope

Every Debezium event is a JSON envelope with before (old row state), after (new row state), and op (c=create, u=update, d=delete, r=snapshot read).

-- What a Debezium UPDATE event looks like in RECORD_CONTENT
{
  "before": { "order_id": 101, "status": "PENDING",   "amount": 100.00 },
  "after":  { "order_id": 101, "status": "CONFIRMED", "amount": 100.00 },
  "op":     "u",
  "ts_ms":  1710000000000
}

-- Apply CDC events to a Snowflake CURATED table using MERGE
MERGE INTO orders_curated tgt
USING (
  SELECT
    RECORD_CONTENT:op::STRING              AS op,
    RECORD_CONTENT:after:order_id::INT     AS order_id,
    RECORD_CONTENT:after:status::STRING    AS status,
    RECORD_CONTENT:after:amount::FLOAT     AS amount,
    RECORD_CONTENT:before:order_id::INT    AS del_order_id,
    RECORD_METADATA:CreateTime::BIGINT     AS kafka_ts,
    ROW_NUMBER() OVER(
      PARTITION BY COALESCE(
        RECORD_CONTENT:after:order_id::INT,
        RECORD_CONTENT:before:order_id::INT)
      ORDER BY RECORD_METADATA:CreateTime::BIGINT DESC
    ) AS rn
  FROM orders_kafka_raw
  QUALIFY rn = 1  -- keep only the latest event per order_id
) src ON tgt.order_id = COALESCE(src.order_id, src.del_order_id)
WHEN MATCHED AND src.op IN ('u', 'r') THEN
  UPDATE SET status = src.status, amount = src.amount
WHEN MATCHED AND src.op = 'd' THEN DELETE
WHEN NOT MATCHED AND src.op IN ('c', 'r') THEN
  INSERT (order_id, status, amount)
  VALUES (src.order_id, src.status, src.amount);

Snowpipe Streaming SDK (low-latency alternative)

For sub-second latency, bypass Kafka Connect entirely. The Snowpipe Streaming Java/Python SDK opens a persistent channel to Snowflake and streams rows directly — no staging files, no Snowpipe overhead.

# Python Snowpipe Streaming SDK (conceptual)
from snowflake.ingest import SimpleIngestManager

# The SDK maintains an open channel; you push rows as Python dicts
# Latency: ~1 second (vs ~90 seconds for file-based Snowpipe)
# Use when: real-time dashboards, fraud detection, operational analytics
# Cost model: serverless credits per row ingested (not per warehouse minute)

Interview trap — initial snapshot

Debezium starts capturing from the binlog at a point in time. For existing data before CDC was enabled, you must do an initial snapshot (Debezium's snapshot.mode=initial or a separate bulk load). The snapshot emits op: "r" (read) events. Your MERGE must handle r as an INSERT or UPSERT — do not filter it out.

Senior angle — ordering guarantees

Kafka partitions guarantee order within a partition. If a table's CDC events land in multiple partitions (e.g., partitioned by order_id hash), the Kafka Connector may write events out of order per row. The QUALIFY ROW_NUMBER() trick in the MERGE above handles this by picking the latest event per key — but it means the raw table is the definitive log, and the curated table is the latest state only. Keep the raw table for full audit / time travel.

Chapter 04

External Functions & API Integration

01

What is it

A mechanism to call an external REST API (via AWS API Gateway, Azure API Management, or GCP API Gateway) from within a Snowflake SQL query — as if it were a native UDF. The function sends rows out in batches and receives results back.

02

Why it matters

Enables SQL-native calls to: ML models hosted outside Snowflake, address standardisation APIs, geocoding services, fraud scoring engines, or any HTTP-based service — without writing a data pipeline or Snowpark stored procedure.

03

How it works

Snowflake sends a POST request with a JSON batch of rows to your API endpoint. Your function processes them and returns a JSON array of results. Snowflake maps results back to output rows. Auth is via the API Integration object (OAuth or IAM).

Setup: API Integration + External Function

-- Step 1: Create the API Integration (connects Snowflake to your API Gateway)
USE ROLE ACCOUNTADMIN;

CREATE OR REPLACE API INTEGRATION fraud_score_api
  API_PROVIDER = aws_api_gateway
  API_AWS_ROLE_ARN = 'arn:aws:iam::123456789:role/snowflake-external-fn-role'
  API_ALLOWED_PREFIXES = ('https://abc123.execute-api.us-east-1.amazonaws.com/prod/')
  ENABLED = TRUE;

-- Get the values to configure the IAM trust policy on the AWS side
DESCRIBE INTEGRATION fraud_score_api;
-- Note: API_AWS_IAM_USER_ARN and API_AWS_EXTERNAL_ID
-- Add these to the trust policy of the AWS role above

-- Step 2: Create the external function
CREATE OR REPLACE EXTERNAL FUNCTION score_fraud(
  transaction_id  VARCHAR,
  amount          FLOAT,
  merchant_code   VARCHAR
)
RETURNS VARIANT
API_INTEGRATION = fraud_score_api
AS 'https://abc123.execute-api.us-east-1.amazonaws.com/prod/fraud-score';

-- Step 3: Call it in a query — Snowflake batches the rows and sends them
SELECT
  t.transaction_id,
  t.amount,
  score_fraud(t.transaction_id, t.amount, t.merchant_code) AS fraud_result,
  fraud_result:score::FLOAT                                 AS fraud_score,
  fraud_result:risk_band::STRING                            AS risk_band
FROM transactions t
WHERE t.transaction_date = CURRENT_DATE();

Request / response format

Snowflake sends a JSON POST body. Your Lambda / API handler must accept and return this exact shape:

// Snowflake sends (data = array of [row_number, col1, col2, ...])
{
  "data": [
    [0, "TXN001", 450.00, "MCH_GROCERY"],
    [1, "TXN002", 9999.99, "MCH_JEWELLERY"]
  ]
}

// Your API must return (data = array of [row_number, result])
{
  "data": [
    [0, {"score": 0.12, "risk_band": "LOW"}],
    [1, {"score": 0.94, "risk_band": "HIGH"}]
  ]
}

Interview trap — batch size and latency

External functions are designed for batch calls (Snowflake groups rows into batches of up to 10,000 by default). They are not suitable for sub-100ms row-at-a-time calls. Each API call has network round-trip latency. If latency is critical, materialise the scores into a Snowflake table using a scheduled Task rather than calling the API inline on every SELECT.

Senior angle — External Functions vs Cortex

Snowflake Cortex (Module 11) provides built-in LLM and ML functions natively — no API Integration needed. If your use case is text classification, summarisation, or embedding generation, Cortex is simpler and cheaper. Use External Functions when you need a specific proprietary model or service that Cortex doesn't provide (e.g., your company's internal fraud model, a third-party geocoding API).

Hands-on: Simulate a CDC pipeline in Snowflake

This lab simulates the Debezium → Kafka → Snowflake CDC pattern entirely within Snowflake by inserting mock Debezium-shaped events and applying them with MERGE. No external Kafka cluster needed.

1

Set up the environment

USE ROLE SYSADMIN;
CREATE DATABASE IF NOT EXISTS CDC_LAB;
CREATE SCHEMA IF NOT EXISTS   CDC_LAB.DEMO;
CREATE WAREHOUSE IF NOT EXISTS CDC_WH
  WAREHOUSE_SIZE = 'XSMALL' AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
USE CDC_LAB.DEMO;
USE WAREHOUSE CDC_WH;
SHOW DATABASES includes CDC_LAB.
2

Create the RAW (Kafka landing) and CURATED tables

-- Simulates the auto-created table from the Kafka Connector
CREATE OR REPLACE TABLE orders_kafka_raw (
  RECORD_CONTENT   VARIANT,
  RECORD_METADATA  VARIANT
);

-- Target curated table
CREATE OR REPLACE TABLE orders_curated (
  order_id    INT PRIMARY KEY,
  customer_id INT,
  status      VARCHAR,
  amount      FLOAT,
  updated_at  TIMESTAMP_NTZ
);
Both tables created. SHOW TABLES lists 2 tables.
3

Insert mock Debezium CDC events (snapshot + changes)

-- Initial snapshot (op = 'r')
INSERT INTO orders_kafka_raw SELECT
  PARSE_JSON('{"op":"r","after":{"order_id":1,"customer_id":100,"status":"CONFIRMED","amount":250.00}}'),
  PARSE_JSON('{"CreateTime":1710000000000,"offset":0,"partition":0}');
INSERT INTO orders_kafka_raw SELECT
  PARSE_JSON('{"op":"r","after":{"order_id":2,"customer_id":101,"status":"PENDING","amount":99.99}}'),
  PARSE_JSON('{"CreateTime":1710000001000,"offset":1,"partition":0}');

-- New order (op = 'c' create)
INSERT INTO orders_kafka_raw SELECT
  PARSE_JSON('{"op":"c","after":{"order_id":3,"customer_id":102,"status":"PENDING","amount":420.00}}'),
  PARSE_JSON('{"CreateTime":1710000002000,"offset":2,"partition":0}');

-- Update (op = 'u')
INSERT INTO orders_kafka_raw SELECT
  PARSE_JSON('{"op":"u","before":{"order_id":2},"after":{"order_id":2,"customer_id":101,"status":"CONFIRMED","amount":99.99}}'),
  PARSE_JSON('{"CreateTime":1710000003000,"offset":3,"partition":0}');

-- Delete (op = 'd')
INSERT INTO orders_kafka_raw SELECT
  PARSE_JSON('{"op":"d","before":{"order_id":3,"customer_id":102,"status":"PENDING","amount":420.00}}'),
  PARSE_JSON('{"CreateTime":1710000004000,"offset":4,"partition":0}');
SELECT COUNT(*) FROM orders_kafka_raw = 5.
4

Apply CDC events with MERGE

MERGE INTO orders_curated tgt
USING (
  SELECT
    RECORD_CONTENT:op::STRING                              AS op,
    COALESCE(
      RECORD_CONTENT:after:order_id::INT,
      RECORD_CONTENT:before:order_id::INT)                 AS order_id,
    RECORD_CONTENT:after:customer_id::INT                  AS customer_id,
    RECORD_CONTENT:after:status::STRING                    AS status,
    RECORD_CONTENT:after:amount::FLOAT                     AS amount,
    RECORD_METADATA:CreateTime::BIGINT                     AS kafka_ts,
    ROW_NUMBER() OVER(
      PARTITION BY COALESCE(
        RECORD_CONTENT:after:order_id::INT,
        RECORD_CONTENT:before:order_id::INT)
      ORDER BY RECORD_METADATA:CreateTime::BIGINT DESC
    ) AS rn
  FROM   orders_kafka_raw
  QUALIFY rn = 1
) src ON tgt.order_id = src.order_id
WHEN MATCHED AND src.op IN ('u', 'r') THEN
  UPDATE SET
    status     = src.status,
    amount     = src.amount,
    updated_at = TO_TIMESTAMP_NTZ(src.kafka_ts/1000)
WHEN MATCHED AND src.op = 'd' THEN DELETE
WHEN NOT MATCHED AND src.op IN ('c', 'r') THEN
  INSERT (order_id, customer_id, status, amount, updated_at)
  VALUES (src.order_id, src.customer_id, src.status, src.amount,
          TO_TIMESTAMP_NTZ(src.kafka_ts/1000));
SELECT * FROM orders_curated — should have 2 rows: order_id=1 (CONFIRMED) and order_id=2 (CONFIRMED, updated). Order 3 was deleted and must not appear.
Order 3 had op='c' (insert) followed by op='d' (delete). The QUALIFY keeps only the latest event (the delete), so the MERGE sees op='d' with no existing row in curated. WHEN MATCHED AND op='d' won't fire (no match). Add a WHEN NOT MATCHED AND op != 'd' guard to avoid inserting deleted rows.
5

Add a stream on the raw table and automate with a task

CREATE OR REPLACE STREAM orders_cdc_stream
  ON TABLE orders_kafka_raw
  APPEND_ONLY = TRUE;  -- Kafka raw is append-only; use append-only stream

CREATE OR REPLACE TASK apply_cdc_task
  WAREHOUSE = CDC_WH
  SCHEDULE = '1 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('orders_cdc_stream')
AS
MERGE INTO orders_curated tgt
USING (
  SELECT
    RECORD_CONTENT:op::STRING                              AS op,
    COALESCE(
      RECORD_CONTENT:after:order_id::INT,
      RECORD_CONTENT:before:order_id::INT)                 AS order_id,
    RECORD_CONTENT:after:customer_id::INT                  AS customer_id,
    RECORD_CONTENT:after:status::STRING                    AS status,
    RECORD_CONTENT:after:amount::FLOAT                     AS amount,
    RECORD_METADATA:CreateTime::BIGINT                     AS kafka_ts,
    ROW_NUMBER() OVER(
      PARTITION BY COALESCE(
        RECORD_CONTENT:after:order_id::INT,
        RECORD_CONTENT:before:order_id::INT)
      ORDER BY RECORD_METADATA:CreateTime::BIGINT DESC
    ) rn
  FROM   orders_cdc_stream
  QUALIFY rn = 1
) src ON tgt.order_id = src.order_id
WHEN MATCHED AND src.op IN ('u','r') THEN
  UPDATE SET status=src.status,amount=src.amount,updated_at=TO_TIMESTAMP_NTZ(src.kafka_ts/1000)
WHEN MATCHED AND src.op='d' THEN DELETE
WHEN NOT MATCHED AND src.op IN ('c','r') THEN
  INSERT(order_id,customer_id,status,amount,updated_at)
  VALUES(src.order_id,src.customer_id,src.status,src.amount,TO_TIMESTAMP_NTZ(src.kafka_ts/1000));

ALTER TASK apply_cdc_task RESUME;
SHOW TASKS shows apply_cdc_task with state=started. Insert a new CDC event into orders_kafka_raw; within 1 minute the task fires and the new row appears in orders_curated.
6

Cleanup

ALTER TASK apply_cdc_task SUSPEND;
DROP DATABASE IF EXISTS CDC_LAB;
DROP WAREHOUSE IF EXISTS CDC_WH;
Chapter 06

Interview Q&A

How does the Snowflake Kafka Connector handle schema evolution? TRICKY
Because the payload lands in a VARIANT column (RECORD_CONTENT), new fields in the Kafka message appear automatically with no schema change required on the raw table. Schema evolution affects the downstream curated layer: when a new field appears, you add a column to the curated table and update the MERGE/transform query. With Avro + Schema Registry, Debezium/Kafka enforces a schema contract and generates versioned schemas; Snowflake's INFER_SCHEMA can read the Avro schema from the stage to assist with the ALTER TABLE.
What is the difference between the Kafka Connector and Snowpipe Streaming? FUNDAMENTAL
The Kafka Connector uses file-based Snowpipe under the hood: it buffers records into files (up to buffer.flush.time seconds), uploads to an internal stage, then triggers Snowpipe. Latency is typically 90–120 seconds. Snowpipe Streaming (the SDK) opens a persistent channel and streams rows directly — no files, no stage — with ~1 second latency. Use Kafka Connector for throughput-oriented workloads where ~2 minutes is acceptable. Use Snowpipe Streaming for real-time dashboards, fraud detection, or operational analytics requiring sub-10-second freshness.
Spark .mode("overwrite") drops my Snowflake table. How do you avoid this? SCENARIO
Write to a dedicated staging table (e.g., ML_PREDICTIONS_STAGE), then use a Snowflake MERGE or INSERT OVERWRITE from the staging table into the target. This keeps the target table's tags, grants, masking policies, and clustering keys intact. Alternatively, use Snowpark for Python instead of the Spark connector — it runs transforms entirely within Snowflake and avoids cross-system data movement.
What is an API Integration and why is it needed for External Functions? FUNDAMENTAL
An API Integration is a Snowflake object that defines the trust relationship between Snowflake and your cloud-hosted API Gateway. It specifies the cloud provider (AWS, Azure, GCP), the IAM role ARN or service principal, and allowed URL prefixes. DESCRIBE INTEGRATION gives you the IAM trust details (IAM user ARN + external ID for AWS) that you add to your cloud IAM role trust policy. Without this handshake, Snowflake cannot authenticate to your endpoint. The External Function then references the API Integration to inherit these auth credentials.
A CDC pipeline is delivering duplicate rows to Snowflake. How do you diagnose and fix it? SCENARIO
Diagnosis: (1) Check RECORD_METADATA offset — if the same Kafka offset appears twice, the Kafka Connector reprocessed after a restart. (2) Check if two Kafka partitions have the same records (misconfigured partitioning). (3) Check if the Debezium snapshot overlapped with the stream. Fix: (1) The QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY CreateTime DESC) = 1 pattern in the MERGE source deduplicate by keeping only the latest event per key. (2) Snowpipe also deduplicates by file within a 1-hour window — ensure files are distinct. (3) For connector restarts, Kafka's exactly-once delivery (enable.idempotence=true + acks=all) prevents duplicate Kafka messages at the Kafka level.
When would you choose Spark over Snowpark for a transformation workload? TRICKY
Choose Spark when: (1) You need Spark-specific ML libraries (MLlib, XGBoost on Spark, graph algorithms via GraphX/Frames). (2) You have existing Spark-based pipelines and migrating is not cost-effective. (3) You need to join Snowflake data with datasets in other stores (S3, Delta Lake) in a single Spark job. (4) Your team is primarily Spark-native. Choose Snowpark when: the transformation logic is SQL-expressible or Python-expressible without Spark libraries, you want to eliminate data movement costs, and you prefer a single-platform governance model. The cost argument strongly favours Snowpark: no separate Spark cluster to manage or pay for.
What is the Debezium initial snapshot and how do you handle op='r' events? TRICKY
When Debezium first starts (or is reconfigured with snapshot.mode=initial), it reads every existing row from the source table and emits an event with op='r' (read). These look like CDC events but are full table reads, not incremental changes. In your MERGE: treat op='r' as UPSERT — WHEN NOT MATCHED AND op IN ('c','r') THEN INSERT, and WHEN MATCHED AND op IN ('u','r') THEN UPDATE. This correctly handles both: a snapshot row that doesn't yet exist in Snowflake (insert) and a re-snapshot of an existing row that may have been modified (update). Never filter out op='r' events.
Chapter 07

Quiz

1. What authentication method does the Snowflake Kafka Connector require?

✓ RSA key-pair authentication. The Kafka Connector does not support username/password. The RSA private key PEM is set in the connector config; the public key is registered on the Snowflake service account user.

2. What does Spark .mode("overwrite") do to a Snowflake table's masking policies?

✓ Drops and recreates. mode("overwrite") in the Spark connector drops the target table and recreates it, destroying all attached policies, grants, clustering keys, and tags. Write to a staging table instead.

3. A Debezium event has op='d'. How should your MERGE handle it?

✓ WHEN MATCHED AND op='d' THEN DELETE. If you want a soft delete for audit, UPDATE a deleted_at column instead. Hard DELETE is correct for GDPR right-to-erasure compliance.

4. What is the approximate ingestion latency difference between the Kafka Connector and Snowpipe Streaming SDK?

✓ The Kafka Connector buffers records into files before triggering Snowpipe (~90–120s). Snowpipe Streaming opens a persistent channel and streams rows directly (~1s). The tradeoff: Streaming is more expensive per row.

5. What must your API return for an External Function to work correctly?

✓ {"data": [[0, result0], [1, result1], ...]}. The row number must match what Snowflake sent so results map back to the correct rows. Missing or reordered row numbers cause Snowflake to raise an error.
Chapter 08

Cheat sheet

Kafka Connector

Kafka topic → buffer (buffer.flush.time) → Internal Stage → Snowpipe → RECORD_CONTENT VARIANT + RECORD_METADATA VARIANT. Auth = RSA key-pair. Latency ~90–120s.

Kafka buffer tuning

buffer.count.records (rows per file), buffer.flush.time (max seconds before flush), buffer.size.bytes. Too high = consumer lag + replay on restart. Too low = many small files = Snowpipe overhead.

Spark Connector

Read: Snowflake exports Parquet to stage → Spark reads. Write: Spark writes Parquet to stage → COPY INTO. mode("overwrite") drops table. Use staging table + MERGE for safe writes.

Spark vs Snowpark

Spark = external cluster + Spark libraries. Snowpark = inside Snowflake, no data movement, lower cost. Choose Spark only for Spark-specific ML libs or cross-store joins.

CDC with Debezium

op: c=create, u=update, d=delete, r=snapshot. MERGE handles all 4. QUALIFY ROW_NUMBER()=1 to dedup per key on kafka_ts. Keep raw table as audit log.

Snowpipe Streaming

Java/Python SDK. Persistent channel. ~1s latency. No staging files. Priced per row (serverless). Best for fraud, real-time dashboards, IoT.

External Functions

CREATE API INTEGRATION (cloud IAM trust) → CREATE EXTERNAL FUNCTION (references integration + endpoint URL). Input/output: {"data":[[row_num, val],...]}. Batch by default; not for sub-100ms per-row calls.

External Functions vs Cortex

Cortex = built-in LLM/ML (no API Integration). External Functions = custom/proprietary APIs. Use Cortex first; External Functions for what Cortex can't do.
