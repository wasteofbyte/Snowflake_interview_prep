MODULE 12 · ADVANCED SQL · LIVE-CODING ROUND PREP

Think in sets.
Code it live.

Every Snowflake interview for a senior developer has a live SQL round. They aren't testing whether you remember syntax. They're testing whether you can turn a business question ("top 3 products per region", "users active 5 days in a row", "who never ordered?") into correct, readable SQL that handles ties, NULLs and duplicates, and then explain why it works. This module builds that skill from the ground up: how a query really executes, window functions, QUALIFY, recursive CTEs, ROLLUP and PIVOT, ASOF and anti-joins, MATCH_RECOGNIZE, and finally a bank of 11 classic interview problems with hints and full solutions.

Four mental pictures we'll use all the way through:

LOGICAL ORDER
An assembly line

A query is a line of stations: first fetch the rows (FROM), then filter, then group, then rank, then pick columns, then sort. Each station only sees what the previous one handed over.

WINDOW FUNCTION
A train window

Each row is a passenger looking out of a window at its neighbours. It can count, sum or rank what it sees, but it stays in its seat: no rows are merged away, unlike GROUP BY.

CTE / RECURSION
Named scratch notes

A CTE is a labelled note you write before the final answer. A recursive CTE is a family tree: start with the grandparent, then repeatedly add "children of the people I just found".

QUALIFY
The bouncer after the ranking

WHERE checks tickets at the door, before anyone is ranked. QUALIFY stands after the ranking and only lets in "rank = 1". That's why you can't filter a window function in WHERE.

How a live-coding round is scored

1 · Clarify before typing

Ask: ties? NULLs? duplicates in the source? what if a group is empty? "Top 3" with ties means RANK, without ties means ROW_NUMBER. These questions earn points by themselves.

2 · Say the shape out loud

"I'll partition by customer, order by date, then use LAG to compare with the previous row." Name the grain of each CTE. Interviewers follow your reasoning, not just the final query.

3 · Test with a tiny table

Walk two or three rows through your query by hand, including one edge case (a tie, a NULL, a single-row group). Then mention cost: one pass vs a self-join, sort size, and alternatives.

CHAPTER 01

How SQL executes · the logical order of a query

01 · WHAT IS IT

You write a query starting with SELECT, but the database evaluates it in a different order. The logical order is:

FROM / JOIN → WHERE → GROUP BY → HAVING → WINDOW functions → QUALIFY → SELECT (projection) → DISTINCT → ORDER BY → LIMIT

Each clause receives a row set, transforms it, and hands the result to the next one. This is the logical meaning of the query: it defines what the answer must be.

02 · WHY IT MATTERS
  • It explains almost every "why does this error?" question: you can't use a window function in WHERE (windows haven't been computed yet), and you can't use an aggregate in WHERE (groups don't exist yet).
  • It tells you where to filter: filter rows in WHERE (cheap, early), groups in HAVING, window results in QUALIFY.
  • It's the foundation for reading other people's SQL and for debugging wrong counts in an interview.
03 · HOW IT WORKS · LOGICAL vs PHYSICAL

The logical order is a contract, not a recipe. Snowflake's optimizer (in cloud services) is free to execute things physically in any order that gives the same answer: it pushes filters down into the table scan so that micro-partitions are pruned using min/max metadata, reorders joins, and may aggregate before a join. In the Query Profile you'll see operators like TableScan, Filter, Join, Aggregate, WindowFunction, Sort and Limit, often not in the order you wrote them.

INTERVIEW TRAP
"Why does WHERE ROW_NUMBER() OVER (...) = 1 fail?" Because WHERE runs before window functions exist. In most databases you wrap the query in a subquery and filter outside. In Snowflake you simply write QUALIFY ROW_NUMBER() OVER (...) = 1.
SENIOR ANGLE
Snowflake is lenient: it lets you reference a SELECT-list alias in WHERE, GROUP BY, HAVING and QUALIFY (and in later expressions of the same SELECT list). That's a Snowflake convenience, not standard SQL. If an alias has the same name as a real column, the column usually wins in WHERE, so avoid alias names that shadow columns.

CHAPTER 02

Window functions · calculations across related rows

01 · WHAT IS IT

A window function computes a value for each row using a set of related rows, its window, without collapsing the rows. You recognise it by the OVER (...) clause.

SUM(amount) OVER ( PARTITION BY region ORDER BY sale_date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW )
  • function: what to compute (SUM, ROW_NUMBER, LAG…)
  • PARTITION BY: split rows into independent groups (like GROUP BY, but rows survive)
  • ORDER BY: the order of rows inside each partition
  • frame: which rows around the current row are included
02 · WHY WE USE IT

GROUP BY answers "total per region" but loses the detail rows. Window functions give you detail and context together: each sale and its region's running total, each employee and their rank in the department, each day and yesterday's value.

  • Running totals and moving averages
  • Ranking, top-N and deduplication
  • Comparing with the previous or next row (LAG/LEAD)
  • Share of total (RATIO_TO_REPORT), buckets (NTILE)

Without them you'd need self-joins, which are slower and harder to read.

03 · HOW IT WORKS · IN THE ENGINE

Window functions run after WHERE, GROUP BY and HAVING. The engine redistributes rows by the PARTITION BY key so each partition lands on one worker, sorts each partition by the ORDER BY key, then streams through the sorted rows computing the function, keeping a running state (for a running SUM) or a small buffer (for a 3-row moving average). In the Query Profile this shows as a WindowFunction operator, usually fed by a sort. Several window functions with the same PARTITION BY and ORDER BY can typically share one sort.

Cost drivers: the size of the biggest partition (one huge partition can't be split across workers and may spill to disk), the sort, and frames like "UNBOUNDED FOLLOWING" that need the whole partition buffered. No PARTITION BY at all means one global partition, which is the slowest case on big tables.

  • ROW_NUMBER: always unique 1, 2, 3… Ties are broken arbitrarily (non-deterministic) unless you add a tie-breaker column.
  • RANK: ties share a rank, then it skips (1, 2, 2, 4), like Olympic medals.
  • DENSE_RANK: ties share a rank, no gaps (1, 2, 2, 3). Use it for "Nth highest distinct value".

None of these accept a frame, and all of them need ORDER BY inside OVER.

ROWS vs RANGE: the frame that bites

ROWS = physical rows

ROWS BETWEEN 2 PRECEDING AND CURRENT ROW means "this row and the 2 rows physically before it in sort order", no matter what values they have. Use it for moving averages and running balances.

RANGE = logical peers

RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW includes every row with the same ORDER BY value as the current row (its peers). Two sales on the same date both get the same running total. Try it in the simulator: SUM, ORDER BY sale_date, frame "not written".

INTERVIEW TRAP
LAST_VALUE "doesn't work". In ANSI SQL, when you write ORDER BY but no frame, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. The frame stops at the current row, so LAST_VALUE(x) returns the current row's value (or its last peer), not the partition's last value. Defaults for FIRST_VALUE/LAST_VALUE have differed between engines and versions, so check Snowflake's docs for its exact default; the interview-safe answer is to always write the frame: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. Even simpler: use FIRST_VALUE(x) OVER (... ORDER BY d DESC).
LAG / LEAD

LAG(amount, 1, 0) OVER (PARTITION BY rep ORDER BY sale_date): the value 1 row back, defaulting to 0 instead of NULL. LEAD looks forward. Snowflake supports IGNORE NULLS to skip NULL values (handy to "carry forward" the last known value).

NTILE(n)

Splits each ordered partition into n buckets as evenly as possible; earlier buckets get the extra row. NTILE(4) = quartiles. Buckets are by row count, not by value, so ties can straddle buckets.

RATIO_TO_REPORT

RATIO_TO_REPORT(amount) OVER (PARTITION BY region) = amount ÷ SUM(amount) of the partition, i.e. share of total. It takes no ORDER BY or frame. Equivalent to amount / SUM(amount) OVER (PARTITION BY region).

SENIOR ANGLE
Determinism. If ORDER BY in a window has ties, ROW_NUMBER, LAG, FIRST_VALUE and ROWS frames can return different results on different runs, because rows with equal keys may arrive in any order across parallel workers. Always add a unique tie-breaker (ORDER BY sale_date, sale_id). Flaky results in a pipeline are a classic production bug that interviewers like to probe.
CHAPTER 03

QUALIFY · top-N per group and deduplication

01 · WHAT IS IT

QUALIFY is a filter clause that runs after window functions are computed. It does for window functions what HAVING does for aggregates.

SELECT dept, emp, salary FROM employees QUALIFY ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) <= 2;

QUALIFY isn't in the ANSI standard. Snowflake, BigQuery, Databricks and Teradata support it; in Postgres or SQL Server you'd use a subquery.

02 · WHY WE USE IT

Without QUALIFY you write the window in a subquery or CTE, then filter it outside. QUALIFY removes that nesting:

  • Top-N per group: best 3 products per region
  • Dedup / latest row per key: keep the newest version of each customer
  • Compare to the group: orders above twice the customer's average

It's shorter, easier to read in an interview, and the window column doesn't have to appear in the output.

03 · HOW IT WORKS

QUALIFY sits between the window step and the final projection in the logical order (Chapter 01). Physically it becomes a Filter operator right after the WindowFunction operator. It can't reduce how much data is scanned: the window needs all rows of each partition first. So filter rows in WHERE first (dates, status), then rank with QUALIFY. The choice of ranking function decides what happens with ties, which is exactly what the simulator shows.

INTERVIEW TRAP
Dedup with RANK keeps duplicates. Two rows that are exact copies (same key, same timestamp) tie, so RANK() = 1 keeps both. Use ROW_NUMBER() for dedup, and add a tie-breaker (e.g. load_id DESC) so the chosen row is deterministic.
SENIOR ANGLE
QUALIFY can use any window expression, not just ranks: QUALIFY amount > 2 * AVG(amount) OVER (PARTITION BY customer_id) finds unusually large orders, and QUALIFY COUNT(*) OVER (PARTITION BY email) > 1 lists every row of a duplicated key (handy for data-quality checks before a MERGE).
CHAPTER 04

CTEs & recursive CTEs · named steps and hierarchies

01 · WHAT IS IT

A CTE (common table expression) is a named, temporary result defined with WITH name AS (SELECT …) that exists only for one statement. A recursive CTE refers to itself: it starts with an anchor query and repeatedly applies a recursive query to the rows found in the previous round until no new rows appear.

Classic uses: employee → manager hierarchies, bill of materials (parts within parts), folder trees, graph paths, and generating series of dates or numbers.

02 · WHY WE USE IT
  • Readability: break a hard query into named steps (daily, ranked, final), each with a clear grain. In interviews this is the single best habit.
  • Reuse: reference the same CTE several times in one statement.
  • Hierarchies of unknown depth: a fixed number of self-joins only handles a fixed number of levels; recursion handles any depth.
03 · HOW IT WORKS

Plain CTE: the optimizer decides whether to compute it once and reuse it, or inline it like a subquery. In the Query Profile, a reused CTE shows up as WithClause / WithReference operators. A CTE is not a temp table: it isn't stored or indexed and disappears when the statement ends.

Recursive CTE: iteration 0 runs the anchor. Each later iteration runs the recursive member only against the rows produced by the previous iteration (the "working table"), and all iterations are combined with UNION ALL. It stops when an iteration returns zero rows. Snowflake caps recursion depth by default (the limit can be raised through Snowflake support; check the docs for the current value), so a cycle in the data ends in an error rather than running forever, but you should still guard against cycles yourself.

SENIOR ANGLE
Snowflake also supports Oracle-style CONNECT BY (START WITH manager_id IS NULL CONNECT BY PRIOR emp_id = manager_id, with LEVEL and SYS_CONNECT_BY_PATH). Recursive CTEs are more portable and more flexible (e.g. multiple joins in the recursive step). For very deep or wide graphs, recursion runs serially iteration by iteration, so consider materialising a closure table (ancestor, descendant, depth) refreshed by a task or dynamic table.
INTERVIEW TRAP
"Generate every date in 2024" with a recursive CTE works, but in Snowflake the idiomatic answer is SELECT DATEADD('day', SEQ4(), '2024-01-01'::DATE) FROM TABLE(GENERATOR(ROWCOUNT => 366)). Caution: SEQ4() can have gaps in theory; ROW_NUMBER() OVER (ORDER BY SEQ4()) - 1 is gap-free. A date spine like this is the standard fix for "missing days" in reports.
CHAPTER 05

Grouping power · ROLLUP, CUBE, GROUPING SETS, PIVOT

01 · WHAT IS IT

Extensions to GROUP BY that compute several groupings in one query:

  • ROLLUP(region, product): detail, subtotal per region, grand total (a hierarchy)
  • CUBE(region, product): every combination: per region, per product, both, and total
  • GROUPING SETS ((region), (product), ()): exactly the groupings you list
  • GROUPING(col): 1 when that column was rolled up in this row, 0 otherwise

Plus PIVOT (rows → columns), UNPIVOT (columns → rows), and handy aggregates: COUNT_IF, LISTAGG, ARRAY_AGG.

02 · WHY WE USE IT

Reports need subtotals and totals. Without ROLLUP you'd write three GROUP BY queries and UNION ALL them, which means three scans of the table and three places to keep in sync. ROLLUP/CUBE do it in one pass. PIVOT turns "one row per quarter" into "one column per quarter", the shape a spreadsheet or dashboard wants.

03 · HOW IT WORKS

The engine expands the grouping specification into a list of grouping sets and aggregates the input once per set (it can reuse the finest-grained aggregate to compute coarser ones). Columns that are not part of a row's grouping set are returned as NULL. That's why GROUPING() exists: it tells a "subtotal NULL" apart from a real NULL value in the data. Output order is not guaranteed; add ORDER BY.

Conditional aggregation & list aggregates

SELECT region, COUNT(*) AS orders, COUNT_IF(status = 'RETURNED') AS returned, SUM(IFF(quarter = 'Q1', amount, 0)) AS q1_amount, SUM(CASE WHEN quarter = 'Q2' THEN amount ELSE 0 END) AS q2_amount, LISTAGG(DISTINCT product, ', ') WITHIN GROUP (ORDER BY product) AS products, ARRAY_AGG(amount) WITHIN GROUP (ORDER BY amount DESC) AS amounts FROM sales_q GROUP BY region;
  • Conditional aggregation (SUM(IFF(...)) or SUM(CASE …)) is the portable, manual PIVOT. Interviewers often ask for it explicitly because it works everywhere and handles many conditions at once.
  • COUNT_IF(cond) is Snowflake shorthand for SUM(IFF(cond, 1, 0)).
  • LISTAGG(col, ', ') concatenates values into one string; ARRAY_AGG builds an ARRAY (VARIANT). Both ignore NULLs and accept DISTINCT and WITHIN GROUP (ORDER BY …).
  • Watch output size: LISTAGG/ARRAY_AGG results are limited by Snowflake's maximum value size (check docs for the current limit), so don't aggregate millions of values into one cell.
INTERVIEW TRAP
PIVOT groups by every column you didn't mention. PIVOT implicitly groups by all input columns except the pivot column and the aggregated column. If the source has an order_id column, you get one row per order instead of one per region. Always feed PIVOT a subquery that selects only the grouping column, the pivot column and the value column.
SENIOR ANGLE
Dynamic pivot. Classic PIVOT needs a hard-coded list (IN ('Q1','Q2')). Snowflake also accepts IN (ANY ORDER BY quarter) or IN (SELECT DISTINCT quarter FROM …), so new quarters become new columns automatically, and DEFAULT ON NULL (0) replaces missing cells. Trade-off: the output schema now changes with the data, which can break downstream views and BI tools that expect fixed columns.
CHAPTER 06

Special joins · ASOF, semi/anti, self, range, lateral

01 · WHAT IS IT
  • Semi join: "rows of A that have a match in B" (EXISTS / IN). Each A row appears at most once.
  • Anti join: "rows of A with no match in B" (NOT EXISTS, LEFT JOIN … WHERE b.key IS NULL, or NOT IN, which has a NULL trap).
  • ASOF JOIN: for each row of A, the closest earlier (or later) row of B by time, e.g. each trade with the latest quote at that moment.
  • Self join: a table joined to itself (employee to manager).
  • Range join: join on an interval (e.ts BETWEEN p.start_ts AND p.end_ts) instead of equality.
  • Lateral join: the right side can reference columns of the left row; in Snowflake mostly LATERAL FLATTEN over arrays and table functions.
02 · WHY WE USE IT

Real questions are rarely plain equi-joins: "customers who never ordered" (anti), "orders that had at least one return" (semi, without duplicating orders), "price at the time of the trade" (ASOF), "sessions during a promotion" (range).

Choosing the right form avoids wrong answers (the NOT IN + NULL trap, duplicate rows from a plain join used as a filter) and slow plans (range joins without an equality key can explode).

03 · HOW IT WORKS

Equality joins in Snowflake usually run as hash joins: build a hash table on the smaller side, probe it with the bigger side; the profile can show join filters that skip probe-side micro-partitions. EXISTS/IN/NOT EXISTS are typically rewritten to semi/anti hash joins, which stop at the first match. A pure range condition can't be hashed, so the engine compares many row pairs (close to a cartesian product + filter): always add an equality key if you can (same symbol, same day bucket). ASOF JOIN is a dedicated operator: it partitions both sides by the ON keys, orders by time, and picks one best match per left row in a single pass, much cheaper than the classic "join all earlier quotes, then rank with ROW_NUMBER" workaround.

Self join: earning more than their manager
SELECT e.name, e.salary, m.name AS manager, m.salary AS mgr_salary FROM employees e JOIN employees m ON e.manager_id = m.emp_id WHERE e.salary > m.salary;

Two aliases of the same table, joined on the hierarchy key. Use LEFT JOIN if employees without a manager must stay.

Range join: sales during a promotion
SELECT s.sale_id, p.promo_name FROM sales s JOIN promos p ON s.store_id = p.store_id -- equality key first AND s.sale_ts >= p.start_ts AND s.sale_ts < p.end_ts; -- half-open interval

The equality key keeps the join hashable; the range filters within each store. Half-open intervals avoid double-counting at boundaries.

Lateral: explode an array per row
SELECT o.order_id, f.value:sku::STRING AS sku FROM orders o, LATERAL FLATTEN(INPUT => o.items) f;

FLATTEN runs once per order row and can see o.items. That "right side sees the left row" property is what LATERAL means. (Semi-structured details are in Module 06.)

Semi join: orders with at least one return
SELECT o.* FROM orders o WHERE EXISTS (SELECT 1 FROM returns r WHERE r.order_id = o.order_id);

A plain JOIN returns would repeat an order once per returned item. EXISTS returns each order once.

INTERVIEW TRAP
Join explosion. Joining two tables on a key that is not unique on either side multiplies rows (3 order lines × 2 shipments = 6 rows), and then SUM(amount) is silently inflated. Before any join, ask "what is the grain of each side?" Aggregate to the join grain first, or check with QUALIFY COUNT(*) OVER (PARTITION BY key) > 1.
SENIOR ANGLE
ASOF JOIN behaves like a left outer join: trades with no qualifying quote are kept with NULLs. The match condition takes one comparison (>=, >, <=, <), and the ON clause holds equality keys such as the symbol. Before ASOF existed, the pattern was a range join plus QUALIFY ROW_NUMBER() OVER (PARTITION BY trade_id ORDER BY quote_ts DESC) = 1, which still works on any engine but can be far more expensive on large tick tables.
CHAPTER 07

MATCH_RECOGNIZE · regular expressions over rows

01 · WHAT IS IT

MATCH_RECOGNIZE finds sequences of rows that match a pattern, the way a regular expression finds sequences of characters. You classify each row with a symbol (DOWN if the price fell, UP if it rose), then search for a pattern like STRT DOWN+ UP+: a V-shape.

It's part of the SQL:2016 standard (row pattern recognition); Snowflake and Oracle implement it.

02 · WHY WE USE IT

Sequence questions are painful with LAG and self-joins: "V-shaped price recoveries", "3 failed logins followed by a success", "funnel: view → cart → purchase within 1 hour", "sessions split by 30 minutes of inactivity". MATCH_RECOGNIZE expresses them declaratively in one clause and processes each partition in a single ordered pass.

03 · HOW IT WORKS
The clauses, in order

PARTITION BY / ORDER BY: like a window. MEASURES: output columns (MATCH_NUMBER(), CLASSIFIER(), FIRST(...), LAST(...)). ONE ROW PER MATCH or ALL ROWS PER MATCH. AFTER MATCH SKIP …: where to resume. PATTERN: the regex over symbols. DEFINE: the condition for each symbol.

What the engine does

Rows are partitioned and sorted, then a pattern-matching state machine walks each partition. A symbol without a DEFINE (like STRT) matches any row. Quantifiers + * ? {n,m} are greedy by default. After a match, AFTER MATCH SKIP decides whether matches may share rows: SKIP PAST LAST ROW (no overlap, default) or SKIP TO LAST UP (the last row of one V can start the next).
