JSON → S3 → Snowflake

The whole pipeline end to end, mostly as diagrams.

Q

“You have data in JSON. Load it into Snowflake using S3. Walk me through it end to end.”

The 30-second answer (say it out loud)

AWS side Snowflake side
  1. Land it in S3The producer writes NDJSON (gzip) to s3://shopstream-raw-landing/landing/ under clear prefixes, aiming for 100–250 MB files.
  2. Grant access without keysCreate an IAM role and a storage integration, then lock the trust policy to Snowflake’s IAM user and external ID.
  3. Point at itCreate a JSON file format and an external stage on the prefix, then LIST it to prove access works.
  4. Load rawUse COPY INTO a VARIANT table for the backfill, and Snowpipe (S3 event → SQS) for new files.
  5. Model itCast paths (raw:customer.address.city::STRING), LATERAL FLATTEN the items, and keep it incremental with a stream + task MERGE.
  6. Make it safeValidate first, use ON_ERROR plus a quarantine table, rely on idempotent load metadata, and monitor COPY_HISTORY.

Big pictureArchitecture, end to end

Amber is AWS and ice-blue is Snowflake. The moving dashes show where data flows, and the double arrow is the trust relationship.

02

Security handshakeSnowflake IAM user ↔ AWS IAM role

You never paste an access key into Snowflake. Snowflake has its own AWS IAM user, and your role lets that user in only when the request carries your external ID.

Why no access keys?

The integration stores only a role ARN. AWS issues temporary credentials on each assume, so you have nothing to rotate. Revoking access means editing the trust policy and nothing else. Admins create the integration once and grant USAGE to engineers.

External ID = confused-deputy guard

Many Snowflake customers can share the same Snowflake IAM user. The external ID is unique to your integration, so another account can’t point its integration at your role ARN and read your bucket.

Classic gotcha

Running CREATE OR REPLACE on the integration can generate a new external ID, which breaks the trust and gives you “access denied” on the next LIST. Prefer ALTER, and run DESC again whenever you recreate it.

SQL · steps 2, 3, 5
USE ROLE ACCOUNTADMIN;  -- or a role with CREATE INTEGRATION

CREATE STORAGE INTEGRATION S3_LANDING_INT
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::111122223333:role/snowflake-s3-access-role'
  STORAGE_ALLOWED_LOCATIONS = ('s3://shopstream-raw-landing/landing/');

DESC INTEGRATION S3_LANDING_INT;
-- copy STORAGE_AWS_IAM_USER_ARN and STORAGE_AWS_EXTERNAL_ID into the trust policy

GRANT USAGE ON INTEGRATION S3_LANDING_INT TO ROLE LAB_ENGINEER;

USE ROLE LAB_ENGINEER;
CREATE STAGE SHOPSTREAM_LAB.RAW.STG_S3_LANDING
  URL = 's3://shopstream-raw-landing/landing/'
  STORAGE_INTEGRATION = S3_LANDING_INT
  FILE_FORMAT = SHOPSTREAM_LAB.RAW.FF_JSON_NDJSON;

LIST @SHOPSTREAM_LAB.RAW.STG_S3_LANDING;   -- proves the handshake works

03

Building blocksEvery object, one card each

There are seven Snowflake objects, each with one job. If you can explain each one in a sentence, you’ve covered most of the interview.

Storage integration

S3_LANDING_INT

An account-level object that holds the IAM role ARN and the allowed S3 locations. It’s Snowflake’s half of the trust.

A building keycard registered with security. You get a badge, not a copy of the master key.

SQL
CREATE STORAGE INTEGRATION S3_LANDING_INT
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::111122223333:role/snowflake-s3-access-role'
  STORAGE_ALLOWED_LOCATIONS = ('s3://shopstream-raw-landing/landing/');

File format

RAW.FF_JSON_NDJSON · RAW.FF_JSON_ARRAY

A named set of parsing rules: type, compression, and whether to strip the outer [ ]. You can reuse it across stages, COPY, and pipes.

A reading-glasses prescription. The same file reads differently depending on the lens.

SQL
CREATE FILE FORMAT RAW.FF_JSON_NDJSON
  TYPE = JSON
  STRIP_OUTER_ARRAY = FALSE
  COMPRESSION = AUTO;

CREATE FILE FORMAT RAW.FF_JSON_ARRAY
  TYPE = JSON
  STRIP_OUTER_ARRAY = TRUE;

External stage

RAW.STG_S3_LANDING

A named pointer to an S3 URL that uses the integration and a default file format. COPY and Snowpipe read from @stage/prefix/.

A loading dock door that opens onto the S3 warehouse. You can browse it with LIST and query it before you load anything.

SQL
CREATE STAGE RAW.STG_S3_LANDING
  URL = 's3://shopstream-raw-landing/landing/'
  STORAGE_INTEGRATION = S3_LANDING_INT
  FILE_FORMAT = RAW.FF_JSON_NDJSON;

LIST @RAW.STG_S3_LANDING/orders/;

Raw table (VARIANT)

RAW.ORDERS_RAW

One VARIANT column holds each whole order, plus lineage columns for which file, which line, and when. It’s schema-on-read, so new fields never break the load.

An evidence locker. You store exactly what arrived, labeled, and interpret it later.

SQL
CREATE TABLE RAW.ORDERS_RAW (
  raw       VARIANT,
  src_file  STRING,
  src_row   NUMBER,
  loaded_at TIMESTAMP_LTZ DEFAULT CURRENT_TIMESTAMP()
);

COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
  FROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
        FROM @RAW.STG_S3_LANDING/orders/)
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
  ON_ERROR = 'ABORT_STATEMENT';

Pipe (Snowpipe)

RAW.PIPE_ORDERS_INCREMENTAL

A COPY statement wrapped in serverless auto-ingest. S3 ObjectCreated events go to the pipe’s SQS queue, and new files load within about a minute.

A doorbell on the loading dock. Each delivery rings it, and someone unloads right away.

SQL
CREATE PIPE RAW.PIPE_ORDERS_INCREMENTAL
  AUTO_INGEST = TRUE
AS
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
  FROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
        FROM @RAW.STG_S3_LANDING/orders_incremental/)
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON');

SHOW PIPES LIKE 'PIPE_ORDERS_INCREMENTAL' IN SCHEMA RAW;
-- notification_channel = SQS ARN for the S3 event

Stream

RAW.STRM_ORDERS_RAW

A change-tracking offset on ORDERS_RAW that returns only rows added since the last time it was consumed. APPEND_ONLY fits an insert-only raw table.

A bookmark in a log book. It shows only the new pages since you last read.

SQL
CREATE STREAM RAW.STRM_ORDERS_RAW
  ON TABLE RAW.ORDERS_RAW
  APPEND_ONLY = TRUE;

SELECT SYSTEM$STREAM_HAS_DATA('RAW.STRM_ORDERS_RAW');

Task

CURATED.TSK_MERGE_ORDERS

A scheduled SQL job. It runs every 5 minutes but skips the run (and uses no warehouse) unless the stream has data.

A cron job with a “nothing new? stay asleep” check built in.

SQL
CREATE TASK CURATED.TSK_MERGE_ORDERS
  WAREHOUSE = LAB_WH
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('RAW.STRM_ORDERS_RAW')
AS
MERGE INTO CURATED.ORDERS t
USING (SELECT raw:order_id::STRING AS order_id, raw:status::STRING AS status
       FROM RAW.STRM_ORDERS_RAW
       WHERE raw:order_id IS NOT NULL
       QUALIFY ROW_NUMBER() OVER (PARTITION BY raw:order_id::STRING
                                  ORDER BY loaded_at DESC) = 1) s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.status = s.status
WHEN NOT MATCHED THEN INSERT (order_id, status) VALUES (s.order_id, s.status);
-- minimal version; the full two-table task is in section 09

ALTER TASK CURATED.TSK_MERGE_ORDERS RESUME;  -- tasks start suspended

Schema-on-readJSON → VARIANT → relational

Here is a real record, ORD-100001, from the lab data. Each colored box in the JSON maps to one path expression in SQL. A path that doesn’t exist returns NULL instead of an error.

SQL · one row per order
SELECT
  raw:order_id::STRING                     AS order_id,
  raw:order_ts::TIMESTAMP_TZ               AS order_ts,
  raw:status::STRING                       AS status,
  raw:customer.customer_id::STRING         AS customer_id,
  raw:customer.address.city::STRING        AS city,
  TRY_TO_NUMBER(raw:payment.amount::STRING, 12, 2) AS amount,
  raw:shipping.carrier::STRING             AS carrier   -- NULL if absent
FROM RAW.ORDERS_RAW
WHERE raw:order_id IS NOT NULL;
SQL · one row per order line
SELECT
  r.raw:order_id::STRING          AS order_id,
  f.index + 1                     AS line_no,
  f.value:sku::STRING             AS sku,
  f.value:product_name::STRING    AS product_name,
  f.value:qty::NUMBER             AS qty,
  f.value:unit_price::NUMBER(10,2) AS unit_price,
  f.value:discount::NUMBER(4,2)   AS discount
FROM RAW.ORDERS_RAW r,
     LATERAL FLATTEN(input => r.raw:items) f
WHERE r.raw:order_id::STRING = 'ORD-100001';   -- returns 3 rows

Across the full lab: 50 orders in the two NDJSON files flatten to 91 item rows, and adding the array file gives 60 orders and 111 items.

06

Ingestion modesBatch vs. continuous

There are four ways to get S3 data into Snowflake, ordered here from slowest to freshest. Pick based on latency, file pattern, and who pays for compute.

OptionTriggerLatencyCompute / costPick it when…
COPY INTOYou (or a task / Airflow) run itMinutes to hoursYour virtual warehouse, billed per second while runningBackfills, daily batches, one-off loads, and cases where you want full control and simple ops.
Snowpipe (auto-ingest)S3 ObjectCreated → SQS → pipeAbout a minuteServerless, billed by Snowflake for what you ingest, with no warehouse to manageFiles arrive continuously or unpredictably and you want them loaded hands-off. This is the default for “keep it loading.”
Snowpipe StreamingClient SDK / Kafka connector pushes rowsSecondsServerless, and no files means no per-file overheadThe source is an event stream (Kafka, Kinesis via connector) and you need sub-minute freshness. Skip writing files to S3 at all.
External tables / IcebergQuery reads S3 directly (refresh metadata via events)Query-timeWarehouse at query time. Slower than native storage unless you use Iceberg with Snowflake-managed metadata.Data must stay in S3 (data lake, shared with Spark/Athena), you query it rarely, or it’s exploratory. Choose Iceberg for an open table format with good performance.
Interview line: “Use COPY for the backfill and Snowpipe for the steady state. If they need seconds-level latency from Kafka, use Snowpipe Streaming. If the data has to stay in the lake, use an Iceberg or external table.”
07

When files are dirtyError-handling decision tree

COPY only catches parse errors. Data-quality problems in valid JSON load fine and have to be caught later, in the curated layer.

The 4 kinds of bad record in orders_2026-11-19_corrupt.json

parse error

Truncated JSON

{"order_id": "ORD-BROKEN-1", "order_ts": "2026-11-19T10:00:00Z", "status": "PLACED",
✗ rejected by COPY
The writer crashed mid-line. VALIDATION_MODE catches this one.
parse error

Unquoted keys

{order_id: ORD-BROKEN-2, status: PLACED}
✗ rejected by COPY
JavaScript-style, not JSON. A strict parser refuses it.
valid JSON · bad data

Missing order_id

{"order_ts": "2026-11-19T19:16:13Z", "status": "SHIPPED", "channel": "marketplace", "customer": {"customer_id": "C-5003", …}
✓ loads into RAW
It’s filtered at the curated layer with WHERE raw:order_id IS NOT NULL, and you should count and alert on it.
valid JSON · bad data

Wrong type

"order_id": "ORD-100069", … "payment": {"method": "bank_transfer", "amount": "forty-two", …}
✓ loads into RAW
TRY_TO_NUMBER turns it into NULL, where ::NUMBER would fail the whole query. Flag it with a DQ check.
SQL · ① dry run + ② real load
-- VALIDATION_MODE and VALIDATE() don't support COPY with a SELECT
-- transform, so run the dry run against a 1-column probe table.
CREATE TEMPORARY TABLE RAW.ORDERS_PROBE (raw VARIANT);

COPY INTO RAW.ORDERS_PROBE
  FROM @RAW.STG_S3_LANDING/orders_bad/
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
  VALIDATION_MODE = RETURN_ERRORS;        -- shows the 2 parse errors, loads 0

-- Real load: keep the good 9, reject the bad 2
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
  FROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
        FROM @RAW.STG_S3_LANDING/orders_bad/)
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
  ON_ERROR = 'CONTINUE';
SQL · ③ inspect + ④ quarantine
CREATE TABLE IF NOT EXISTS RAW.ORDERS_LOAD_ERRORS (
  error STRING, file STRING, line NUMBER,
  rejected_record STRING,
  captured_at TIMESTAMP_LTZ DEFAULT CURRENT_TIMESTAMP()
);

-- Plain (non-transform) COPY into the probe, then VALIDATE that job
COPY INTO RAW.ORDERS_PROBE
  FROM @RAW.STG_S3_LANDING/orders_bad/
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
  ON_ERROR = 'CONTINUE';

INSERT INTO RAW.ORDERS_LOAD_ERRORS (error, file, line, rejected_record)
  SELECT error, file, line, rejected_record
  FROM TABLE(VALIDATE(RAW.ORDERS_PROBE, JOB_ID => '_last'));

-- Data-quality checks for the valid-but-wrong rows
SELECT COUNT_IF(raw:order_id IS NULL)                          AS missing_id,
       COUNT_IF(raw:payment.amount IS NOT NULL
                AND TRY_TO_NUMBER(raw:payment.amount::STRING) IS NULL) AS bad_amount
FROM RAW.ORDERS_RAW;
08

Run it twice, safelyLoad metadata and idempotency

Every table keeps a ledger of which files it has already loaded. That’s why re-running the same COPY is safe and boring.

The table’s load ledger (kept 64 days)

file (stage-relative)ETag / checksumstatus
orders/orders_2026-11-18_part1.json9f3c…a1LOADED · 25 rows
orders/orders_2026-11-18_part2.json41be…7dLOADED · 25 rows

The key is the file path plus content checksum. Snowpipe keeps its own ledger on the pipe for 14 days.

Why a re-run loads 0 files

safe
0 files on re-run

Run the same COPY again (or a retry after a timeout) and nothing gets duplicated. The table stays at 50 rows.

duplicates
100 rows with FORCE

FORCE = TRUE ignores the ledger and reloads everything, so you end up with every order twice. Only use it after TRUNCATE or for deliberate reprocessing.

sneaky
+25 after a rename

Renaming or re-uploading a file gives it a new path or new ETag, so it counts as a new file and loads again. The same happens when a producer rewrites a file in place.

After 64 days the ledger forgets. If a file’s LAST_MODIFIED is older than 64 days and its status is unknown, COPY skips it by default. Set LOAD_UNCERTAIN_FILES = TRUE to include it, and then you own deduplication.
Belt and braces: the downstream MERGE … ON order_id deduplicates anyway, so even a FORCE accident doesn’t double-count curated orders.
SQL · see the ledger
SELECT file_name, status, row_count, row_parsed, first_error_message, last_load_time
FROM TABLE(SHOPSTREAM_LAB.INFORMATION_SCHEMA.COPY_HISTORY(
       TABLE_NAME => 'RAW.ORDERS_RAW',
       START_TIME => DATEADD(DAY, -7, CURRENT_TIMESTAMP())))
ORDER BY last_load_time DESC;

Schema drift, visualized

Two gotchas that catch everyone

  • Two MERGEs, one stream: the first committed DML consumes the stream, so the second MERGE sees nothing. Wrap both in BEGIN TRANSACTION … COMMIT.
  • Duplicate keys in one batch: if the old and new versions of ORD-100003 land in the same stream batch, MERGE fails as nondeterministic. Deduplicate with QUALIFY ROW_NUMBER() … = 1.
  • Tasks start suspended. Run ALTER TASK … RESUME, and check TASK_HISTORY().
SQL · CURATED.TSK_MERGE_ORDERS (full)
CREATE TABLE IF NOT EXISTS CURATED.ORDERS (
  order_id STRING PRIMARY KEY, order_ts TIMESTAMP_TZ, status STRING, channel STRING,
  customer_id STRING, city STRING, loyalty_tier STRING, amount NUMBER(12,2),
  carrier STRING, delivered_ts TIMESTAMP_TZ
);
CREATE TABLE IF NOT EXISTS CURATED.ORDER_ITEMS (
  order_id STRING, line_no NUMBER, sku STRING, qty NUMBER,
  unit_price NUMBER(10,2), discount NUMBER(4,2),
  PRIMARY KEY (order_id, line_no)
);

CREATE OR REPLACE TASK CURATED.TSK_MERGE_ORDERS
  WAREHOUSE = LAB_WH
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('RAW.STRM_ORDERS_RAW')
AS
EXECUTE IMMEDIATE
$$
BEGIN
  BEGIN TRANSACTION;   -- both MERGEs read the same stream snapshot

  MERGE INTO CURATED.ORDERS t
  USING (
    SELECT raw:order_id::STRING                      AS order_id,
           raw:order_ts::TIMESTAMP_TZ                AS order_ts,
           raw:status::STRING                        AS status,
           raw:channel::STRING                       AS channel,
           raw:customer.customer_id::STRING          AS customer_id,
           raw:customer.address.city::STRING         AS city,
           raw:customer.loyalty_tier::STRING         AS loyalty_tier,
           TRY_TO_NUMBER(raw:payment.amount::STRING, 12, 2) AS amount,
           raw:shipping.carrier::STRING              AS carrier,
           raw:delivered_ts::TIMESTAMP_TZ            AS delivered_ts
    FROM RAW.STRM_ORDERS_RAW
    WHERE raw:order_id IS NOT NULL
    QUALIFY ROW_NUMBER() OVER (PARTITION BY raw:order_id::STRING
                               ORDER BY loaded_at DESC, src_row DESC) = 1
  ) s
  ON t.order_id = s.order_id
  WHEN MATCHED THEN UPDATE SET
    t.status = s.status, t.carrier = s.carrier, t.delivered_ts = s.delivered_ts,
    t.loyalty_tier = s.loyalty_tier, t.amount = s.amount
  WHEN NOT MATCHED THEN INSERT
    (order_id, order_ts, status, channel, customer_id, city, loyalty_tier, amount, carrier, delivered_ts)
    VALUES (s.order_id, s.order_ts, s.status, s.channel, s.customer_id, s.city,
            s.loyalty_tier, s.amount, s.carrier, s.delivered_ts);

  MERGE INTO CURATED.ORDER_ITEMS t
  USING (
    SELECT r.raw:order_id::STRING           AS order_id,
           f.index + 1                      AS line_no,
           f.value:sku::STRING              AS sku,
           f.value:qty::NUMBER              AS qty,
           f.value:unit_price::NUMBER(10,2) AS unit_price,
           f.value:discount::NUMBER(4,2)    AS discount
    FROM RAW.STRM_ORDERS_RAW r,
         LATERAL FLATTEN(input => r.raw:items) f
    WHERE r.raw:order_id IS NOT NULL
    QUALIFY ROW_NUMBER() OVER (PARTITION BY r.raw:order_id::STRING, f.index
                               ORDER BY r.loaded_at DESC, r.src_row DESC) = 1
  ) s
  ON t.order_id = s.order_id AND t.line_no = s.line_no
  WHEN MATCHED THEN UPDATE SET
    t.sku = s.sku, t.qty = s.qty, t.unit_price = s.unit_price, t.discount = s.discount
  WHEN NOT MATCHED THEN INSERT (order_id, line_no, sku, qty, unit_price, discount)
    VALUES (s.order_id, s.line_no, s.sku, s.qty, s.unit_price, s.discount);

  COMMIT;
END;
$$;

ALTER TASK CURATED.TSK_MERGE_ORDERS RESUME;

Make it fast & cheapPerformance and cost cheat-sheet

Five levers. Most real-world cost problems come down to file size and leaving warehouses running.

1 · File sizing

< 10 MB
overhead
10–100
100–250 MB gz ✓
≤ 5 GB
huge
single
  • Aim for 100–250 MB compressed per file. Thousands of tiny files mean per-file overhead, and one giant file can’t be loaded in parallel.
  • Batch small events upstream (Firehose buffering, or a compaction job).
  • Use date-partitioned prefixes (orders/2026/11/18/) so you can scope COPY with PATTERN and avoid long LISTs.

2 · Warehouse sizing

XS
S
M
L
XL
each size up = 2× credits/hour = ~2× files loaded in parallel
  • Load throughput scales with file count, not with the size of one file. Upsizing doesn’t help a load of 3 files.
  • LAB_WH is XSMALL with AUTO_SUSPEND = 60, so it sleeps a minute after the load.
  • Use a dedicated loading warehouse so loads don’t compete with BI queries.

3 · Snowpipe cost model

  • Snowpipe uses serverless compute, so no warehouse sits idle. Billing has historically been compute-seconds plus a per-file overhead, and newer pricing moves toward a flat per-GB rate. Check the current price list.
  • Either way, fewer, well-sized files are cheaper. Watch spend with PIPE_USAGE_HISTORY.
  • If files only arrive once a day, a scheduled COPY is usually cheaper and simpler.

4 · Materialize hot JSON paths

  • Snowflake already columnarizes many VARIANT sub-paths, but mixed types and very sparse keys defeat that.
  • Promote fields you filter or join on (order_ts, status, customer_id) to typed columns, and consider clustering by order date on very large tables.
  • Keep RAW for replay and audit, and point BI at CURATED.

5 · Compression

NDJSON raw · 100%
gzip
JSON is very repetitive (the same keys on every line), so gzip often shrinks it 5–10×.
  • COMPRESSION = AUTO detects gzip/bz2/zstd/brotli. Snowflake also supports zstd, and gzip is the safe default.
  • Smaller files mean less S3 GET traffic and faster transfer. Inside Snowflake, the data is recompressed into its own columnar format anyway.

How to talk through it

  1. Clarify first: volume, latency SLA, NDJSON or array, does the schema change, are there updates (upserts)?
  2. Landing: S3 bucket with dated prefixes, NDJSON gzip, 100–250 MB files.
  3. Access: IAM role + storage integration, trust tied to the external ID, no keys.
  4. Plumbing: JSON file format + external stage, then LIST to test it.
  5. Raw load: COPY into VARIANT with file name and row lineage, then Snowpipe for new files.
  6. Model: paths, casts, and FLATTEN into CURATED, kept incremental with a stream + task MERGE.
  7. Quality: VALIDATION_MODE, ON_ERROR, VALIDATE() into a quarantine table, and DQ checks.
  8. Operate: idempotent load metadata, COPY_HISTORY / PIPE_STATUS monitoring, alerts, and cost controls.

Common mistakes

  • Putting AWS access keys in the stage definition instead of using a storage integration.
  • Recreating the integration and forgetting the external ID changed (access denied).
  • Loading a JSON array without STRIP_OUTER_ARRAY = TRUE, which gives one giant row or a size error.
  • Casting with ::NUMBER on dirty data, so one bad value fails the query. Use TRY_TO_NUMBER.
  • Forgetting ::STRING, so values keep their JSON quotes and joins silently miss.
  • Using FORCE = TRUE “to make it work”, which duplicates rows.
  • Two MERGEs on one stream without an explicit transaction.
  • Creating the pipe but never adding the S3 event notification to the SQS ARN.
  • Thousands of KB-sized files feeding Snowpipe, which means overhead-dominated cost.
  • Skipping the clarifying questions and going straight to SQL.
