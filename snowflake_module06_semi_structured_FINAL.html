MODULE 06 · SEMI-STRUCTURED DATA

Messy JSON in.
Clean SQL out.

APIs, event streams, mobile apps and SaaS exports rarely hand you neat CSV rows. They send JSON, Avro, Parquet or XML: nested, optional, and changing shape every few weeks. Snowflake lets you load that data as-is into a single VARIANT column and query it with SQL straight away. This module goes from "what is JSON" to how Snowflake stores VARIANT inside micro-partitions, why some JSON queries prune beautifully and others scan everything, and when a senior engineer "promotes" fields into real columns.

Four everyday pictures to keep in your head:

VARIANT
A school backpack

One bag that can hold anything: a book (string), a calculator (number), a pencil case full of smaller things (object), a stack of notebooks (array). The table only sees "one backpack per row".

PATH NOTATION
A postal address

v:customer.address.city is like "House → Floor 2 → Room 5". You follow the labels from the outside in. Spell a label wrong (or in the wrong case) and the letter never arrives: you get NULL.

FLATTEN
Unpacking a tiffin box

One tiffin (one row) holds three containers (an array of three items). FLATTEN lays each container on the table as its own row, still labelled with whose tiffin it came from.

COLUMNARIZATION
Sorting a junk drawer

Snowflake notices that almost every backpack has a "lunchbox" and a "water bottle", so it stores those in labelled trays (sub-columns). Rare or odd items stay loose in the drawer (the blob).

CHAPTER 01

Data shapes & formats · structured, semi-structured, unstructured

01 · WHAT IS IT

Structured data fits a fixed table: every row has the same columns with the same types (a CSV of orders). Semi-structured data carries its own labels inside each record: keys and values, nesting, lists, and fields that may or may not be there (JSON, Avro, Parquet, ORC, XML). Unstructured data has no fields at all: PDFs, images, audio (covered in Module 02).

The key word for semi-structured is self-describing: each record tells you its own shape, so two records in the same file can look different.

02 · WHY WE USE IT
  • Sources produce it: REST APIs, Kafka events, clickstreams, IoT devices and app logs speak JSON or Avro.
  • Schema changes are constant: a developer adds "promo_code" to an event on Tuesday. With a fixed table, the load breaks. With VARIANT, the new key simply appears.
  • Nesting is natural: an order has a list of items. JSON keeps that together; a flat table needs two tables and a join.
  • Land first, model later: load raw data now (ELT), decide the typed model once you understand it.
03 · HOW IT WORKS · SCHEMA-ON-WRITE VS SCHEMA-ON-READ
Schema-on-write (classic warehouse)

You define CREATE TABLE orders (id INT, amount NUMBER(10,2), ...) before loading. Every row is checked against it at load time. Bad or unexpected fields fail the load or are dropped. Fast, predictable queries, but rigid.

Schema-on-read (VARIANT)

You load the whole record into one VARIANT column. The "schema" is applied when you query: v:amount::NUMBER(10,2). Nothing breaks when fields are added. The cost: types and structure are checked every time you read, and mistakes show up as NULLs instead of load errors.

Snowflake supports both in one table: a common pattern is raw_events (event_id STRING, load_ts TIMESTAMP_NTZ, payload VARIANT), so a few key fields are typed columns and everything else stays flexible.

CHAPTER 02

VARIANT, OBJECT, ARRAY · and what happens inside storage

01 · WHAT IS IT

Snowflake has three semi-structured data types:

  • VARIANT: a universal container. One VARIANT value can hold a string, number, boolean, null, an OBJECT or an ARRAY. It remembers the type of what is inside (check it with TYPEOF()).
  • OBJECT: a set of key-value pairs, like a JSON { }. Keys are strings; values are VARIANT.
  • ARRAY: an ordered list, like a JSON [ ]. Elements are VARIANT (so one array may mix types). Indexes start at 0.

Size limit: a single VARIANT value has a maximum size. For years it was 16 MB; newer Snowflake releases have raised it. Check the current documentation for the exact limit and any conditions, rather than quoting a number in an interview with certainty.

02 · WHY WE USE IT

VARIANT lets you load a JSON document without declaring its shape, keep every field (even ones you don't use yet), and still query any part with SQL. OBJECT and ARRAY are useful when you build JSON (for APIs, exports or compact storage) and when you want to say "this column is always an object" for clarity.

Most raw landing tables use just one column: v VARIANT.

03 · HOW IT WORKS · TWO KINDS OF NULL
SQL NULL

"There is no value here." You get it when a path doesn't exist: v:missing_key returns SQL NULL. IS NULL is TRUE.

JSON null (VARIANT null)

"The value exists and it is the JSON literal null." v:coupon on {"coupon": null} returns a VARIANT null, shown as null. IS NULL is FALSE! Test it with IS_NULL_VALUE(v:coupon), and convert it to SQL NULL with STRIP_NULL_VALUE() or by casting (v:coupon::STRING returns SQL NULL).

Storage, in the backend. A table with a VARIANT column is still stored in normal columnar micro-partitions. When data is written, Snowflake looks at the documents in each micro-partition and tries to extract common paths into their own hidden sub-columns, each stored in a typed, columnar way with its own metadata (such as min/max values). That means WHERE v:country = 'IN' can read only the country sub-column and can prune micro-partitions using its min/max, just like a normal column.

Paths that can't be extracted cleanly stay in the remaining binary blob for that row. According to Snowflake's documentation, things that typically stop extraction include: values with inconsistent types across rows (a number here, a string there), elements that contain a JSON null in some rows, and data inside arrays. Values such as dates in JSON are stored as strings, so filters on them are less efficient than on a real DATE column. The exact heuristics (how many paths, what share of rows) are internal and not fully documented, so describe it as "Snowflake tries to columnarize consistent paths" rather than as a fixed rule.

INTERVIEW TRAP
"I filtered WHERE v:discount IS NULL and got fewer rows than expected." Rows with "discount": null hold a JSON null, which is a real value, so IS NULL is FALSE for them. Write WHERE v:discount IS NULL OR IS_NULL_VALUE(v:discount), or simply WHERE v:discount::NUMBER IS NULL (casting turns JSON null into SQL NULL).
SENIOR ANGLE
If your source sends null for "not set", loading with STRIP_NULL_VALUES = TRUE removes those keys. Besides saving space, Snowflake's docs note that elements containing JSON nulls are not extracted into sub-columns, so stripping them can improve columnarization and pruning. Only do it if "key present with null" and "key absent" really mean the same thing for your business.
CHAPTER 03

Querying paths · colon, dot, brackets, casting

01 · WHAT IS IT

To reach inside a VARIANT you write a path:

  • v:customer: the colon goes from the column to the first-level key.
  • v:customer.name: dots go deeper into nested objects.
  • v:items[0]: square brackets with a number pick an array element (0-based).
  • v['ship-to'] or v:"ship-to": bracket notation or double quotes for keys with spaces, hyphens or other special characters.
  • GET(v, 'customer'), GET_PATH(v, 'customer.name'): the function forms (the colon is shorthand for GET_PATH).
02 · WHY IT MATTERS

Paths are how every JSON query starts, and they are where most silent bugs live. A wrong path doesn't raise an error; it returns NULL. Interviewers love asking why v:Name returned nothing, or why the output shows "Asha" with quotes.

Casting (::STRING, ::NUMBER, ::DATE) turns a VARIANT into a normal SQL type so you can compare, join, sort and aggregate correctly.

03 · HOW IT WORKS · FOUR RULES TO REMEMBER
1 · Keys are case-sensitive

The column name is not case-sensitive (V: = v:), but element names are: v:Status and v:status are different keys. Unknown key → SQL NULL, no error. GET_IGNORE_CASE() exists when you can't control the casing.

2 · A path returns VARIANT

v:customer.name is still a VARIANT holding a JSON string, so Snowsight shows it JSON-encoded: "Asha" with quotes. v:customer.name::STRING converts it to a real VARCHAR: Asha. Comparisons and joins should use the cast value.

3 · Cast safely

v:qty::NUMBER fails the whole query if one row has "qty": "two". Use the TRY family on the string form: TRY_TO_NUMBER(v:qty::STRING), TRY_TO_DATE(v:dt::STRING), or TRY_CAST(v:qty::STRING AS NUMBER). They return NULL instead of failing.

4 · Know the inner type

TYPEOF(v:price) returns names like INTEGER, DECIMAL, DOUBLE, VARCHAR, BOOLEAN, OBJECT, ARRAY, or NULL_VALUE for JSON null. Helpers: IS_OBJECT, IS_ARRAY, IS_INTEGER, AS_VARCHAR, AS_NUMBER…

"My join on a JSON field returns no matches, but the values look identical." One side's JSON may hold "10" (a string) and the other 10 (a number). Rule of thumb: cast before you join, group, sort or compare (v:customer_id::NUMBER = c.id), so both sides are the same SQL type and the result is predictable.
CHAPTER 04

FLATTEN & LATERAL · one row with a list → many rows

01 · WHAT IS IT

FLATTEN is a table function: give it an ARRAY or OBJECT and it returns one row per element. LATERAL lets that function see the columns of the row to its left, so each order's own items array is flattened and joined back to that order.

Output columns:

COLUMNMEANING
SEQA number identifying the input record (all rows exploded from the same input share it). Not guaranteed to be gap-free or ordered.
KEYThe key name when flattening an OBJECT (NULL for array elements).
PATHPath to the element relative to the input, e.g. [0] or [0].sku.
INDEXThe position when flattening an ARRAY (NULL for object fields).
VALUEThe element itself, as VARIANT. This is the one you use most: f.value:sku::STRING.
THISThe element (array or object) being flattened at this level.
02 · WHY WE USE IT

Reports and joins need rows: "revenue per SKU", "count of tags per event". Arrays hide those rows inside a single cell. FLATTEN is how you turn one order with 3 items into 3 order-item rows that you can GROUP BY, join to a product table, or load into a typed fact table.

The full signature: FLATTEN(INPUT => expr, PATH => 'path', OUTER => FALSE, RECURSIVE => FALSE, MODE => 'BOTH'). MODE can be 'OBJECT', 'ARRAY' or 'BOTH'.

03 · HOW IT WORKS · THE TWO SWITCHES THAT CHANGE ROW COUNTS
OUTER => TRUE

By default, a row whose array is empty, missing or NULL produces zero rows, so the lateral join silently drops that order. With OUTER => TRUE, FLATTEN emits exactly one row for it, with NULL in KEY, INDEX and VALUE. It's the LEFT JOIN of the JSON world.

RECURSIVE => TRUE

Normally FLATTEN expands only one level. Recursive expands every nested level: objects inside arrays inside objects. Great for discovering all paths in unknown JSON (SELECT DISTINCT f.path), but too noisy for normal reporting.

Backend: FLATTEN runs on the warehouse as a table-function operator in the query plan (you'll see it as Flatten in the Query Profile, feeding a lateral join). Each input row is expanded in memory and the output can be many times larger than the input, so filter before flattening where you can, and select only the fields you need from value.

INTERVIEW TRAP
"Our order count dropped after we added item-level reporting." Classic cause: LATERAL FLATTEN(input => v:items) without OUTER => TRUE drops every order whose items array is empty or missing. Second classic: counting COUNT(*) after flattening counts items, not orders; use COUNT(DISTINCT order_id).
SENIOR ANGLE
Nested arrays need a double flatten: FROM raw_orders o, LATERAL FLATTEN(input => o.v:items) i, LATERAL FLATTEN(input => i.value:tags) t. Each level multiplies rows, so 1M orders × 5 items × 4 tags = 20M rows. Push filters as early as possible, and in a pipeline, materialize the flattened grain once (a typed order_items table or dynamic table) instead of re-flattening in every dashboard query.
CHAPTER 05

Building semi-structured data · from rows back to JSON

01 · WHAT IS IT

The reverse of flattening: functions that create VARIANT, OBJECT and ARRAY values.

  • PARSE_JSON(str) turns JSON text into VARIANT (errors on invalid JSON). TRY_PARSE_JSON(str) returns NULL instead.
  • OBJECT_CONSTRUCT('k1', v1, 'k2', v2) builds an object; pairs whose value is SQL NULL are left out. OBJECT_CONSTRUCT_KEEP_NULL keeps them as JSON null. OBJECT_CONSTRUCT(*) turns a whole row into an object.
  • ARRAY_CONSTRUCT(a, b, c) builds an array from values; ARRAY_CONSTRUCT_COMPACT drops NULLs.
  • ARRAY_AGG(x) aggregates many rows into one array (NULLs skipped; add WITHIN GROUP (ORDER BY …) for order). OBJECT_AGG(key, value) aggregates rows into one object.
  • TO_JSON(variant) serializes a VARIANT to a JSON string; STRIP_NULL_VALUE(v) turns a JSON null into SQL NULL.
02 · WHY WE USE IT
  • API payloads and exports: build one JSON document per customer to unload or send to a service.
  • Nesting for consumers: "one row per order with its items as an array" is easier for apps than a join.
  • Auditing and logging: store "before/after" snapshots of a row as an object.
  • Metadata tricks: ARRAY_AGG(OBJECT_CONSTRUCT(*)) is exactly what CREATE TABLE … USING TEMPLATE needs with INFER_SCHEMA (chapter 06).

"Our API export is missing the coupon field for some customers and the frontend crashes." OBJECT_CONSTRUCT silently omits keys whose value is SQL NULL. If consumers expect every key to exist, use OBJECT_CONSTRUCT_KEEP_NULL (or COALESCE the value). Also: OBJECT_AGG fails if the same key appears twice in a group, so deduplicate first.
CHAPTER 06

Loading semi-structured files · JSON, Parquet, Avro, ORC, XML

01 · WHAT IS IT

The same COPY INTO (and Snowpipe) you know from earlier modules, with a file format of TYPE = JSON | AVRO | PARQUET | ORC | XML. Two landing styles:

  • Raw landing: each record goes into one VARIANT column (COPY INTO raw_events FROM @stage, read as $1).
  • Typed landing: fields go straight into real columns, using MATCH_BY_COLUMN_NAME (Parquet/Avro/ORC, and JSON) or a transformation COPY INTO t FROM (SELECT $1:id::NUMBER, $1:name::STRING FROM @stage).
02 · WHY THE OPTIONS MATTER
  • STRIP_OUTER_ARRAY = TRUE: a file shaped [ {...}, {...} ] is otherwise one giant record (one row), which can hit the VARIANT size limit and makes FLATTEN mandatory.
  • STRIP_NULL_VALUES = TRUE: drops keys whose value is JSON null.
  • INFER_SCHEMA: reads file metadata (Parquet/Avro/ORC, and in current releases JSON and CSV too) and proposes column names and types, so you don't hand-write 80 columns.
  • XML: Snowflake parses XML into VARIANT and you navigate it with $, @ and XMLGET.
03 · HOW IT WORKS · BACKEND

The warehouse reads each staged file and its parser turns records into VARIANT values. For JSON, Snowflake accepts newline-delimited records (one document per line) or documents simply concatenated, and a single outer array (which STRIP_OUTER_ARRAY unwraps). For Parquet, the reader uses the file's own schema and column chunks; with MATCH_BY_COLUMN_NAME it maps file columns to table columns by name (CASE_SENSITIVE or CASE_INSENSITIVE), and table columns with no match are loaded as NULL. Once loaded, the data becomes micro-partitions like any other table, and the columnarization from chapter 02 happens at write time. Load metadata (the 64-day "already loaded" memory) works the same as for CSV.

With ENABLE_SCHEMA_EVOLUTION = TRUE on the table plus MATCH_BY_COLUMN_NAME, Snowflake can automatically add new columns it finds in incoming files (the loading role needs the right privileges). Check the docs for the exact conditions before relying on it.

INFER_SCHEMA in three steps

1 · Look

SELECT * FROM TABLE(INFER_SCHEMA(LOCATION => '@pq_stage/orders/', FILE_FORMAT => 'pq_fmt')) returns one row per detected column: COLUMN_NAME, TYPE, NULLABLE, EXPRESSION, FILENAMES, ORDER_ID. The file format must be a named file format object.

2 · Create

CREATE TABLE orders USING TEMPLATE (SELECT ARRAY_AGG(OBJECT_CONSTRUCT(*)) FROM TABLE(INFER_SCHEMA(...))) builds the table from those rows. Column names keep the file's case, so you may need to quote them later.

3 · Load

COPY INTO orders FROM @pq_stage/orders/ FILE_FORMAT = (FORMAT_NAME = 'pq_fmt') MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE. Review the inferred types first: inference samples files, so wide or rare values may need manual adjustments.

INTERVIEW TRAP
"COPY of a Parquet file into my 10-column table fails with '… file format can produce one and only one column of type variant, object, or array'." Without MATCH_BY_COLUMN_NAME or a SELECT $1:… transformation, semi-structured formats produce one VARIANT column, which only fits a single-column target. Add one of the two.
CHAPTER 07

Performance & modeling · query in place or promote?

01 · WHAT IS IT

Two ways to serve JSON to analysts:

  • Query in place: keep only the raw VARIANT and write paths in every query (often hidden behind a view that casts and renames: v:customer.id::NUMBER AS customer_id).
  • Promote: extract hot fields into real typed columns (in the landing table, or in a downstream table / dynamic table), and keep the VARIANT for everything else.
02 · WHY IT MATTERS

When paths are consistent, Snowflake's sub-column extraction makes VARIANT queries surprisingly fast. But when data drifts (types change, keys come and go, nulls appear, values live inside arrays, dates are strings), more data stays in the blob, pruning gets worse, and every query parses more. Promoted typed columns give stable pruning, correct types, clustering options, and simpler SQL for BI tools.

03 · HOW TO DECIDE · A SENIOR CHECKLIST
Promote a field when…

It's used in filters, joins or clustering; it's a date/timestamp or a number stored as a string; it lives inside an array you flatten constantly; its type is inconsistent and needs cleaning once; or BI users need a simple column.

Keep it in VARIANT when…

It's rarely queried; the schema changes often; you need to keep the full original payload for replay/audit; or it's exploratory data where the model isn't decided yet.

Handling schema drift

Land raw VARIANT (never breaks) → typed view or dynamic table on top (casts with TRY_ functions) → monitor new paths with FLATTEN(…, RECURSIVE => TRUE) + SELECT DISTINCT path, and alert on TYPEOF changes. Add new columns deliberately.

Search optimization on VARIANT

For selective point lookups (WHERE v:device_id::STRING = 'abc'), ALTER TABLE t ADD SEARCH OPTIMIZATION ON EQUALITY(v:device_id) (Enterprise Edition or higher) builds a search access path that can skip micro-partitions. It has storage and maintenance costs; check the docs for supported predicates and casts.
