MODULE 08 · SECURITY & GOVERNANCE

Who are you?
What may you see?

Every query in Snowflake passes through a series of checks before a single row comes back: where is it coming from, who is sending it, which role is active, which rows and columns that role may see, and who wrote it all down. This module walks through each check, from network policies and key-pair logins to role hierarchies, masking and row access policies, tags, audit views and the encryption keys underneath.

Think of Snowflake as a big office building that stores everyone's files:

NETWORK POLICY
The gate guard

Checks which street you came from before you even reach the door. Unknown address? You never get inside, no matter who you are.

AUTHENTICATION
The ID check at reception

Proves you are really Priya: badge plus a code on your phone (MFA), or a signed letter only you could write (key-pair).

AUTHORIZATION (RBAC)
The keycard

Your card is programmed for a job, not a person: the "Analyst" card opens floors 3 and 4. Change jobs, swap the card.

MASKING + ROW ACCESS
Black marker & folder filter

Inside the room, salary lines are blacked out for you, and the cabinet only shows your region's folders. Same cabinet, different view per person.

AND THE CCTV
Every door swipe and every file opened is recorded: LOGIN_HISTORY is the visitor logbook and ACCESS_HISTORY is the camera on the filing cabinets. Security you can't audit is security you can't prove, which is exactly what auditors ask about.
CHAPTER 01

Defence in depth · five layers, one query

01 · WHAT IS IT

Defence in depth means stacking several independent security controls so that if one fails or is misconfigured, the next one still protects the data. In Snowflake the layers are:

  • Network: network policies and rules (allowed / blocked IPs), private connectivity (PrivateLink and similar).
  • Authentication: proving identity: password + MFA, key-pair, SSO (SAML), OAuth.
  • Authorization: what the active role may do: RBAC + DAC, privileges on objects.
  • Data-level controls: row access policies, masking policies, secure views.
  • Monitoring: LOGIN_HISTORY, ACCESS_HISTORY, QUERY_HISTORY, Trust Center.

Underneath all of them: encryption of every byte at rest and in transit.

02 · WHY WE USE IT

No single control is perfect. A password leaks, a role gets granted too widely, a contractor's laptop is stolen. With layers:

  • A leaked password is useless from outside the allowed network, or without the MFA device.
  • A wrongly granted SELECT still shows masked PII if the masking policy doesn't list that role.
  • Even a fully authorised user only sees their region's rows.
  • And whatever happens, the audit trail tells you who saw what, when.

Regulations (GDPR, HIPAA, PCI DSS, SOX) expect exactly this: least privilege, need-to-know, and proof.

03 · HOW IT WORKS · FOLLOW ONE QUERY THROUGH THE LAYERS

Pick a scenario and press Next. Each layer lights up with what the user experiences and what Snowflake does in the backend. Almost all of these checks run in the cloud services layer (Module 1), before or while the query is compiled, so a denied query usually never starts a warehouse.

INTERVIEW TRAP
"In which order are row access and masking policies applied?" Row access first, then masking. Snowflake first decides which rows survive, then decides how each column value is displayed. That also means the row access policy is evaluated on the original, unmasked values.
SENIOR ANGLE
Most of these features (masking, row access policies, tag-based masking, classification, ACCESS_HISTORY) need Enterprise Edition or higher. Private connectivity and Tri-Secret Secure need Business Critical. Mentioning the edition when you propose a design shows you've done this for real.
CHAPTER 02

Access control model · roles, privileges, owners

01 · WHAT IS IT

Snowflake combines two models:

  • RBAC (role-based access control): privileges are granted to roles, and roles are granted to users (or to other roles). A user never holds a privilege directly.
  • DAC (discretionary access control): every object has an owner, the role that holds its OWNERSHIP privilege (usually the role that created it). The owner decides who else gets access.

Four words to remember: securable object (what you protect), privilege (what you may do to it: SELECT, USAGE, INSERT…), role (the container of privileges), user (the person or program who activates a role).

02 · WHY WE USE IT

Granting privileges to 400 individual people is unmanageable: when someone changes team you'd hunt for dozens of grants. With roles you grant once to ANALYST, and moving a person is a single GRANT ROLE / REVOKE ROLE.

Role inheritance lets you build small reusable blocks ("read sales", "write sales") and compose them into job roles. Ownership (DAC) lets teams manage their own objects without a central admin approving every grant, and managed access schemas (chapter 03) let you switch that freedom off where needed.

03 · HOW IT WORKS · THE SECURABLE OBJECT HIERARCHY

Objects live inside containers, and access is checked at every level. To touch a table you need a path of privileges all the way down: USAGE on the database, USAGE on the schema, then the object privilege (SELECT).

Access roles vs functional roles

Access roles hold object privileges and describe data: SALES_RO, SALES_RW. Functional roles describe a job: ANALYST, DATA_ENGINEER. Access roles are granted to functional roles, functional roles to users, and functional roles roll up to SYSADMIN. A new analyst gets one grant. A new table means changing one access role, not twenty job roles.

Ownership

The role that creates an object owns it (OWNERSHIP), and can grant privileges on it to others (in a normal schema). Ownership belongs to a role, not a person, so objects survive when people leave. Ownership can be transferred with GRANT OWNERSHIP … COPY CURRENT GRANTS (chapter 03).

Secondary roles and database roles

Secondary roles

A session has exactly one primary role (USE ROLE ANALYST). USE SECONDARY ROLES ALL (or a list of roles) adds the privileges of the user's other granted roles to the session, so a query can join data visible to different roles. Important rule: creating objects and ownership use the primary role only, while privileges for other SQL actions come from the primary plus secondary roles. Newer accounts may set users to DEFAULT_SECONDARY_ROLES = ('ALL') by default; check your account's behaviour.

Database roles

A role that lives inside a database (CREATE DATABASE ROLE sales_db.reader). Its privileges can only cover objects in that database. You can't USE ROLE a database role directly: you grant it to an account role (or another database role in the same database). They are perfect for data sharing (grant different database roles to a share so consumers see different subsets) and for packaging a database's access model with the database itself.

INTERVIEW TRAP
"ACCOUNTADMIN can see everything, right?" Not automatically. ACCOUNTADMIN inherits SYSADMIN and SECURITYADMIN. If a custom role that owns a database is not granted up to SYSADMIN, then neither SYSADMIN nor ACCOUNTADMIN inherit its privileges (an "orphan" role). SECURITYADMIN could grant itself access through MANAGE GRANTS, but it doesn't have it by default. Try it in the simulator: untick ANALYST → SYSADMIN.
SENIOR ANGLE
Separate duties: USERADMIN creates users and roles, SECURITYADMIN manages grants and policies, SYSADMIN owns databases and warehouses, and ACCOUNTADMIN is a break-glass role used rarely, held by at least two people with MFA. Manage all of it as code (Terraform, schemachange or dbt grants) so every grant is reviewed.
CHAPTER 03

Privileges in practice · why can't I query this table?

01 · WHAT IS IT

A privilege is one permitted action on one securable object. The ones you'll use every day:

  • USAGE on a database, schema or warehouse: "you may enter / use it". It doesn't let you read any data by itself.
  • SELECT, INSERT, UPDATE, DELETE, TRUNCATE on tables; SELECT on views.
  • CREATE TABLE / CREATE VIEW… on a schema; OPERATE and MONITOR on a warehouse.
  • OWNERSHIP: full control, exactly one owner role per object.
02 · WHY IT MATTERS

"Access denied" tickets are the most common security work a Snowflake developer does, and the error messages are deliberately vague: Snowflake says an object "does not exist or not authorized" so it never confirms to an unauthorised user that a table exists.

Knowing the full privilege chain, plus future grants, managed access and what CREATE OR REPLACE does to grants, lets you fix those tickets in minutes and design schemas where they don't happen.

03 · HOW IT WORKS · THE PRIVILEGE CHAIN

When you run SELECT * FROM sales_db.core.orders, cloud services checks, for the roles active in your session (primary + secondary, including everything they inherit): USAGE on SALES_DB → USAGE on CORE → SELECT on ORDERS. All three are needed. To actually execute, the session also needs a warehouse the role has USAGE on (USAGE is enough for an auto-resume warehouse to start; OPERATE is needed to suspend or resume it by hand). Privileges are evaluated at compile time, so a denied query never consumes warehouse credits.

Future grants vs ON ALL

GRANT SELECT ON ALL TABLES IN SCHEMA …

A one-time bulk grant on the tables that exist right now. A table created tomorrow gets nothing. A table re-created with CREATE OR REPLACE is a new object and loses its grants (unless you add COPY GRANTS).

GRANT SELECT ON FUTURE TABLES IN SCHEMA …

A rule stored on the schema: every table created there from now on automatically gets the grant. It doesn't touch existing tables, so you run both statements. If a schema has its own future grants for an object type, database-level future grants for that type are ignored in that schema.

Managed access schemas: who is allowed to grant?

In a normal schema, the owner of each object decides who gets access (DAC). In a managed access schema (CREATE SCHEMA … WITH MANAGED ACCESS) object owners lose that right: only the schema owner or a role with MANAGE GRANTS can grant privileges on objects in the schema. Grant decisions become centralised, while engineers can still create and own tables.

Grants to a share

Data sharing uses the same model: GRANT USAGE ON DATABASE … TO SHARE s, GRANT USAGE ON SCHEMA …, GRANT SELECT ON TABLE … TO SHARE s, or grant a database role to the share. Views must be secure views to be shared. Module 10 goes deep.

Transferring ownership

GRANT OWNERSHIP ON TABLE t TO ROLE new_owner COPY CURRENT GRANTS keeps the existing grants on the object. REVOKE CURRENT GRANTS drops them. If the object already has grants to other roles and you specify neither, the statement fails, which protects you from silently breaking access.

Inspect before you guess

SHOW GRANTS ON TABLE t (who can access it), SHOW GRANTS TO ROLE r (what a role holds), SHOW GRANTS TO USER u (which roles a user has), SHOW FUTURE GRANTS IN SCHEMA s. For history: ACCOUNT_USAGE.GRANTS_TO_ROLES and GRANTS_TO_USERS.

INTERVIEW TRAP
"The dbt job rebuilt the table overnight and now the BI tool can't read it." CREATE OR REPLACE TABLE creates a new object, so direct grants on the old one are gone. Fixes: future grants on the schema, COPY GRANTS in the CREATE statement, or dbt's grants config / copy_grants setting.
SENIOR ANGLE
A clean production pattern: one managed access schema per data domain, owned by a deploy role; future grants to <domain>_RO and <domain>_RW access roles; access roles granted to functional roles; nobody grants anything by hand. New tables are readable the moment they're created, and every privilege traces back to code.
CHAPTER 04

Authentication & network · proving who you are, and where from

01 · WHAT IS IT

Authentication answers "are you really this user?". Network policies answer "are you allowed to connect from this address at all?". Both happen before any role or privilege is considered.

Snowflake supports passwords with MFA, key-pair (RSA) authentication, SSO through SAML 2.0 identity providers (Okta, Microsoft Entra ID…), OAuth (Snowflake OAuth or External OAuth), and programmatic access tokens. Users can be provisioned automatically from your IdP with SCIM.

02 · WHY WE USE IT

Stolen credentials are one of the most common causes of cloud data breaches. A strong setup means:

  • Humans log in through the company IdP (SSO) with MFA, so leaving the company disables Snowflake access automatically.
  • Pipelines use service users with key-pair or OAuth: no passwords in config files.
  • Network policies make a leaked credential useless from outside known networks.

Snowflake has been moving toward blocking password-only sign-in for human users and enforcing MFA, in phases. Check the current timeline in the docs, but in an interview say: "humans use SSO + MFA, services use key-pair or OAuth".

03 · HOW IT WORKS · COMPARE THE METHODS
STEPPER · ZERO-DOWNTIME KEY-PAIR ROTATION · service user SVC_ETL
Service users

CREATE USER svc_etl TYPE = SERVICE marks a non-human user. Service users can't log in with a password or use MFA and SSO; they authenticate with key-pair, OAuth or tokens. The default is TYPE = PERSON. A LEGACY_SERVICE type exists for older password-based integrations and is being phased out.

SCIM provisioning

A SECURITY INTEGRATION TYPE = SCIM lets Okta or Entra ID push users and groups into Snowflake: IdP groups become Snowflake roles, and disabling someone in the IdP disables their Snowflake user. The integration runs as a dedicated provisioner role (RUN_AS_ROLE), which owns the users and roles it creates.

Authentication policies

CREATE AUTHENTICATION POLICY controls which methods (AUTHENTICATION_METHODS), client types and MFA settings are allowed, at account or user level. Example: humans must enrol in MFA and may only use SAML; service users only key-pair.

Network policies and network rules

A network rule is a reusable list of network identifiers (TYPE = IPV4 CIDR ranges, or private endpoint IDs such as AWSVPCEID) with a MODE (INGRESS for connections into Snowflake). A network policy references rules in ALLOWED_NETWORK_RULE_LIST and BLOCKED_NETWORK_RULE_LIST (the older ALLOWED_IP_LIST / BLOCKED_IP_LIST still work). You activate a policy on the account, on a user, or on a security integration. Rules: blocked wins over allowed; if an allowed list exists, anything not in it is denied; a user-level policy replaces the account-level one for that user.

INTERVIEW TRAP
"We added a user-level policy for the ETL user and now it can connect from an IP that the account policy blocks. Bug?" No, that's how precedence works: the user-level policy replaces the account-level one for that user, so the account's allowed and blocked lists no longer apply to it. Also remember: Snowflake won't let you activate an account policy that would block your own current IP, which protects you from locking yourself out.
SENIOR ANGLE
Private connectivity (AWS PrivateLink, Azure Private Link, Google Cloud Private Service Connect) keeps traffic off the public internet. It needs Business Critical edition. Combine it with network rules of type AWSVPCEID / AZURELINKID and a policy that blocks public access, so even valid credentials only work from inside your VPC.
CHAPTER 05

Column-level security · dynamic data masking

01 · WHAT IS IT

A masking policy is a schema-level object containing a small SQL expression (usually a CASE) that decides, at query time, what value a user sees in a column: the real value, a partially masked value, a hash, or NULL. You write it once and attach it to any number of columns (ALTER TABLE … MODIFY COLUMN email SET MASKING POLICY pii_email).

The stored data is never changed. That's why it's called dynamic masking: the same row looks different depending on who asks.

02 · WHY WE USE IT
  • One table for everyone instead of a "masked copy" per audience, which drifts and doubles storage.
  • Follows the column everywhere: views, joins, CTAS, BI tools, shares. You can't bypass it by querying differently.
  • Separation of duties: a security team owns the policy, and even the table owner (or ACCOUNTADMIN) sees masked data unless the policy says otherwise.
  • GDPR / HIPAA / PCI: PII and PHI visible only to those with a need to know.
03 · HOW IT WORKS · IN THE BACKEND

When a query is compiled, cloud services sees that a column has a policy and rewrites the query: every reference to email becomes pii_email(email) wrapped around the column at the point it's read from the table. The policy body is evaluated per row with session context functions:

  • CURRENT_ROLE() returns only the primary role name. It ignores the role hierarchy and secondary roles.
  • IS_ROLE_IN_SESSION('PII_READER') returns TRUE if that role is the primary role, a secondary role, or inherited by them. This is usually what you want.
  • INVOKER_ROLE() is useful when the policy fires inside a view or UDF.

Conditional masking passes extra columns into the policy (USING (email, consent_flag)), so a value can be shown or hidden based on another column in the same row.

Tag-based masking

Attach a policy to a tag instead of a column: ALTER TAG pii SET MASKING POLICY pii_string. Every column tagged pii (now or later) whose data type matches is masked automatically. One policy per data type per tag. A policy set directly on a column takes precedence over the tag-based one.

External tokenization

Data is tokenized before it lands in Snowflake by a partner (for example Protegrity or ALTR). A masking policy calls an external function to detokenize on the fly, but only for authorised roles. Snowflake never stores the clear value.

Rules worth knowing

A column can have one masking policy. The policy's input and return types must match the column type. Masking applies to the result, so WHERE email = 'x@y.com' by a masked role compares against the masked value. Use POLICY_REFERENCES to see where a policy is attached.

INTERVIEW TRAP
"I'm HR_ADMIN, which inherits PII_READER, but I still see masked emails." The policy uses CURRENT_ROLE() IN ('PII_READER'), which compares only the primary role's name. Switch to IS_ROLE_IN_SESSION('PII_READER'), which honours the hierarchy and secondary roles. Try it in the simulator.
SENIOR ANGLE
Don't hard-code role names in 40 policies. Keep a small entitlement table or a dedicated role (PII_READER) and reference it in every policy, then manage who gets that role. Combine with tag-based masking and classification so new PII columns are protected the day they're created.
CHAPTER 06

Row-level security · row access policies

01 · WHAT IS IT

A row access policy is a schema-level object whose body returns a BOOLEAN for each row: TRUE means the row is visible, FALSE means it silently disappears from the result. You attach it to a table or view on one or more columns: ALTER TABLE orders ADD ROW ACCESS POLICY region_rap ON (region).

The most common pattern uses a mapping table: role SALES_EMEA → region EMEA. The policy looks up whether the current role is mapped to the row's region.

02 · WHY WE USE IT
  • One ORDERS table instead of ORDERS_EMEA, ORDERS_APAC… or dozens of filtered views.
  • Access changes are data changes (insert a row in the mapping table), not code deployments.
  • Works for multi-tenant SaaS (tenant_id), regional compliance, and manager hierarchies.
  • Enforced for every query path: BI tools, notebooks, ad-hoc SQL.
03 · HOW IT WORKS · IN THE BACKEND

At compile time Snowflake rewrites the query as if a hidden WHERE region_rap(region) filter were added on the table scan. If the policy body queries a mapping table, that lookup becomes part of the plan (typically a join or semi-join), and it runs with the policy owner's privileges, so users don't need SELECT on the mapping table. Row access is evaluated before masking.

Performance tips: keep the mapping table small, use simple equality lookups, and consider memoizable functions for the lookup. Large or complex policy bodies show up as extra joins in the Query Profile.

"A user says the dashboard total is wrong." With row access policies there's no error when rows are filtered: COUNT(*) and SUM() simply return smaller numbers. Always check POLICY_REFERENCES for the table and the user's role mapping before debugging the SQL.

CHAPTER 07

Governance & monitoring · know your data, prove who touched it

01 · WHAT IS IT
  • Object tagging: key-value labels (cost_center = 'finance', pii = 'email') on accounts, warehouses, databases, schemas, tables and columns.
  • Data classification: Snowflake samples column values and suggests semantic categories (EMAIL, NAME, PHONE_NUMBER…) and privacy categories (IDENTIFIER, QUASI_IDENTIFIER, SENSITIVE), optionally applying system tags.
  • Audit views: ACCESS_HISTORY (which columns each query read and wrote), LOGIN_HISTORY, QUERY_HISTORY.
  • Secure views / UDFs, Trust Center, and the encryption model underneath everything.
02 · WHY WE USE IT

Masking and row access policies protect data you know is sensitive. Governance answers the harder questions: where is all our PII?, who queried customer emails last quarter?, which dashboards break if we drop this column?, how much does the finance team spend?

Auditors and regulators ask for evidence, not intentions. These features turn "we think it's secure" into a query result.

03 · HOW IT WORKS · TAG INHERITANCE (click a level)

A tag set on a parent object is inherited by its children: tag a schema and every table and column in it reports that tag, unless a child sets its own value (the nearest one wins). Query TAG_REFERENCES or the TAG_REFERENCES_ALL_COLUMNS function to see direct and inherited tags.

Snowflake has also added automatic tag propagation, where tags can follow data into derived objects (for example through CTAS or views) when the tag is configured to propagate. Check the current docs for exactly which operations propagate.

Classification

SYSTEM$CLASSIFY('db.sch.customers', {'auto_tag': true}) analyses a table and can set the system tags SNOWFLAKE.CORE.SEMANTIC_CATEGORY and PRIVACY_CATEGORY on columns. Snowflake also offers automatic, scheduled classification of whole databases through classification profiles. Feature names and options have evolved, so verify the current syntax.

ACCESS_HISTORY

In SNOWFLAKE.ACCOUNT_USAGE (Enterprise+). One row per query with JSON arrays: direct_objects_accessed (what the SQL named), base_objects_accessed (the underlying tables behind views), objects_modified (writes, with column lineage) and policies_referenced. Data arrives with some latency (up to a few hours) and is kept for 365 days.

LOGIN_HISTORY

Every login attempt: user, client IP, client type, first and second authentication factor, success flag and error message. ACCOUNT_USAGE.LOGIN_HISTORY keeps 365 days (with latency); the INFORMATION_SCHEMA.LOGIN_HISTORY() table function covers the last 7 days in near real time.

Secure views & UDFs

CREATE SECURE VIEW hides the view definition from non-owners and stops the optimizer from using tricks (like pushing a user's filter below the view's own filter) that could leak hidden rows through errors or timing. The cost: some optimizations are disabled, so they can be slower. Required for views in shares.

Trust Center

A Snowsight area that runs scanners against your account (for example CIS benchmark checks: MFA for ACCOUNTADMIN users, network policies set, and so on) and lists findings with remediation guidance. A good answer to "how do you continuously check the security posture?".

Object dependencies & lineage

ACCOUNT_USAGE.OBJECT_DEPENDENCIES shows which views depend on which tables. With objects_modified in ACCESS_HISTORY you get column-level lineage: which source columns fed which target columns.

Encryption: the key hierarchy

All data in Snowflake is encrypted at rest with AES-256 and in transit with TLS 1.2+, always on, at no cost. Keys form a hierarchy: a root key held in a hardware security module (HSM) protects account master keys, which protect table master keys, which protect the file keys that encrypt each micro-partition. Each key only protects a small amount of data, which limits the blast radius of any single key.

INTERVIEW TRAP
Rotation ≠ rekeying. Rotation (automatic, about every 30 days) means new data gets a new key and old keys become decrypt-only; old data stays encrypted with old keys. Periodic rekeying (PERIODIC_DATA_REKEYING = TRUE, Enterprise+) re-encrypts data whose key is older than a year with a fresh key, then retires the old key for good.
SENIOR ANGLE
Tri-Secret Secure (Business Critical) combines a Snowflake-managed key with a customer-managed key in your cloud KMS into a composite master key. Snowflake can't decrypt your data without your key, and if you revoke it, the data becomes unreadable, which is a strong control for regulated industries. The trade-off: losing or revoking the key by mistake means losing access.
