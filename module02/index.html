MODULE 02 · LOAD & AUTOMATE

Get data in.
Keep it moving.|

Module 1 showed how Snowflake is built. This module covers how data actually gets into it and keeps flowing: SnowSQL to move files from your laptop, the unstructured data pipeline for PDFs, audio and images, streams and tasks to process new data automatically, and stored procedures to package multi-step logic into one call.

We'll keep the restaurant analogy from Module 1 and add four new characters:

SNOWSQL
The delivery van

Drives ingredients (files) from your home (laptop) to the restaurant's pantry (stage), and lets you phone in orders (SQL) from outside.

UNSTRUCTURED DATA
Sealed crates

A whole fish, a sack of potatoes: nothing is labelled or portioned. You store the crate, write it in the inventory book (directory table), then prep it into usable pieces.

STREAM
The ticket rail

Shows only the order tickets that arrived since the chef last cleared the rail. It doesn't hold the food, just a bookmark of what's new.

TASK
The kitchen timer

Rings every few minutes and tells a chef to cook whatever is on the ticket rail. If the rail is empty, nobody turns on the stove.

CHAPTER 01

SnowSQL · Snowflake from your terminal

01 · WHAT IS IT

SnowSQL is Snowflake's command-line client. You install it on your laptop or a server, type snowsql, and get a prompt where you can run any SQL plus special client commands that start with ! (like !spool or !source).

Under the hood it's built on the Snowflake Python connector. It talks to your account URL (<account>.snowflakecomputing.com) over HTTPS (TLS, port 443), the same way Snowsight or a JDBC driver does.

Snowflake's newer CLI is Snowflake CLI (command snow). Snowflake now recommends it for new work, but SnowSQL is still in heavy use, so interviewers ask about both.

02 · WHY WE USE IT
  • Upload and download local files: PUT sends files from your machine to an internal stage, and GET brings them back. You can't run these from a Snowsight worksheet.
  • Automation: run SQL scripts from shell scripts, cron jobs, Airflow or CI/CD (snowsql -f deploy.sql), with exit codes your scheduler can check.
  • Scripting features: variables (&run_date), output to CSV files (!spool), and named connections stored in a config file.
  • No browser needed: works on servers and over SSH.

"Which commands only work from a client like SnowSQL?" PUT and GET, because they move files between your local file system and an internal stage. For external stages (S3, Azure, GCS), you upload with cloud tools instead, and Snowflake reads the files with COPY.
CHAPTER 02

Inside PUT & COPY · what happens in the backend

01 · WHAT IS IT

Loading a local file into a table is two separate steps:

  • PUT: copy the file from your laptop into a stage (a storage area Snowflake manages). The file is still just a file.
  • COPY INTO: a warehouse reads the staged files, parses them, and writes the rows into a table as micro-partitions.
02 · WHY TWO STEPS?

Moving bytes over the network and parsing or converting data are very different jobs. PUT is network-bound and runs on your machine, so it costs no warehouse credits. COPY is CPU-bound and runs in parallel on a warehouse. Splitting them also means a failed load can be re-run straight from the stage without uploading again.

03 · HOW PUT WORKS · STEP BY STEP
1 · Ask for permission

SnowSQL asks cloud services where the stage lives. It gets back temporary, scoped credentials for that storage location.

2 · Compress

With AUTO_COMPRESS=TRUE (the default), each file is gzipped on your laptop, so a CSV usually shrinks to around a quarter of its size and far fewer bytes cross the network.

3 · Encrypt

Files are encrypted before they leave your machine, so they're never readable in transit or at rest.

4 · Upload in parallel

PARALLEL=n threads (default 4, max 99) upload files directly to cloud storage. Large files are uploaded in chunks. A file with the same name that's already in the stage is SKIPPED unless you add OVERWRITE=TRUE.

Then COPY INTO: cloud services checks the table's load metadata (which files were already loaded in the last 64 days) and skips them. That's why running the same COPY twice doesn't create duplicates. The warehouse splits the remaining files across its workers, parses them with the FILE_FORMAT, and writes compressed columnar micro-partitions.

CHAPTER 03

Unstructured data · PDFs, audio, images in Snowflake

01 · WHAT IS IT

Data comes in three shapes. Click each one to see how Snowflake stores it:

02 · WHY IT MATTERS

Most company data is unstructured: contracts, invoices, support call recordings, product photos, scanned forms, emails. It holds valuable facts (amounts, dates, complaints, defects) that SQL can't reach until you extract them.

Snowflake lets you keep these files next to your tables, with the same security and governance, and process them with SQL (Cortex AI functions) or Python. There's no separate document system to run, and the files never leave Snowflake.

03 · HOW IT WORKS · THE FULL PIPELINE (click Next)

Each step shows what you do and what happens in the backend. The key idea: the file itself is never turned into table rows. It stays a file in a stage. Snowflake keeps a catalog of the files, and you write the extracted results to normal tables.

Three ways to point at a staged file

To let a function, an app or a person open a staged file, you generate a URL for it. Interviewers like to ask how these three differ.

Scoped URL

BUILD_SCOPED_FILE_URL(@stage, path)
Encoded URL that only works for the user or role that generated it, valid for 24 hours (the duration of the query's result cache). Best for passing files into UDFs and for short-lived access. Callers don't need privileges on the stage.

File URL

BUILD_STAGE_FILE_URL(@stage, path)
Permanent URL. Anyone opening it must authenticate to Snowflake and have privileges on the stage. Good for internal apps and catalogs. The directory table's FILE_URL column contains it.

Pre-signed URL

GET_PRESIGNED_URL(@stage, path, seconds)
A plain HTTPS link that needs no Snowflake login and expires after the time you set. Good for showing a document in a BI tool or browser. Treat it like a temporary password.

INTERVIEW TRAP
"I PUT a PDF into a stage and the AI function can't read it." By default PUT gzips the file (AUTO_COMPRESS=TRUE), so the stage holds contract.pdf.gz, not a PDF. For unstructured files, use AUTO_COMPRESS=FALSE. For internal stages used with Cortex or pre-signed URLs, also create the stage with ENCRYPTION = (TYPE = 'SNOWFLAKE_SSE') (server-side encryption).

CHAPTER 05

Streams · "what changed since last time?"

01 · WHAT IS IT

A stream is an object that records which rows changed in a table (or view, directory table, external table…) since a bookmark called the offset. You query it like a table and get the changed rows plus three extra columns:

  • METADATA$ACTION: INSERT or DELETE
  • METADATA$ISUPDATE: TRUE when the row is half of an UPDATE
  • METADATA$ROW_ID: a stable, unique ID for the row

A stream stores no data. It stores only the offset, a point in the table's version history. When you query it, Snowflake compares the table "then" (at the offset) with "now" using the same versioning that powers Time Travel (from Module 1).

02 · WHY WE USE IT

This is Change Data Capture (CDC) inside Snowflake. Without a stream you'd reprocess the whole table every run, or rely on fragile updated_at > last_run logic that misses deletes and late updates.

  • Process only new or changed rows, which is cheap and fast
  • Captures inserts, updates and deletes
  • Exactly-once handoff: the offset moves only when your DML commits
03 · HOW IT WORKS · PLAY WITH IT

Change the source table, then watch the stream. Note the difference between just looking (SELECT) and consuming (using the stream in a DML statement such as INSERT or MERGE). Only consuming moves the offset.

Standard (delta)

Inserts, updates and deletes, as net changes. A row inserted and then deleted before you consume shows nothing. For tables, directory tables and views.

Append-only

Only inserts. Updates and deletes are ignored, so it's much cheaper to compute. Ideal for append-only event and log tables.

Insert-only

For external tables and externally managed Iceberg tables: tracks new files and rows only, because Snowflake can't see changes to existing files.

INTERVIEW TRAP
Staleness. If a stream isn't consumed within the table's data retention period, its offset falls out of the history and the stream becomes stale, which means unusable until it's recreated (and you may lose changes). When retention is shorter than 14 days, Snowflake temporarily extends it for tables that have streams, up to MAX_DATA_EXTENSION_TIME_IN_DAYS (default 14). Check STALE and STALE_AFTER in SHOW STREAMS, and consume regularly.
SENIOR ANGLE
One stream per consumer. Two pipelines reading one stream will fight: the first one to commit moves the offset, and the second one misses those changes. Create two streams on the same table, which costs almost nothing because streams store no data.
CHAPTER 06

Tasks · Snowflake's built-in scheduler

01 · WHAT IS IT

A task runs one SQL statement or stored procedure call on a schedule (SCHEDULE = '5 MINUTE' or a CRON expression with a time zone), or after another task finishes.

Tasks can be chained into a task graph (DAG): one root task has the schedule, child tasks declare AFTER parent, and an optional finalizer task runs at the end whether the run succeeded or failed (good for cleanup and alerts).

02 · WHY WE USE IT
  • Automate pipelines inside Snowflake, with no external scheduler needed for simple flows
  • Combined with streams, process new data every few minutes (near-real-time CDC)
  • WHEN SYSTEM$STREAM_HAS_DATA('s') skips the run when there's nothing new, without starting any compute
  • Runs with the task owner's privileges, and every run is logged in TASK_HISTORY
03 · HOW IT WORKS
Serverless tasks

Omit WAREHOUSE. Snowflake picks and resizes the compute automatically from past runs, and you're billed only for the seconds actually used, with no 60-second minimum or idle time. Great for short, frequent tasks. Requires the EXECUTE MANAGED TASK privilege.

User-managed (warehouse) tasks

Set WAREHOUSE = etl_wh. Each run resumes that warehouse, so the usual billing applies: 60-second minimum + idle time until auto-suspend. Better for long, heavy, predictable jobs or when you want to share an existing warehouse.

Lifecycle: every new task is created SUSPENDED. You must ALTER TASK … RESUME it (children first, root last, or use SYSTEM$TASK_DEPENDENTS_ENABLE('root')). By default, if a run is still going when the next scheduled time arrives, the new run is skipped (ALLOW_OVERLAPPING_EXECUTION = FALSE).

CHAPTER 07

Streams + tasks together · a live CDC pipeline

This is the classic pattern from interviews: new orders land in RAW_ORDERS, a stream marks them as new, and every minute a task checks the stream. If there's data, it MERGEs the changes into CURATED_ORDERS, and that commit moves the stream's offset. Press Start the clock, then send orders.

LIVE ANIMATION · RAW → STREAM → TASK → CURATED
Start the clock. One simulated minute passes every 6 real seconds.
CREATE STREAM raw_stream ON TABLE raw_orders; CREATE TASK merge_orders SCHEDULE = '1 MINUTE' -- serverless (no WAREHOUSE) WHEN SYSTEM$STREAM_HAS_DATA('raw_stream') -- skip when nothing new AS MERGE INTO curated_orders t USING raw_stream s ON t.order_id = s.order_id WHEN MATCHED AND s.METADATA$ACTION = 'INSERT' THEN UPDATE SET t.amount = s.amount WHEN NOT MATCHED AND s.METADATA$ACTION = 'INSERT' THEN INSERT (order_id, amount) VALUES (s.order_id, s.amount); -- the MERGE commits → offset of raw_stream moves forward → stream is empty again ALTER TASK merge_orders RESUME;
SENIOR ANGLE
Streams + tasks vs dynamic tables. A dynamic table is declarative: you write a SELECT and a TARGET_LAG, and Snowflake handles incremental refresh for you. Choose streams + tasks when you need procedural control: custom MERGE logic, SCD Type 2, calling procedures, sending notifications, or writing to several targets.
INTERVIEW TRAP
"My task ran but the stream didn't empty." The task probably only SELECTed from the stream (for example inside a procedure that returned a result), or the transaction rolled back. The offset moves only when the stream is used in DML and the transaction commits.
CHAPTER 08

Stored procedures · programs that run inside Snowflake

01 · WHAT IS IT

A stored procedure is a named program saved in a schema and run with CALL my_proc(args). Inside, it can run many SQL statements plus real programming logic: variables, IF/ELSE, loops, cursors and error handling.

Unlike a view or a UDF, it can change things: DML (INSERT, MERGE, DELETE), DDL (CREATE, ALTER, DROP) and even GRANTs. You can write it in SQL (Snowflake Scripting), Python, JavaScript, Java or Scala. It returns one value (a status message, a number, a JSON object) or, with RETURNS TABLE, a result set.

02 · WHY WE USE IT
  • Multi-step logic in one call: a task runs exactly one statement, so real pipelines are written as a procedure and the task just CALLs it.
  • Control flow and error handling that plain SQL lacks: skip when there's no data, validate, roll back, log, re-raise.
  • Controlled access: with owner's rights, an analyst can run purge_old_orders() without ever being granted DELETE on the table.
  • Dynamic SQL: loop over 50 staging tables, or build statements from metadata.
  • Reuse: one tested piece of logic instead of copy-pasted scripts.

Where does a procedure actually run?

1 · CALL goes to cloud services

Cloud services checks that your role has USAGE on the procedure, binds the arguments, and starts executing the body.

2 · Each statement is a real query

Every SELECT, INSERT or MERGE inside a SQL procedure is compiled and run like any other query, on the session's current warehouse, and shows up separately in Query History. To speed up a slow procedure, find its slowest statement.

3 · Python, Java, Scala

These run in a secure sandbox on the warehouse. The handler's first argument is a Snowpark Session, and libraries come from Snowflake's Anaconda channel through PACKAGES. Memory-heavy work may need a Snowpark-optimized warehouse.

Owner's rights vs caller's rights

A procedure always runs with someone's privileges. Owner's rights (EXECUTE AS OWNER, the default) uses the privileges of the role that owns the procedure. Caller's rights (EXECUTE AS CALLER) uses the privileges and session of whoever calls it.

INTERVIEW TRAP
BEGIN is not a transaction. In Snowflake Scripting, BEGIN … END only marks a block of code. To make several statements all-or-nothing, write BEGIN TRANSACTION … COMMIT, with ROLLBACK in the EXCEPTION handler. Any DDL statement (CREATE, ALTER, DROP) also commits an open transaction implicitly.
SENIOR ANGLE
A good production procedure is idempotent (DELETE + INSERT, or MERGE, for the run date, so re-runs never duplicate), returns a status, logs every run to an audit table, and re-raises errors so the calling task fails loudly instead of succeeding silently.
