MODULE 05 · DYNAMIC TABLES & TRANSFORMS

Describe the result.
Let Snowflake keep it fresh.

Module 04 got raw data into Snowflake. This module is about what happens next: turning messy raw rows into clean, trustworthy tables that dashboards and data scientists can use. You'll learn dynamic tables (Snowflake's declarative pipelines), how incremental refresh really works, when to pick streams + tasks or materialized views instead, MERGE and slowly changing dimensions, deduplication, UDFs, and how transactions and locks behave when several jobs write at once.

Four characters to keep in mind as we go:

DYNAMIC TABLE
A spreadsheet formula cell

You type =SUM(A1:A9) once and the cell keeps itself up to date. A dynamic table is a SELECT that Snowflake keeps refreshed, within a delay you choose.

MERGE
Updating the class register

New student? Add a line. Existing student changed section? Update their line. Left the school? Strike them off. One pass over the register does all three.

SCD TYPE 2
Passport stamps

You don't erase the old visa when you get a new one. Every version stays, each with its own valid-from and valid-to dates, so you can answer "where was this customer living in March?"

UDF
A custom kitchen gadget

When the built-in knives aren't enough, you build your own tool once (a function) and every chef can use it inside any recipe (query).

01 · WHAT IS IT

The transformation layer is everything between "data landed" and "data is ready to use". Most teams organise it in layers (you'll hear bronze / silver / gold or raw / staging / marts):

  • Raw: exactly what arrived (files, CDC rows, JSON). Never edited, so you can always replay.
  • Clean / staging: typed, deduplicated, renamed, filtered, joined to reference data.
  • Marts: business-shaped tables (facts and dimensions, daily aggregates) built for BI.

There are two ways to build those layers: procedural ("do step 1, then step 2, on this schedule") and declarative ("this table should always equal this SELECT, no more than 10 minutes behind").

02 · WHY IT MATTERS

Raw data is rarely usable directly: duplicates from retries, late-arriving rows, inconsistent types, history that needs to be kept. Interviewers for a senior role want to hear that you can build this layer so that it is:

  • Correct: no duplicates, history handled deliberately (SCD).
  • Fresh enough: matched to what the business really needs, not "real time" by default.
  • Cheap: processes only what changed where possible.
  • Re-runnable: a retry never doubles the numbers.
03 · HOW IT WORKS · PROCEDURAL VS DECLARATIVE (click around)

Pick a style, then pick a layer. Notice what you have to write and own in each style. In Module 02 you built the procedural version with streams, tasks and stored procedures; here you see the declarative alternative next to it.

Style:
Layer:

Procedural is giving a new cook a recipe card: "every 5 minutes, check the ticket rail, chop what's new, add it to the pot". CHAPTER 01

Dynamic tables · a SELECT that keeps itself fresh

01 · WHAT IS IT

A dynamic table (DT) is a table whose contents are defined by a query. You don't INSERT into it; Snowflake refreshes it so that it matches the query result, within a delay you choose called the target lag.

CREATE OR REPLACE DYNAMIC TABLE stg_orders TARGET_LAG = '10 minutes' -- or DOWNSTREAM WAREHOUSE = transform_wh -- compute used for refreshes REFRESH_MODE = AUTO -- AUTO | INCREMENTAL | FULL INITIALIZE = ON_CREATE -- or ON_SCHEDULE AS SELECT order_id, customer_id, amount::NUMBER(12,2) AS amount, order_ts FROM raw_orders WHERE amount IS NOT NULL;

It's a real table on disk (micro-partitions, queryable, clonable), just read-only for DML: Snowflake owns its contents.

02 · WHY WE USE IT
  • No orchestration code: no streams, tasks, MERGE statements or dependency wiring for straightforward transformations.
  • Freshness as a setting: you state "10 minutes behind at most" instead of hand-tuning schedules.
  • Incremental for free (when possible): Snowflake works out which rows changed and updates only the affected results.
  • Chains are automatic: a DT can read other DTs; Snowflake builds the dependency graph and refreshes it in the right order with consistent snapshots.
  • Built-in observability: refresh history, graph view in Snowsight, per-refresh statistics.
03 · HOW IT WORKS · THE BACKEND
Target lag

The maximum amount of time the DT's content should trail its base tables (lag is measured against the original sources, not against the DT right above it). A time value such as '1 minute' or '4 hours' (check the docs for the current minimum), or DOWNSTREAM: "refresh me only when a DT that reads from me needs fresh data". A DOWNSTREAM table with no time-based consumer never refreshes on its own.

Scheduling by lag

There is no CRON. Snowflake's scheduler picks refresh times so the lag stays under target, typically refreshing more often than the lag value to leave headroom. Refreshes across a graph are aligned so every DT reads upstream data as of the same data timestamp, which keeps joins consistent.

Refresh modes

INCREMENTAL: process only changes since the last refresh, using change tracking on the sources. FULL: recompute the whole query and replace the content. AUTO: Snowflake chooses at creation time based on the query. The chosen mode is visible in SHOW DYNAMIC TABLES (refresh_mode, plus refresh_mode_reason when it picks FULL). For production, Snowflake advises setting the mode explicitly rather than relying on AUTO.

Initialization

INITIALIZE = ON_CREATE (default) runs the first full population synchronously inside the CREATE, so a slow query means a slow CREATE. ON_SCHEDULE returns immediately and populates at the first scheduled refresh. Change tracking is enabled on the source tables automatically if the owner has the rights to do so.

Each refresh

Cloud services first checks whether any source changed. If nothing did, the refresh is recorded as NO_DATA and the data timestamp still moves forward without real warehouse work. Otherwise the refresh runs as an ordinary query on the DT's WAREHOUSE and commits atomically: readers see the old version or the new one, never half.

Operate & monitor

ALTER DYNAMIC TABLE … SUSPEND | RESUME | REFRESH (needs OPERATE). History in INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY() and ACCOUNT_USAGE.DYNAMIC_TABLE_REFRESH_HISTORY. Repeated consecutive refresh failures can auto-suspend a DT, so alert on failures.

Cost model: you pay (1) warehouse credits for every refresh that does real work, under the usual warehouse billing (60-second minimum on resume, then per second, plus idle time before auto-suspend), (2) a small amount of cloud services for change checks, and (3) storage for the DT's data and its Time Travel history. Shorter lag means more refreshes, so lag is the biggest cost dial you have.

INTERVIEW TRAP
"I set every DT to DOWNSTREAM and nothing refreshes." DOWNSTREAM means "refresh when someone below me needs it". If the leaf DT is also DOWNSTREAM, nobody ever asks, so the graph sits still unless you refresh manually. Rule of thumb: time-based lag on the leaves (what users query), DOWNSTREAM on the intermediate DTs.
SENIOR ANGLE
Don't ask for "1 minute" because it sounds good. Ask what decision the data drives. A finance mart refreshed hourly can cost a small fraction of the same mart at 1-minute lag. Also keep refresh warehouses separate from BI warehouses so refresh load never slows dashboards, and size them for the refresh query, not the base table.
CHAPTER 02

Incremental vs full refresh · the deep dive

01 · WHAT IS IT

Full refresh re-runs the whole query and swaps in the result. Simple, always correct, cost grows with the size of the inputs.

Incremental refresh computes only how the result changes because of the rows that changed in the inputs, then applies that change to the DT. Its cost grows with the amount of change, not with table size.

02 · WHY IT MATTERS

A 2-billion-row fact table where 50,000 rows arrive every 10 minutes: full refresh re-reads 2 billion rows each time; incremental touches roughly the 50,000 new ones and the results they affect. That's the difference between a pipeline that costs a little and one that costs a lot.

But incremental is not always cheaper: when a large share of the input changes, or changes are scattered everywhere, working out the delta can cost more than just recomputing.

03 · HOW IT WORKS · INSIDE AN INCREMENTAL REFRESH
1 · Change tracking

Sources have change tracking enabled (the same hidden row-level metadata that powers streams, from Module 02). Snowflake can ask: "which rows were inserted or deleted between version A and version B?"

2 · Delta query

The DT's SELECT is rewritten into a delta query. A filter just filters the changed rows. A join becomes "changed left rows ⋈ right" plus "left ⋈ changed right rows". An aggregate recomputes only the groups those rows belong to.

3 · Apply

The delta is merged into the DT: inserts, deletes, and updates as delete + insert. Micro-partitions are immutable, so every DT partition holding a changed row is rewritten. Scattered changes mean many partitions rewritten.

4 · Commit

The new DT version and its data timestamp commit atomically. Downstream DTs then use this version as their input snapshot.

What makes a query incremental-capable?

Usually fine for incremental

Projections and deterministic expressions, WHERE, inner and outer joins, GROUP BY with common aggregates, UNION ALL, DISTINCT, LATERAL FLATTEN, window functions with PARTITION BY, CTEs, reading other DTs.

Commonly forces FULL (verify against current docs)

Non-deterministic functions such as RANDOM() or time functions like CURRENT_TIMESTAMP() in the logic, external functions, sampling, some set operators (e.g. MINUS/INTERSECT) and certain unusual nested constructs. Snowflake keeps widening support, so check refresh_mode_reason instead of memorising a list.

If you say REFRESH_MODE = INCREMENTAL and the query isn't supported, the CREATE fails with an explanation. With AUTO, Snowflake silently picks FULL. That silence is why teams pin the mode explicitly in production: you'd rather find out at deploy time than on the invoice.

INTERVIEW TRAP
"AUTO will switch to FULL on days with lots of changes." No: AUTO picks a mode when the DT is created (or recreated) and keeps it. It doesn't re-decide per refresh. If your change ratio swings wildly, choose the mode yourself.
SENIOR ANGLE
To keep incremental refresh cheap: avoid non-deterministic functions, keep the DT's natural write pattern append-like, cluster or order the DT by the column most changes land in (often a date), and split one giant DT into a chain so each step has a simple, incremental-friendly shape.
CHAPTER 03

DT vs streams + tasks vs MV vs view · picking the right tool

01 · WHAT IS IT

Four ways to give users "a table that reflects a query": a view (computed every time someone queries it), a materialized view (pre-computed and kept current by a background service), a dynamic table (pre-computed, refreshed to a target lag), and streams + tasks (you write the change-processing logic yourself, from Module 02).

02 · WHY IT MATTERS

"Which would you use and why?" is one of the most common senior-level questions. The right answer always names the trade-off: freshness vs cost vs flexibility vs how much code you own.

"Materialized views are just cached results, so they can be stale." For Snowflake MVs that's wrong: results are always current, because Snowflake fills in base-table changes that background maintenance hasn't applied yet. SENIOR ANGLE
Mixed architectures are normal: Snowpipe → raw, streams + tasks where you need SCD2 or side effects, dynamic tables for the bulk of the clean and mart layers, secure views on top for consumers and sharing, and a materialized view only for one or two hot single-table aggregates.
CHAPTER 04

MERGE patterns · upserts, deletes, SCD Type 1 & 2

01 · WHAT IS IT

MERGE compares a source (new data) with a target table on a key and, in one statement, decides per row what to do:

  • WHEN MATCHED [AND cond] THEN UPDATE: the key exists, so change it
  • WHEN MATCHED [AND cond] THEN DELETE: the key exists but the source says remove it
  • WHEN NOT MATCHED [AND cond] THEN INSERT: a new key, so add it

A slowly changing dimension (SCD) is a dimension (customer, product, employee) whose attributes change now and then. Type 1 overwrites: only the latest value survives. Type 2 keeps history: the old row is closed (effective_to set, is_current = FALSE) and a new version is opened.

02 · WHY WE USE IT
  • One atomic statement instead of separate UPDATE + INSERT + DELETE that could half-succeed.
  • Idempotent loads: re-running a MERGE with the same source doesn't create duplicates.
  • CDC application: apply inserts, updates and deletes from a stream or a source system's change feed.
  • Correct history: SCD2 lets you report "sales by the region the customer lived in at the time", which SCD1 can't.
03 · HOW IT WORKS · BACKEND

MERGE runs as a join between source and target (the Query Profile literally shows a join), followed by writes. Because micro-partitions are immutable, every target partition with an updated or deleted row is rewritten, and new rows go into new partitions. Two consequences interviewers like:

Prune the target

Add a predicate on a clustered column (e.g. AND t.order_date >= '2024-06-01') in the ON clause or source so the join reads only recent partitions instead of the whole target.

One source row per key

If two source rows match the same target row for UPDATE/DELETE, Snowflake raises a nondeterministic merge error (controlled by ERROR_ON_NONDETERMINISTIC_MERGE, default TRUE). Deduplicate the source first (next chapter).

Hash diff

Compare one hash of all tracked columns instead of a.x <> b.x OR …. Use MD5/SHA2 over a delimited string, and COALESCE NULLs first: CONCAT_WS returns NULL if any argument is NULL, and NULL <> 'x' is not TRUE.

INTERVIEW TRAP
"Write SCD2 with one MERGE." A single MERGE can either update or insert per source row, but a changed customer needs both (close the old row and insert the new one). The classic trick: build the source as a UNION ALL where changed keys appear twice, once with the real key (matches → close) and once with a NULL merge key (never matches → insert). The alternative is UPDATE then INSERT inside one explicit transaction. Both are in the SQL lab.
SENIOR ANGLE
Use a surrogate key (sequence or IDENTITY) on SCD2 dimensions so facts point at the version that was current when the event happened. Use effective_to = '9999-12-31' (or NULL) consistently for open rows, and make effective_from come from the source change time, not load time, otherwise late-arriving changes create wrong history.
CHAPTER 05

Deduplication & idempotency · run it twice, get the same answer

01 · WHAT IS IT

Deduplication keeps exactly one row per business key. The Snowflake idiom is QUALIFY ROW_NUMBER() OVER (PARTITION BY key ORDER BY version DESC) = 1: number the rows inside each key, newest first, and keep row 1. QUALIFY filters on a window function the way HAVING filters on an aggregate.

Idempotency means running a load once or five times leaves the target in the same state.

02 · WHY WE USE IT
  • Retries, at-least-once delivery (Kafka, Snowpipe re-sends, CDC tools) and re-dropped files all create duplicates.
  • Orchestrators retry failed jobs automatically. If the job isn't idempotent, a retry doubles revenue on the dashboard.
  • Late-arriving data: an older version of a row can arrive after a newer one. Picking "the last one loaded" then silently goes backwards in time.
03 · HOW IT WORKS · BACKEND

The window function needs all rows for a key together, so Snowflake repartitions (shuffles) rows by the PARTITION BY key across the warehouse, sorts within each key, then filters. On large tables that shuffle is the cost; limit it by deduplicating only the new batch plus a lookback window, not all of history.

ROW_NUMBER vs RANK

ROW_NUMBER always gives 1, 2, 3, so exactly one survivor. RANK / DENSE_RANK give ties the same number, so two rows can both be "1" and duplicates survive.

Deterministic tie-break

If two rows tie on the ORDER BY, which one is "1" is not guaranteed and can change between runs. Always add tie-breakers (ingest time, file name, row number in file) until the order is total.

Version, not arrival

Order by the source's version (updated_at, CDC LSN / sequence), then by arrival only as a tie-break. Ordering by arrival time lets late, older data win.

CHAPTER 06

UDFs & UDTFs · your own functions inside SQL

01 · WHAT IS IT

A user-defined function (UDF) is a function you create and then call inside any query, like a built-in: SELECT clean_phone(phone) FROM customers. A scalar UDF returns one value per input row.

A user-defined table function (UDTF) returns zero, one or many rows per input row (or per partition of rows), and you call it in the FROM clause: FROM events, TABLE(sessionize(user_id, ts) OVER (PARTITION BY user_id ORDER BY ts)).

Languages: SQL, Python, Java, JavaScript (and Scala). UDFs are read-only: they can't run DML. That's what procedures are for (Module 02).

02 · WHY WE USE IT
  • Reuse: one tested definition of "clean a phone number" or "fiscal quarter" instead of the same CASE expression copied into 40 models.
  • Logic SQL can't express easily: regex-heavy parsing, scoring with a Python library, fuzzy matching.
  • Row-expanding logic (UDTF): sessionization, splitting a string into tokens, exploding date ranges into days, stateful running logic per partition.
  • Hide logic or data: secure UDFs keep the definition and any internal lookup data private, which helps with sharing.
03 · HOW IT WORKS · WHERE THE CODE RUNS
SQL UDFs

The expression is typically inlined into the calling query, so the optimizer treats it like hand-written SQL. Usually the fastest option, with no sandbox overhead.

Python / Java / Scala

Run in a secure sandbox on the warehouse nodes. Rows are sent to the handler in batches and results streamed back. Libraries come via PACKAGES (Anaconda channel for Python) or IMPORTS from a stage. Scalar Python UDFs call the handler once per row.

Vectorized Python UDFs

The handler receives a pandas DataFrame (a batch of rows) and returns a pandas Series or array. Far fewer Python calls and vectorised maths, often much faster for numeric work. Mark it with the @vectorized(input=pandas.DataFrame) decorator from _snowflake; batch size is chosen by Snowflake, with an optional upper bound (max_batch_size).

UDTF handlers

A Python UDTF is a class: optional __init__ (once per partition), process(self, …) called for each row and yields output rows, and optional end_partition(self) called after the last row of a partition, perfect for emitting totals or the final session. Java uses process / endPartition. With OVER (PARTITION BY … ORDER BY …) you control grouping and order.

Secure UDFs

CREATE SECURE FUNCTION hides the body from users who don't own it, and Snowflake disables some optimizations that could leak information about the underlying data. Use it for shared logic or logic that embeds sensitive rules. Cost: it can be slower, so don't make everything secure "just because".

External functions

Call a service outside Snowflake (e.g. through a cloud API gateway) via an API integration. Rows are batched into HTTPS requests. Useful for legacy integrations; for most new work Snowflake points you to external access instead. Calls add latency and generally prevent incremental DT refresh.

External access integrations

Let Python/Java UDFs and procedures reach specific external endpoints directly. You define a network rule (allowed hosts), optional secrets (API keys, OAuth), and an external access integration combining them, then attach it with EXTERNAL_ACCESS_INTEGRATIONS = (…) and SECRETS = (…). Check current docs for edition and cloud availability.

INTERVIEW TRAP
"My Python UDF is slow on 500 million rows, should I use a bigger warehouse?" First ask whether it needs to be Python at all. A SQL expression or SQL UDF is usually much faster. If it must be Python, make it vectorized, avoid per-row network calls, load models or lookup files once (module-level or cached), and only then consider a larger or Snowpark-optimized warehouse for memory-heavy work.
SENIOR ANGLE
UDFs inside dynamic tables: deterministic SQL UDFs are generally fine for incremental refresh; anything non-deterministic or calling out to external systems may force FULL refresh or block it. Mark Python UDFs IMMUTABLE only when they really are (same input → same output), since that is a promise to the engine.
CHAPTER 07

Transactions & concurrency · when two jobs write at once

01 · WHAT IS IT

A transaction is a group of statements that succeed or fail together. By default Snowflake runs in autocommit mode: every DML statement is its own transaction and commits when it finishes. An explicit transaction (BEGIN TRANSACTION … COMMIT / ROLLBACK) groups several statements.

Concurrency control decides what happens when two sessions touch the same table at the same time.

02 · WHY IT MATTERS
  • A transform that deletes yesterday's rows and inserts new ones must not leave dashboards showing zero in between.
  • Two tasks MERGEing into the same table at the same time will queue behind each other, and long explicit transactions can make other jobs wait or time out.
  • "Intermittent lock timeouts" is a classic production incident and a classic interview scenario.
03 · HOW IT WORKS · BACKEND
Readers never wait (MVCC)

Every commit creates a new table version (a new set of micro-partition pointers in cloud services metadata). A SELECT reads the latest committed version when it starts, so readers never block writers and writers never block readers. Isolation level for standard tables is READ COMMITTED.

Writers on the same table

UPDATE, DELETE and MERGE take locks that generally stop them running in parallel with other UPDATE/DELETE/MERGE on the same table; the second one waits. INSERT and COPY only add new micro-partitions, so they can usually run alongside other writes. (Hybrid tables use row-level locking, a different model.)

Locks last until commit

In autocommit, a lock is released when the statement ends. Inside an explicit transaction, locks are held until COMMIT or ROLLBACK, so slow work between the MERGE and the COMMIT keeps everyone else waiting. Waiting statements give up after LOCK_TIMEOUT (default 43,200 seconds = 12 hours), and there's a cap on how many statements may queue on one table's lock.

Implicit commits & tools

DDL (CREATE, ALTER, DROP…) commits any open transaction. Deadlocks are detected and one transaction is rolled back. Investigate with SHOW LOCKS, SHOW TRANSACTIONS, Query History (the "blocked" time), and end a stuck one with SELECT SYSTEM$ABORT_TRANSACTION(<id>).

INTERVIEW TRAP
"Snowflake has no locking because it's MVCC." Half right: reads never lock, but writes to the same table do coordinate. Two MERGE tasks on one table run one after the other, and a long explicit transaction can make others wait for a long time. That's why intermittent "lock wait timeout" failures appear when schedules start to overlap as data grows.
SENIOR ANGLE
Design for one writer per table (or per table per time window). Fan-in many sources into a staging table with INSERT/COPY (those can run concurrently), then have one MERGE task apply it. Keep explicit transactions short: do validation and heavy SELECTs before BEGIN TRANSACTION, and only the final writes inside it.
