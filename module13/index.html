MODULE 13 · DATA MODELING & TOOLING

Shape the data.
Ship it safely.|

The previous modules taught you how Snowflake stores, loads, secures and queries data. This module is about the two things that decide whether a warehouse stays useful after year one: how you shape the tables (star schemas, Data Vault, layers, keys) and how you build and release changes (dbt, Airflow, schemachange, Git, clones and SWAP).

01 · WHAT IS IT

Data modeling means deciding which tables exist, what one row in each table means, and how tables connect. It's the blueprint of the warehouse. Tooling is the machinery that turns that blueprint into real objects, tests them and deploys them repeatably: dbt for SQL transformations, an orchestrator for scheduling, and CI/CD for safe releases.

02 · WHY IT STILL MATTERS IN A COLUMNAR CLOUD WAREHOUSE

A common fresher myth: "Snowflake is fast and storage is cheap, so just dump everything into one wide table." Speed fixes slow queries, not wrong answers. Without a model you get double-counted revenue (wrong grain), five different definitions of "active customer", and history that silently disappears when a source overwrites a row.

  • Correctness: the grain and keys decide whether SUMs are right.
  • Usability: analysts and BI tools understand a star schema immediately.
  • Cost: a clear model means fewer giant ad-hoc joins and less rework.
  • Change: sources change constantly; a good model absorbs it.
03 · HOW SNOWFLAKE CHANGES THE OLD RULES
Joins are cheaper

Columnar storage reads only the columns a query touches, and micro-partition pruning skips most of a big fact table. A few joins to small dimensions are rarely the bottleneck, so star schemas stay a good default.

Wide tables are fine too

Because unused columns cost nothing to scan, a denormalized "one big table" for a single dashboard is acceptable as a final serving layer, built on top of a proper model, not instead of it.

Constraints don't protect you

Snowflake doesn't enforce primary or foreign keys on standard tables (chapter 05). The model, your dbt tests and your MERGE logic are what keep data clean.

Five analogies to carry through the module:

STAR SCHEMA
A shop receipt

Each receipt line is a fact (what was sold, how much). The product catalog, customer card and calendar are the dimensions that describe it.

DATA VAULT
LEGO bricks

Hubs are the studs (business keys), links are connectors, satellites are the coloured pieces that change. You only ever add bricks.

MEDALLION
A water plant

Raw river water (bronze), filtered and treated (silver), bottled and labelled for drinking (gold).

DBT
A recipe book

Each model is a recipe that names its ingredients with ref(). dbt works out the cooking order and tastes every dish (tests).

BLUE / GREEN
A stage set change

Build the new set behind the curtain (a clone), then swap it in one move. If it looks wrong, swap back.

CHAPTER 01

Dimensional modeling · facts, dimensions and grain

01 · WHAT IS IT

Dimensional modeling (Ralph Kimball's method) splits data into two kinds of tables:

  • Fact tables record business events or measurements: a sale, a payment, a shipment, a daily balance. They hold numeric measures (amount, quantity) plus foreign keys to dimensions. They are long and narrow, and grow every day.
  • Dimension tables hold the descriptive context, the "who, what, where, when": customer, product, store, date. They are short and wide, with many text attributes used for filtering and grouping.

Arrange one fact in the middle with dimensions around it and you get a star schema.

02 · WHY WE USE IT
  • Easy to understand: business users read it as "sales by product by month".
  • Predictable SQL: every question is fact JOIN dimensions, GROUP BY attributes. BI tools (Power BI, Tableau, Looker) are built around this shape.
  • Consistent numbers: shared (conformed) dimensions mean "customer" means the same thing in sales, returns and support facts.
  • Performs well in Snowflake: big fact pruned by date, small dimensions easily broadcast to every node during a join.
03 · HOW IT WORKS · THE FOUR-STEP DESIGN
1 · Pick the process

One business process per fact: orders, shipments, inventory. Not "the sales department".

2 · Declare the grain

Say exactly what one row means, e.g. "one row per order line". This is the most important decision.

3 · Choose dimensions

Everything that is true at that grain: date, customer, product, store, promotion.

4 · Choose facts

Numeric measures true at that grain: quantity, net amount, discount.

Dimensions get a surrogate key (a meaningless integer or hash like customer_sk) instead of the source system's ID. That lets you keep history (several rows for the same customer, chapter 02), combine sources whose IDs clash, and add an "Unknown" member (key -1) so facts with missing data still join.

The vocabulary interviewers expect

Grain

The exact meaning of one fact row. Mixing grains (order header totals next to order line amounts) is the #1 cause of double-counting.

Conformed dimension

One dimension shared by several facts with the same keys and attribute values (e.g. dim_date, dim_customer), so you can compare sales vs returns side by side. Kimball calls the matrix of facts × conformed dims the bus matrix.

Star vs snowflake schema

Star: each dimension is one flattened table (category name repeated per product). Snowflake: dimensions normalized into sub-tables (product → category → department). Star is simpler and usually faster for BI; snowflaking saves little in a columnar store.

Degenerate dimension

A dimension key with no dimension table, stored directly in the fact: order_number, invoice_no. Useful for grouping lines of one order.

Junk dimension

Combines several small low-cardinality flags (is_gift, payment_type, channel) into one table of all combinations, so the fact carries one key instead of five flag columns.

Bridge table

Resolves many-to-many: one bank account with several holders, one patient with several diagnoses. The bridge lists the pairs (with an optional allocation weight) so you don't double count.

INTERVIEW TRAP
"Revenue doubled after we added the shipments table to the join." That's a fan-out: joining two facts of different grain (or a fact to a many-to-many without a bridge) repeats rows. Fix: aggregate each fact to a common grain first, then join on conformed dimensions ("drill across").
SENIOR ANGLE
In Snowflake, cluster big facts by date (or let natural load order do it) so date filters prune micro-partitions; keep dimensions small enough to be broadcast. Prefer integer or binary surrogate keys over long strings on very large facts, and keep a dim_date table rather than calling date functions in every report.
CHAPTER 02

Slowly changing dimensions · recap

01 · WHAT IS IT

Dimension attributes change slowly: a customer moves city, a product changes category. An SCD type is the rule for what happens to the old value.

02 · WHY IT MATTERS

If you overwrite a customer's city, last year's sales suddenly appear under the new city. Sometimes that's what the business wants, often it's not. You must choose per attribute.

03 · HOW EACH TYPE WORKS
TYPEWHAT HAPPENS ON CHANGEHISTORY?TYPICAL USE

Type 2 is the one interviews focus on. The full SCD2 MERGE pattern with streams (and the dbt snapshot equivalent) is built step by step in Module 05 · Dynamic tables & transforms; in this module we'll see dbt snapshots in chapter 06.

INTERVIEW TRAP
"With Type 2, which key does the fact table store?" The surrogate key of the dimension row that was current when the event happened, looked up by business key and event date between valid_from and valid_to. Joining on the business key instead returns every historical version and multiplies rows.
CHAPTER 03

Data Vault 2.0 · hubs, links and satellites

01 · WHAT IS IT

Data Vault (Dan Linstedt) is a modeling method for the integration layer of an enterprise warehouse. It splits every source entity into three kinds of table:

  • Hub: the list of unique business keys (customer number, order number). One row per key, ever.
  • Link: a relationship between hubs (customer placed order). One row per unique combination.
  • Satellite: the descriptive attributes and their history (name, city, amount), hanging off a hub or a link. A new row only when something changes.

Every row carries a hash key, a load date and a record source.

02 · WHY WE USE IT
  • Many changing sources: adding a new source system means adding satellites, not redesigning tables.
  • Full auditability: insert-only, every version kept with where and when it came from (finance, insurance, regulated industries).
  • Parallel loading: hash keys are calculated from the business key itself, so hubs, links and satellites load at the same time with no lookups.
  • Raw history first, business rules later: you store what the source said, then apply interpretation in a separate layer.
03 · HOW IT WORKS
Hash keys

MD5(UPPER(TRIM(business_key))) (or SHA-1/SHA-2) gives a fixed-length, deterministic key. Any loader in any system computes the same key for "C-1001", so no sequence lookup is needed. In Snowflake, MD5_BINARY stores 16 bytes instead of a 32-char string.

Hashdiff

A hash of all the satellite's descriptive columns. Compare the incoming hashdiff with the latest stored one: equal means "no change, insert nothing"; different means "insert a new satellite row".

Raw vs business vault

Raw vault: hubs/links/sats exactly as the sources delivered (no business rules). Business vault: derived satellites, computed attributes, de-duplication and rules. Information marts (often star schemas) are built on top.

PIT (point-in-time) tables store, for each hub key and snapshot date, which satellite row was valid in each satellite, so queries do simple equi-joins instead of complex "latest row before date" logic. Bridge tables pre-join hubs and links along a common path for faster mart queries. Both are query helpers, not sources of truth.

INTERVIEW TRAP
"Why not just use Snowflake's HASH() function for hash keys?" HASH() returns a 64-bit integer and is not meant as a collision-resistant key; it can also differ from other tools. Data Vault uses standard MD5 or SHA on normalized input (trimmed, upper-cased, consistent delimiter and null handling) so every loader produces identical keys.
SENIOR ANGLE
Data Vault suits Snowflake well: insert-only loads are cheap (no updates rewriting micro-partitions), multi-table INSERT (INSERT ALL) can feed hub, link and satellites from one staging scan, and the many joins are handled by PIT tables or dynamic tables that flatten the vault into marts. Don't use it for a small team with two sources: it's heavy.
CHAPTER 04

Medallion architecture · bronze, silver, gold in Snowflake

01 · WHAT IS IT

A layered architecture moves data through stages of increasing quality. The "medallion" names come from the lakehouse world; dbt projects call the same idea raw / staging / marts.

  • Bronze (raw): data exactly as it arrived, often VARIANT JSON, plus load metadata.
  • Silver (staging / integration): cleaned, typed, de-duplicated, conformed. Data Vault often lives here.
  • Gold (marts): business-ready star schemas and aggregates for BI, ML and sharing.
02 · WHY WE USE IT
  • Replay: bronze keeps the original, so a bug in silver logic can be fixed and rebuilt without re-ingesting.
  • Separation of concerns: ingestion engineers own bronze, analytics engineers own gold.
  • Security: analysts get access to gold only; raw PII stays locked in bronze.
  • Cost control: different retention and table types per layer.

Environment strategy: dev / test / prod with zero-copy clones

Every team needs places to build and test without touching production. In Snowflake the usual pattern is one database per layer per environment (PROD_RAW, PROD_ANALYTICS, DEV_ANALYTICS…) or one database per environment with a schema per layer. Test environments are created with zero-copy clones: the clone shares prod's micro-partitions and only pays storage for data it changes.

Naming conventions that scale

Databases: <ENV>_<LAYER> (PROD_RAW, DEV_MARTS). Schemas by source or domain (RAW.SHOPIFY, MARTS.FINANCE). Tables by role: stg_, int_, dim_, fct_, agg_. Warehouses by workload (LOAD_WH, TRANSFORM_WH, BI_WH). Roles per layer and access level. Consistency makes RBAC grants and monitoring scripts simple.

Dynamic tables as the layer glue

Silver and gold can be dynamic tables: a SELECT plus a TARGET_LAG, and Snowflake refreshes them incrementally where possible (Module 05). Use TARGET_LAG = DOWNSTREAM on intermediate layers so they refresh only when a gold table needs them.

INTERVIEW TRAP
"Is a clone free forever?" No. It's free at creation. As soon as either the clone or the source changes micro-partitions, the changed partitions are stored separately. A long-lived dev clone of a busy prod table slowly becomes a full copy. Also remember that named internal stages are not cloned with a database, and clones keep child-object grants but not the grants on the cloned container itself (check docs for the exact rules).
SENIOR ANGLE
Put staging and scratch layers in transient databases/schemas: no Fail-safe (7 days of extra storage avoided) and Time Travel of at most 1 day. Keep bronze permanent if it is your only copy of the source, since replay depends on it. Gold usually stays permanent with a longer Time Travel window for "who broke the dashboard yesterday" recovery.
CHAPTER 05

Keys & constraints · what Snowflake does and doesn't enforce

01 · WHAT IS IT

Snowflake lets you declare PRIMARY KEY, UNIQUE, FOREIGN KEY and NOT NULL. On standard tables, only NOT NULL is enforced. PK, UNIQUE and FK are informational: stored in metadata, shown in SHOW PRIMARY KEYS and used by BI and modeling tools, but a duplicate primary key insert succeeds.

Hybrid tables (Unistore, for transactional workloads) are different: they require a primary key and enforce PK, UNIQUE and FK constraints. Check current docs for their availability and limits in your region.

02 · WHY DECLARE THEM ANYWAY
  • Documentation: anyone reading the DDL knows the grain and relationships.
  • Tools: BI tools, ER diagram tools and some semantic layers read the constraints to suggest joins.
  • Optimizer (with RELY): setting the RELY property tells Snowflake it may trust the constraint, which can enable optimizations such as eliminating an unnecessary join. Only use it when your pipeline guarantees the data honours the constraint, otherwise results can be wrong.

INTERVIEW TRAP
"I put a PRIMARY KEY on the table, so it can't have duplicates, right?" Wrong in Snowflake (for standard tables). Your MERGE logic, a QUALIFY ROW_NUMBER() ... = 1 de-dup step, and a dbt unique test are what guarantee uniqueness. Also: a MERGE whose source has duplicate keys can fail with a nondeterministic-merge error or update the target ambiguously; de-dup the source first.
SENIOR ANGLE
Declare constraints anyway, add RELY only where tests prove it, and pick surrogate keys by need: integer sequences for classic Kimball dims in a single pipeline; hash keys when loads run in parallel, must be re-runnable, or merge several sources (and dbt's generate_surrogate_key macro produces exactly that).
CHAPTER 06

dbt with Snowflake · SQL transformations as software

01 · WHAT IS IT

dbt (data build tool) lets you write each transformation as a SELECT statement in a .sql file (a model). dbt wraps it in the right DDL/DML (CREATE VIEW, CREATE TABLE AS, MERGE…), runs everything in dependency order on Snowflake, and tests the results. It's the "T" in ELT: data is already loaded into Snowflake, and all compute runs on your Snowflake warehouse.

Available as open-source dbt Core (CLI), the managed dbt Cloud service, and Snowflake also offers running dbt projects natively inside Snowflake (a newer feature; check current docs).

02 · WHY TEAMS USE IT
  • Dependency graph for free: {{ ref('stg_orders') }} both resolves the table name and records the dependency.
  • Environments: the same code builds into DEV or PROD schemas depending on the target.
  • Tests and docs live next to the SQL, in version control.
  • Reuse: Jinja macros and packages (dbt_utils) remove copy-paste.
  • Software practices: pull requests, code review, CI.
03 · HOW IT WORKS
1 · Parse

dbt reads every model, finds the ref() and source() calls and builds a DAG (saved in manifest.json).

2 · Compile

Jinja is rendered: ref('stg_orders') becomes analytics.staging.stg_orders for the current target.

3 · Materialize

The SELECT is wrapped in DDL/DML for its materialization and sent to Snowflake. Independent models run in parallel threads.

4 · Test

Each test compiles to a query that returns failing rows. Zero rows = pass.

The other building blocks

Sources

Declared in YAML (sources.yml) with database, schema and tables; referenced with {{ source('raw','orders') }}. Adds lineage and freshness checks (loaded_at_field, warn/error after N hours).

Snapshots (SCD2)

dbt compares the source to the snapshot table each run (strategy timestamp on an updated_at column, or check on listed columns) and adds dbt_valid_from / dbt_valid_to rows. History you can't recreate later, so run it on a schedule.

Tests

Generic tests in YAML: unique, not_null, accepted_values, relationships (FK check). Singular tests are .sql files returning bad rows. Packages add more (dbt_utils, dbt_expectations).

Seeds

Small CSV files in the repo loaded with dbt seed: country codes, mapping tables. Not for big data.

Macros & Jinja

Reusable Jinja functions: {% macro cents_to_dollars(col) %}. Jinja gives loops, ifs and variables, e.g. {% if is_incremental() %} and {{ this }} (the current model's table).

Commands

dbt run (models), dbt test, dbt snapshot, dbt seed, and dbt build which does all of them in DAG order, testing each node before its children run.

INTERVIEW TRAP
"An incremental model missed late-arriving rows." The filter WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }}) skips rows that arrive late with older timestamps. Use a lookback window (e.g. minus 3 days) together with the merge strategy and a unique_key so reprocessed rows update instead of duplicating, and schedule periodic --full-refresh if needed.
SENIOR ANGLE
Snowflake-specific dbt configs worth naming: transient (dbt-snowflake creates table models as transient by default; set transient: false for tables needing Fail-safe), cluster_by, snowflake_warehouse (per-model warehouse), copy_grants, query_tag for cost attribution, and merge_update_columns to limit what a merge updates.
CHAPTER 07

Orchestration & CI/CD · run it on time, release it safely

01 · WHAT IS IT

Orchestration decides when and in what order jobs run, and what happens when one fails. CI/CD (continuous integration / delivery) decides how code changes reach production: every change goes through Git, automated tests on a safe copy, and a repeatable deployment.

02 · WHY IT MATTERS

Without it, people run DDL by hand in prod worksheets, nobody knows which version of a table is live, and a broken model is discovered by the CFO's dashboard. With it, every change is reviewed, tested against real-shaped data, and can be rolled back.

03 · HOW · THE TOOLS AND WHERE THEY FIT
Airflow

Python DAGs that orchestrate across systems: wait for an S3 file, run Snowflake SQL, trigger dbt, call an API, notify Slack. The apache-airflow-providers-snowflake package provides the connection and operators (the classic SnowflakeOperator; newer versions steer you to the generic SQLExecuteQueryOperator, and a SQL API operator exists too).

Snowflake tasks

Native scheduler (Module 02): great when everything happens inside Snowflake. Choose an external orchestrator when the pipeline spans other systems, needs rich retries/backfills/SLAs, or the company already standardised on one.

Git integration

A GIT REPOSITORY object (via an API integration) mirrors a remote repo inside Snowflake. You FETCH it and run files directly: EXECUTE IMMEDIATE FROM @repo/branches/main/deploy.sql.

schemachange

An open-source Python tool for database migrations. Versioned scripts V1.2.0__add_col.sql run once, in version order. Repeatable scripts R__views.sql re-run whenever their checksum changes. Always scripts A__grants.sql run every deploy. Applied scripts are recorded in a change-history table.

Terraform

Infrastructure as code for account objects: warehouses, databases, roles, grants, users, integrations, via the Snowflake Terraform provider (now maintained under Snowflake's GitHub organisation). Usually for platform objects, while dbt/schemachange manage tables and views.

Snowflake CLI

The snow command: run SQL (snow sql -f), manage connections, deploy Streamlit apps, Snowpark code and Native Apps, work with Git repository objects. Easy to call from GitHub Actions or Jenkins.

Blue/green deployment with clone + SWAP

-- 1. build the new version next to prod CREATE OR REPLACE DATABASE analytics_green CLONE analytics; -- 2. run migrations + dbt build against analytics_green -- 3. validate (tests, row counts, reconciliation) -- 4. atomic name exchange ALTER DATABASE analytics SWAP WITH analytics_green; -- 5. rollback = swap again; later drop the old copy ALTER DATABASE analytics SWAP WITH analytics_green;
Why it works

SWAP WITH exchanges the names of two databases (or schemas, or tables) in a single metadata operation, so consumers querying analytics.marts.fct_sales see the old version until the instant of the swap and the new one right after. No data moves. Things to check: queries using fully-qualified names follow the name, grants travel with the object (not the name), and stages, pipes and tasks inside need care when cloned.

INTERVIEW TRAP
"How do you test a pipeline change on production data without risking production?" Not by running it in prod "carefully". Zero-copy clone prod into a CI database (seconds, almost no storage), run migrations and dbt build there, run tests, then drop the clone. For PII, clone into a schema where masking policies apply, or use a masked/sampled copy.
SENIOR ANGLE
Slim CI: dbt build --select state:modified+ --defer --state prod_artifacts/ builds only changed models and their children, reading unchanged parents from prod. It keeps CI fast and cheap on large projects. Tag queries (QUERY_TAG) per pipeline so CI spend is visible in cost reports.
