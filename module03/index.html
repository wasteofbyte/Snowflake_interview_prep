MODULE 03 · PERFORMANCE TUNING

Make it fast.
Know why it was slow.|

Module 1 showed how Snowflake is built: micro-partitions, warehouses, three cache layers. This module turns that knowledge into a skill interviewers test hard at the senior level: looking at a slow query and explaining, with evidence, what to change. You'll learn to read the Query Profile, choose between clustering, Search Optimization, Query Acceleration and materialized views, spot SQL anti-patterns, and walk through a real "dashboard got slow" investigation.

Think of performance tuning like a doctor's visit. A good doctor never prescribes before examining. Four steps, every time:

1 · MEASURE
Take the vitals

Get the facts: elapsed time, queued time, bytes scanned, partitions scanned, spill. From QUERY_HISTORY and the Query Profile, not from "it feels slow".

2 · FIND THE BOTTLENECK
Locate the pain

Which operator eats most of the time? Is the query waiting in a queue, scanning too much, spilling, or joining badly? One cause usually dominates.

3 · FIX THE CAUSE
Treat the disease

A bigger warehouse is a painkiller. Rewriting a filter, fixing a join key or adding a clustering key is the cure. Pick the cheapest fix that removes the cause.

4 · RE-MEASURE
Check the patient

Run it again, compare the same numbers. If nothing moved, your guess was wrong, so go back to step 2. Also check what the fix costs per month.

01 · WHAT IS IT

Performance tuning means making queries finish faster, or with fewer credits, or both, by removing the thing that is slowing them down. In Snowflake there are no indexes to build, no vacuum to run and no partitions to manage by hand. Instead you control how much data a query has to touch and how much compute it gets.

02 · WHY IT MATTERS

Every second a warehouse runs costs credits, and slow dashboards cost people's time. A 6-year Snowflake developer is expected to explain why a query is slow from its profile, and to know when a feature like clustering or Search Optimization is worth its ongoing serverless cost, and when it's just burning money.

03 · HOW IT WORKS · THE FIVE LEVERS

Almost every Snowflake performance problem, and every fix, maps to one of five levers you met in Module 1:

PRUNINGSkip micro-partitions using min/max metadata. Fixes: sargable filters, clustering keys, Search Optimization.
MEMORYJoins, sorts and aggregations need RAM; overflow spills to local SSD, then to remote storage. Fixes: bigger warehouse, less data, better joins.
PARALLELISMMore nodes scan more partitions at once. Fixes: warehouse size, Query Acceleration for outliers.
CONCURRENCYToo many queries at once → they wait in a queue. Fixes: multi-cluster warehouses, separate warehouses per workload.
CACHINGResult cache (cloud services), local disk cache (warehouse SSD), metadata. Fixes: stable query text, don't suspend hot warehouses too eagerly, MVs.
ANALOGY
A query is a librarian fetching books. Pruning = knowing which shelves to skip. Memory = the size of the desk to spread books on. Parallelism = how many assistants you send. Concurrency = how many people are queuing at the counter. Caching = remembering the answer you gave five minutes ago.
CHAPTER 01

Reading the Query Profile · the X-ray of a query

01 · WHAT IS IT

The Query Profile (in Snowsight: Query History → pick a query → Query Profile tab) is a visual execution plan with real runtime numbers. It's a tree of operators; data flows from the bottom (table scans) up to the top (Result).

  • TableScan: reads micro-partitions of a table. Filter: drops rows. Join: combines two inputs. Aggregate: GROUP BY. Sort / SortWithLimit: ORDER BY. WindowFunction, Flatten, UnionAll, Result.
  • Each node shows its % of total execution time, and the arrows show row counts flowing between nodes.

The same numbers are available in SQL through GET_QUERY_OPERATOR_STATS(query_id).

02 · WHY WE USE IT

It turns "the query is slow" into a specific, provable cause. Without it you guess: resize the warehouse, add a clustering key, hope. With it you can say: "95% of time is the TableScan on SALES, it read 48,000 of 48,300 partitions because the filter wraps the date column in a function". That sentence is what interviewers want to hear.

The panel on the right of the profile lists the most expensive nodes, so you always start where the time actually goes.

Where does the elapsed time go?

Queued

QUEUED_OVERLOAD_TIME: warehouse busy with other queries. QUEUED_PROVISIONING_TIME: waiting for the warehouse to start or resize. QUEUED_REPAIR_TIME: replacing a failed node (rare).

Compilation

Cloud services parses, optimizes and prunes using metadata. Huge IN-lists, very deep views or thousands of UNIONed branches make this large. COMPILATION_TIME in QUERY_HISTORY.

Execution

The warehouse actually runs the operator tree. EXECUTION_TIME. This is the part the Query Profile breaks down per operator.

INTERVIEW TRAP
"The profile shows only 5 seconds of execution, but the user waited 4 minutes." The profile only covers execution. Look at queued time in the query details or QUERY_HISTORY. Resizing the warehouse won't help a queue; more clusters (multi-cluster) or a separate warehouse will.
SENIOR ANGLE
Don't tune one query in isolation. Pull the top 20 queries by total elapsed time (or by credits) from ACCOUNT_USAGE.QUERY_HISTORY, grouped by QUERY_PARAMETERIZED_HASH so repeated queries with different literals count as one. Fixing the query that runs 5,000 times a day beats fixing the one that runs once a month.
CHAPTER 02

Clustering keys · & automatic clustering

01 · WHAT IS IT

Every table is stored as micro-partitions (roughly 50–500 MB of uncompressed data each). For every column, Snowflake keeps the min and max value per partition. A filter like WHERE order_date = '2024-03-15' can skip every partition whose range doesn't include that date. This is pruning.

By default, data is stored in the order it was loaded: its natural ordering. A clustering key (ALTER TABLE … CLUSTER BY (…)) tells Snowflake to keep rows with similar key values together, so partition ranges stay narrow.

02 · WHY WE USE IT

If you load data daily, it's naturally ordered by load date, and date filters prune well for free. But after years of updates, deletes, late-arriving data or loads in a different order, ranges get wide and overlapping: every partition covers "January to December", and nothing can be skipped.

A clustering key restores narrow ranges for the column you filter on most, so big queries read a few hundred partitions instead of tens of thousands.

03 · HOW IT WORKS · DEPTH, OVERLAP & THE BACKGROUND SERVICE
  • Overlap: how many other partitions share a part of a partition's value range. Depth: for a given value, how many partitions contain it. The best possible depth is 1 (only one partition holds each value). Lower = better pruning.
  • SYSTEM$CLUSTERING_INFORMATION('sales', '(order_date)') returns JSON: total_partition_count, total_constant_partition_count, average_overlaps, average_depth and a partition_depth_histogram. SYSTEM$CLUSTERING_DEPTH returns just the average depth.
  • Automatic Clustering is a serverless background service. Once a key is defined, Snowflake watches how "clustered" the table is and, when it's worth it, rewrites overlapping partitions into new, better-sorted ones. You don't need a warehouse; you pay serverless credits, visible in AUTOMATIC_CLUSTERING_HISTORY.
  • Rewritten partitions are new partitions. The old ones stay around for Time Travel and Fail-safe, so heavy reclustering also increases storage for a while.
  • You can pause it with ALTER TABLE … SUSPEND RECLUSTER and restart with RESUME RECLUSTER.

Choosing a clustering key · try it

KEY CHOOSER · 5 TB EVENTS table, most queries filter on a date range and often on tenant
Good candidates

Large tables (Snowflake's guidance: typically multi-terabyte), columns used most often in selective filters or join predicates, with enough distinct values to prune but not so many that maintenance is expensive. Use expressions to lower cardinality: TO_DATE(ts), DATE_TRUNC('month', ts), SUBSTRING(code, 1, 3). Keep it to 3–4 columns at most, ordered from lower to higher cardinality.

When NOT to cluster

Small tables (a few GB: they're already few partitions). Tables that are constantly updated everywhere (high churn), because Snowflake keeps reclustering and the credits never stop. Tables whose natural load order already matches the filter. Tables queried in many unrelated ways where no single key helps most queries.

INTERVIEW TRAP
"Is a clustering key an index?" No. There's no separate structure to look up. It only changes how rows are physically grouped into micro-partitions so min/max pruning works better. It helps range and equality filters on the key; it does nothing for a filter on an unrelated column.
SENIOR ANGLE
Before adding a key, prove it: (1) check the queries really filter on that column (ACCESS_HISTORY / query text), (2) look at SYSTEM$CLUSTERING_INFORMATION and partitions scanned today, (3) test on a clone sorted with CREATE TABLE … AS SELECT … ORDER BY key to see the pruning you'd get, (4) watch AUTOMATIC_CLUSTERING_HISTORY for the first weeks. If the ongoing credits exceed the warehouse time you save, remove it.
CHAPTER 03

Search Optimization Service · needle-in-a-haystack queries

01 · WHAT IS IT

The Search Optimization Service (SOS) is a table-level feature (Enterprise Edition and higher) that builds and maintains a persistent data structure called a search access path. Think of it as a compact map that records, for chosen columns, which micro-partitions might contain which values.

It speeds up highly selective queries, the ones that return a few rows out of billions:

  • Equality and IN: WHERE order_id = 'ORD-88123', WHERE email IN (…)
  • Substring and regex: LIKE '%timeout%', ILIKE, RLIKE, REGEXP_LIKE
  • Fields inside VARIANT: WHERE payload:customer.email::STRING = '…'
  • Geospatial: ST_INTERSECTS, ST_CONTAINS, ST_DWITHIN on GEOGRAPHY columns
02 · WHY WE USE IT

Clustering can make only one ordering great. If a table is clustered by date, a lookup on customer_id or a text search in a log message still scans everything, because those values are spread across all partitions.

SOS adds pruning for many columns at once, independent of the physical order. It shines for point lookups from apps and APIs, investigation queries on logs ("find all events for this user"), and security analytics.

03 · HOW IT WORKS · BACKEND
  • You enable it: ALTER TABLE events ADD SEARCH OPTIMIZATION ON EQUALITY(user_id), SUBSTRING(message); (or for the whole table with just ADD SEARCH OPTIMIZATION, which covers eligible columns for equality).
  • A serverless service builds the search access path in the background (it can take a while on big tables). DESCRIBE SEARCH OPTIMIZATION ON events and SHOW TABLES (search_optimization_progress) show its status.
  • At query time, during compilation, the optimizer consults the access path to prune partitions that definitely don't contain the value, on top of normal min/max pruning. The Query Profile then shows a Search Optimization Access node.
  • Every insert, update or delete makes Snowflake maintain the access path, again with serverless credits.
  • Costs: (1) storage for the access path (can be a meaningful fraction of the table size), (2) serverless compute to build it, (3) ongoing maintenance compute proportional to churn. Estimate first with SYSTEM$ESTIMATE_SEARCH_OPTIMIZATION_COSTS; track with SEARCH_OPTIMIZATION_HISTORY.

INTERVIEW TRAP
"We enabled Search Optimization and the dashboard didn't get faster." SOS only helps selective predicates. A query returning 30% of the table, or one that aggregates everything, still scans almost everything. Also check that the predicate type was enabled (an EQUALITY path does nothing for LIKE '%x%'; that needs SUBSTRING).
SENIOR ANGLE
Enable SOS per column and per method (ON EQUALITY(user_id), SUBSTRING(message)) instead of the whole table: smaller access path, lower maintenance. And combine features: cluster the log table by TO_DATE(event_ts) for time-window queries and add SOS on user_id for investigations.
CHAPTER 04

Query Acceleration Service · borrow extra muscle for outliers

01 · WHAT IS IT

The Query Acceleration Service (QAS) is a warehouse setting (Enterprise Edition and higher). When a query on that warehouse is eligible, Snowflake offloads parts of its work, mainly scanning and filtering lots of partitions (and some partial aggregation), to shared serverless compute, then hands the reduced results back to your warehouse to finish.

ALTER WAREHOUSE bi_wh SET
  ENABLE_QUERY_ACCELERATION = TRUE
  QUERY_ACCELERATION_MAX_SCALE_FACTOR = 8;
02 · WHY WE USE IT

Picture a MEDIUM warehouse serving dashboards fine all day, until an analyst runs an ad-hoc query that scans 3 TB. That one outlier hogs the warehouse, other queries queue, and you're tempted to make the warehouse XLARGE for everyone, all day.

QAS gives that outlier extra compute only while it runs, so you can keep the warehouse sized for the normal workload.

03 · HOW IT WORKS · BACKEND
  • Eligibility is decided by Snowflake per query. Typical eligible queries: large scans with selective filters or aggregations that reduce data a lot, including some INSERT/CTAS/COPY workloads. Typically not eligible: too few partitions to be worth it, or filters that don't reduce the data much.
  • QUERY_ACCELERATION_MAX_SCALE_FACTOR caps the extra compute as a multiple of the warehouse size. Default is 8; 0 means no upper limit. A MEDIUM (4 credits/hour) with factor 8 can lease up to 32 credits/hour of acceleration compute.
  • SYSTEM$ESTIMATE_QUERY_ACCELERATION('<query_id>') tells you whether a past query was eligible and its estimated time at different scale factors. ACCOUNT_USAGE.QUERY_ACCELERATION_ELIGIBLE lists eligible queries across the account.
  • Billing is serverless, per second of acceleration compute used, visible in QUERY_ACCELERATION_HISTORY. The Query Profile shows the accelerated scan (partitions scanned by the service).

INTERVIEW TRAP
"QAS vs a bigger warehouse vs multi-cluster?" Bigger warehouse: every query gets more memory and CPU, all the time (fixes spilling). Multi-cluster: more copies of the same size (fixes queuing from many concurrent queries). QAS: extra scan power only for eligible outlier queries. It does not fix spilling in a join or sort that happens on the warehouse.
SENIOR ANGLE
Find candidates with data, not hope: query QUERY_ACCELERATION_ELIGIBLE grouped by warehouse, ordered by eligible_query_acceleration_time. Enable QAS on the warehouses with the most eligible time, start with a modest scale factor, and compare QUERY_ACCELERATION_HISTORY credits against the warehouse credits you saved by not upsizing.
CHAPTER 05

Materialized views vs dynamic tables vs result cache · precompute or reuse

01 · WHAT IS IT

Three ways to avoid recomputing the same answer:

  • Materialized view (MV): a view whose result is stored and kept up to date automatically by Snowflake. Enterprise Edition and higher.
  • Dynamic table (DT): a table defined by a query plus a TARGET_LAG ("at most 15 minutes behind"); Snowflake refreshes it, incrementally when it can. Deep dive in Module 05.
  • Result cache: cloud services remembers the result of a query for 24 hours and returns it instantly if the exact same query runs again and the data hasn't changed.
02 · WHY WE USE IT

If 200 dashboard users run "daily revenue by region" over a 5-billion-row table, scanning those rows 200 times is waste. Precomputing once and reading a tiny result is faster and cheaper.

Each tool trades something: MVs are always current but very restricted; DTs are flexible but lag; the result cache is free but fragile (any data change or text change misses).

03 · HOW IT WORKS · BACKEND
MV maintenance & rewrite

A serverless background service updates the MV after base-table DML (billed; see MATERIALIZED_VIEW_REFRESH_HISTORY). If the MV is momentarily behind, Snowflake combines the MV with the newest base-table changes, so results are always current. The optimizer can also rewrite a query on the base table to use the MV automatically.

MV restrictions

One table only: no joins (not even self-joins). No window functions, HAVING, ORDER BY, LIMIT, UDFs or non-deterministic functions like CURRENT_TIMESTAMP; only a subset of aggregates (SUM, COUNT, MIN, MAX, AVG…). It can't select from another view or MV. Check the docs for the full current list.

Result cache rules

Kept 24 hours, and each reuse extends it (up to 31 days from the first run). Hit only if the query text matches, the data is unchanged, no non-deterministic functions, and your role can read the tables. No warehouse needed on a hit. Controlled by USE_CACHED_RESULT (default TRUE).

"Why not create an MV for every slow query?" Each MV costs storage + serverless maintenance every time the base table changes. CHAPTER 06

Joins & SQL anti-patterns · the cheapest fix is often the SQL

01 · WHAT IS IT

A join combines rows from two inputs on a condition. Inside a multi-node warehouse, the optimizer must decide how to bring matching rows onto the same node:

  • Broadcast: the small side (the build side, e.g. a dimension) is copied to every node; each node then joins its share of the big side (the probe side) locally. Cheap when one side is small.
  • Hash-partitioned: both sides are redistributed by a hash of the join key, so equal keys land on the same node. Used when both sides are large.

An anti-pattern is a SQL habit that works but forces Snowflake to do far more work than needed.

02 · WHY IT MATTERS

Most "Snowflake is slow" tickets are not Snowflake problems. They're a function wrapped around a filter column, a join on a non-unique key, or a DISTINCT hiding duplicates. Rewriting the SQL costs nothing per month; a bigger warehouse costs every hour it runs.

03 · HOW IT WORKS · JOINS IN THE BACKEND

Snowflake's optimizer picks the join order and distribution from table statistics; you don't write hints. It builds a hash table from the build side, then streams the probe side through it. It can also push a join filter (shown as JoinFilter in the profile) built from the build side's keys down to the probe-side scan, so partitions and rows that can't match are skipped early. Your job is to give it good inputs: unique keys where you expect them, filters before joins, and the columns you actually need.

INTERVIEW TRAP
"I added DISTINCT and the duplicates went away, so it's fixed." No: the join still produced millions of extra rows, and now Snowflake also has to aggregate all of them to remove duplicates. Find out why a key is duplicated (SCD2 history rows, a missing join column, bad source data) and fix the join.

  
SENIOR ANGLE
Make these checks part of code review: filter columns used raw (sargable), explicit column lists, UNION ALL unless dedup is required, uniqueness test on every dimension key, no ORDER BY in views or subqueries, and a look at the Query Profile for any new query that will run on a schedule.






  
CHAPTER 07

  
Warehouse tuning & a full debugging walkthrough · size, clusters, guardrails

  

    
01 · WHAT IS IT
      
The warehouse is the compute your query gets. You tune it along two axes:

      
    
        
  • Scale up (size XS → S → M … each step doubles nodes, memory, local SSD and credits/hour): for big or spilling queries.
    • 
        
  • Scale out (multi-cluster: MIN_CLUSTER_COUNT / MAX_CLUSTER_COUNT, Enterprise Edition): for many concurrent queries that queue.
    • 
      

      
Plus warehouse types: standard; Snowpark-optimized (much more memory per node, for memory-heavy Python, ML training and large UDFs); and Snowflake's newer generation 2 standard warehouses (faster hardware and engine improvements; check your region's availability and current syntax in the docs).

    

    
02 · WHY IT MATTERS
      
Picking the wrong axis wastes money: a bigger warehouse doesn't fix queuing if the queries were already fast, and more clusters don't fix one query spilling to remote storage. Guardrail parameters stop one runaway query from burning credits for two days.

    

    
03 · HOW IT WORKS · KNOBS YOU SHOULD KNOW
      

        
KNOBWHAT IT DOES

        
WAREHOUSE_SIZEEach size up doubles compute and credits/hour. For well-parallelised work, time roughly halves, so cost per query stays similar until scaling stops.

        
MIN/MAX_CLUSTER_COUNT, SCALING_POLICYMulti-cluster: STANDARD policy starts clusters quickly to avoid queuing; ECONOMY waits until there's enough load to keep a new cluster busy, saving credits.

        
MAX_CONCURRENCY_LEVELHow many queries one cluster runs at once before queuing (default 8). Lowering it gives each query more resources; raising it packs more small queries.

        
STATEMENT_TIMEOUT_IN_SECONDSCancels queries running longer than this (default 172800 = 2 days). Set it much lower on BI warehouses.

        
STATEMENT_QUEUED_TIMEOUT_IN_SECONDSCancels queries that waited in the queue too long (default 0 = never).

        
QUERY_TAGSession parameter: a label (e.g. 'dash:revenue') stored with every query in QUERY_HISTORY, so you can find and attribute workloads.

        
AUTO_SUSPENDSeconds idle before suspending. Too low on a BI warehouse throws away the local disk cache on every gap.
