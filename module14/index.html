Chapter 01

Late-arriving & out-of-order data

01

What is it

Events that arrive in Snowflake after the time window in which they logically belong — e.g., a mobile click event from 11:50 PM that lands in the pipeline at 12:15 AM the next day.

02

Why it matters

Without handling this, daily aggregations are wrong, SCD Type 2 effective dates overlap, and deduplication logic silently drops real records or keeps phantom duplicates.

03

Core patterns

Watermark window in MERGE, INSERT OVERWRITE for partitioned slices, QUALIFY dedup on streams, and downstream alerts on late-arrival rate via TASK_HISTORY.

Pattern 1 — Watermark-window MERGE

Only process source rows within a rolling window (e.g., 72 hours back). The MERGE upserts late arrivals and corrects existing rows if the late record is newer.

-- events_raw receives late events; events_curated is the clean layer
MERGE INTO events_curated tgt
USING (
  SELECT
    event_id,
    event_ts,
    user_id,
    event_type,
    ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY loaded_at DESC) AS rn
  FROM events_raw
  WHERE event_ts >= DATEADD('hour', -72, CURRENT_TIMESTAMP())
  QUALIFY rn = 1                      -- deduplicate within the window
) src ON tgt.event_id = src.event_id
WHEN MATCHED AND src.event_ts > tgt.event_ts THEN
  UPDATE SET
    event_ts   = src.event_ts,
    event_type = src.event_type,
    updated_at = CURRENT_TIMESTAMP()
WHEN NOT MATCHED THEN
  INSERT (event_id, event_ts, user_id, event_type)
  VALUES (src.event_id, src.event_ts, src.user_id, src.event_type);

Pattern 2 — INSERT OVERWRITE for date-partitioned tables

When a whole date slice may need to be recomputed (e.g., a backfill), overwrite just that partition rather than running a full table MERGE.

-- Recompute one date slice atomically
INSERT OVERWRITE INTO daily_sales_summary
  SELECT
    DATE(event_ts)  AS sale_date,
    region,
    SUM(amount)    AS total_amount,
    COUNT(*)       AS order_count
  FROM events_raw
  WHERE DATE(event_ts) = '2024-03-15'  -- the date being recomputed
  GROUP BY 1, 2;

Pattern 3 — Stream staleness guard

A stream becomes stale if its offset is not consumed before the table's data retention period expires. Monitor this proactively.

-- Alert on streams approaching staleness
SELECT
  stream_name,
  stale,
  stale_after,
  DATEDIFF('hour', CURRENT_TIMESTAMP(), stale_after) AS hours_until_stale
FROM INFORMATION_SCHEMA.STREAMS
WHERE stale_after < DATEADD('hour', 24, CURRENT_TIMESTAMP())
ORDER BY hours_until_stale;

Interview trap

"Can a Dynamic Table handle late arrivals?" — Yes, but only within its LAG window. If a late record arrives after the last refresh and outside the LAG, it may not be reflected until the next full refresh. For guaranteed late-arrival correctness, Streams + Tasks with a watermark MERGE give more control.

Senior angle

Agree on a late-arrival SLA with upstream teams before building pipelines: "we accept events up to 48 hours late." Model this as a Snowflake dynamic table with a lag of 1 hour plus a nightly MERGE task that re-processes the past 48 hours. Document the boundary in your data contract.

Chapter 02

Multi-account enterprise strategy

01

What is it

Running multiple separate Snowflake accounts — typically one per environment (dev/test/prod) and sometimes one per business unit or regulatory boundary — connected by replication or data sharing.

02

Why it matters

A single account for all environments risks production data leaks, uncontrolled cost from dev workloads, and can violate data residency requirements. Separate accounts provide hard blast-radius boundaries.

03

How it works

Snowflake's Organization layer manages multiple accounts under one contract. Accounts can share data via Snowflake Data Sharing or replicate databases via DATABASE REPLICATION GROUPS.

Account topology patterns

PatternWhen to useData movement
Single account, multiple databasesStartup / small team, tight budgetNone — same account
Dev / Test / Prod accountsStandard enterprise; separate cost and accessZero-copy clone promotion or replication
Per-BU accounts + central sharingLarge enterprise; different data ownersSecure Data Sharing (read-only)
Per-region accountsData residency / GDPR requirementsReplication with region pinning

Promoting code from dev → test → prod

-- Step 1: Clone prod database into test (zero-copy, instant)
CREATE DATABASE TEST_DB CLONE PROD_DB;

-- Step 2: Run regression tests against TEST_DB
-- Step 3: Once approved, promote via schema swap (atomic rename)
ALTER DATABASE PROD_DB RENAME TO PROD_DB_OLD;
ALTER DATABASE TEST_DB  RENAME TO PROD_DB;
-- If problems: reverse the rename (rollback in seconds)

Cross-account replication

-- On the PRIMARY account: enable replication
ALTER DATABASE PROD_DB ENABLE REPLICATION TO ACCOUNTS
  my_org.prod_replica_account;

-- On the SECONDARY account: create replica and refresh
CREATE DATABASE PROD_DB_REPLICA
  AS REPLICA OF my_org.primary_account.PROD_DB
  DATA_RETENTION_TIME_IN_DAYS = 1;

ALTER DATABASE PROD_DB_REPLICA REFRESH;  -- or schedule via Task

Senior angle — cost attribution across accounts

Use Snowflake's Organization Usage views (SNOWFLAKE.ORGANIZATION_USAGE.USAGE_IN_CURRENCY_DAILY) to aggregate credit consumption across all accounts under one contract. Set up resource monitors at the account level in each environment, with stricter quotas on dev/test than prod.

Interview trap

"Can you share data between accounts in real time?" — Secure Data Sharing is not a copy: the consumer account queries your objects directly in near-real time with no data movement cost. Replication IS a copy and incurs storage and compute. Know when to use each.

Chapter 03

Private Link / Private Endpoints

01

What is it

A mechanism to route traffic between your VPC and Snowflake over the cloud provider's private backbone — never crossing the public internet. AWS PrivateLink, Azure Private Link, and GCP Private Service Connect.

02

Why it matters

Required for PCI-DSS and HIPAA workloads. Eliminates public internet exposure for Snowflake traffic. Combined with Network Policies, it restricts connection sources to your corporate network only.

03

How it works

Snowflake provides a VPC endpoint service. You create an interface endpoint in your VPC that gets a private DNS hostname. All Snowflake traffic from your VPC resolves to that private IP.

Setup steps (AWS PrivateLink)

StepActorAction
1Snowflake AdminRun SELECT SYSTEM$GET_PRIVATELINK_CONFIG(); — get the endpoint service name and allowed principals.
2AWS AdminCreate a VPC Interface Endpoint using the service name from Step 1. Enable private DNS.
3Snowflake AdminAuthorize the endpoint: SYSTEM$AUTHORIZE_PRIVATELINK('vpce-0abc...')
4DNS AdminUpdate internal DNS to resolve <account>.snowflakecomputing.com to the VPC endpoint IP.
5Snowflake AdminCreate a network rule + policy to block all public internet access, forcing PrivateLink-only connections.
 
-- Step 1: Get PrivateLink config (run as ACCOUNTADMIN)
SELECT SYSTEM$GET_PRIVATELINK_CONFIG();
-- Returns JSON: {"privatelink-account-name":"...", "privatelink-vpce-id":"...", ...}

-- Step 3: Authorize the VPC endpoint
SELECT SYSTEM$AUTHORIZE_PRIVATELINK(
  'vpce-0abc123def456789a',  -- your VPC endpoint ID
  'arn:aws:iam::123456789:root'  -- AWS account ARN
);

-- Step 5: Lock down to PrivateLink only via network policy
CREATE OR REPLACE NETWORK RULE block_public
  TYPE = HOST_PORT
  MODE = INGRESS
  VALUE_LIST = ('0.0.0.0/0');  -- match everything public

CREATE OR REPLACE NETWORK POLICY privatelink_only
  ALLOWED_NETWORK_RULE_LIST = ()        -- nothing allowed by default
  BLOCKED_NETWORK_RULE_LIST = (block_public);

ALTER ACCOUNT SET NETWORK_POLICY = privatelink_only;

Interview trap

PrivateLink secures the connection from your VPC to Snowflake, but it does not secure data inside Snowflake. You still need RBAC, masking policies, and network policies to control who can access what once connected.

Chapter 04

Tri-secret Compose & Customer-Managed Keys

01

What is it

An encryption architecture where data at rest requires both a Snowflake-managed key AND a customer-managed key (CMK) held in your own KMS (AWS KMS, Azure Key Vault, or GCP Cloud KMS) to decrypt.

02

Why it matters

By default, Snowflake holds all encryption keys. Tri-secret Compose ensures that even Snowflake cannot decrypt your data without your CMK — giving you unilateral ability to revoke access instantly by rotating or deleting your KMS key.

03

How it works

Three keys compose to form the final data encryption key: (1) Snowflake root key, (2) account key derived from it, (3) customer CMK from your KMS. All three must be present to decrypt. Available on Business Critical edition only.

Key hierarchy

LevelKey typeHeld byRotated by
1 — RootSnowflake Root KeySnowflake HSMSnowflake (auto, yearly)
2 — AccountAccount Master KeySnowflakeSnowflake (auto, 30 days)
3 — TableTable Master KeySnowflakeSnowflake (auto)
4 — CMKCustomer-Managed KeyYour KMSYou (manual or scheduled)

Setup overview (AWS KMS)

-- Step 1: Create a symmetric KMS key in AWS with this key policy
-- (allow Snowflake's IAM role to use the key)

-- Step 2: In Snowflake (ACCOUNTADMIN), configure the KMS key ARN
ALTER ACCOUNT SET
  CUSTOMER_MANAGED_KEY = 'arn:aws:kms:us-east-1:123456789:key/abc-def-123';

-- Step 3: Snowflake performs a "wrap" of your account key with your CMK
-- From this point on, every I/O requires a KMS call to unwrap the key

-- To verify CMK is active:
SELECT current_account(), encryption_key_type
FROM SNOWFLAKE.ACCOUNT_USAGE.ACCOUNTS;

Critical operational note

If you disable or delete your CMK in AWS KMS, Snowflake cannot access your data — this is intentional for compliance scenarios. It also means you cannot run any queries. Always implement CMK rotation through key versioning (not deletion) to avoid accidental outages. Set up CloudWatch alarms on KMS key usage and rotation status.

Senior angle — Business Continuity Key (BCK)

Snowflake's Business Critical edition supports a BCK: a Snowflake-managed fallback key that lets Snowflake decrypt data for a limited time window in a disaster scenario (e.g., your KMS becomes unavailable). You can enable or disable the BCK. For maximum security (pure Tri-secret), disable the BCK and accept the operational risk of KMS unavailability.

Chapter 05

Snowflake Horizon

01

What is it

Snowflake's built-in unified governance layer — a set of features and tools for discovering, classifying, protecting, and monitoring all data, apps, and AI models across accounts and clouds from one place.

02

Why it matters

Enterprises need governance at scale — thousands of tables, hundreds of roles, dozens of teams. Horizon makes policy enforcement declarative (apply a tag once, masking follows everywhere) rather than column-by-column.

03

Key components

Trust Center (security posture), Compliance Center (audit reports), Data Quality Monitoring, Universal Search, Object Tagging, Data Classification, Access History, and Lineage.

Horizon pillars

PillarFeatureWhat it does
DiscoverUniversal Search, LineageFind any object; trace data from source to report
ClassifySYSTEM$CLASSIFY, Data ClassificationAuto-detect PII/PHI columns using ML
ProtectObject Tagging, Masking Policies, Row Access Policies, Tag-based policiesApply policies declaratively via tags
MonitorTrust Center, Access History, Data Quality MonitoringSecurity posture, audit trail, freshness/completeness
ComplyCompliance CenterSOC 2, HIPAA, PCI-DSS readiness reports

Trust Center

The Trust Center runs automated security checks against your account and surfaces findings. Access it via Snowsight → Admin → Trust Center.

-- Query Trust Center findings programmatically
SELECT check_name, severity, finding, recommendation
FROM SNOWFLAKE.TRUST_CENTER.FINDINGS
WHERE severity IN ('CRITICAL', 'HIGH')
ORDER BY severity, check_name;

Data Quality Monitoring (Metric Functions)

Snowflake Horizon includes Data Metric Functions (DMFs) — scheduled checks on table freshness, completeness, and validity that run on a schedule and write results to SNOWFLAKE.LOCAL.DATA_QUALITY_MONITORING_RESULTS. Built-in DMFs include FRESHNESS, NULL_COUNT, DUPLICATE_COUNT, and ROW_COUNT. You can also write custom DMFs.

Chapter 06

Object Tagging & Tag-based Policies

01

What is it

A metadata labelling system: you create a TAG object, apply it to any Snowflake object (database, schema, table, column, warehouse), and then policies can be driven automatically by those tags.

02

Why it matters

Without tags, masking policies must be applied column by column — dozens of ALTER TABLE statements that drift over time. With tag-based masking, applying one tag to a column enforces the right policy automatically, even as new tables are added.

03

How it works

Tags propagate from table → columns (lineage propagation). A masking policy is associated with a tag+type combination. When Snowflake encounters a query, it checks tags on queried columns and applies any associated masking policy.

Tag lifecycle — full example

-- 1. Create the tag (ACCOUNTADMIN or SYSADMIN + CREATE TAG privilege)
USE ROLE ACCOUNTADMIN;

CREATE OR REPLACE TAG pii_level
  ALLOWED_VALUES 'HIGH', 'MEDIUM', 'LOW'
  COMMENT = 'PII sensitivity classification';

CREATE OR REPLACE TAG data_domain
  ALLOWED_VALUES 'IDENTITY', 'CONTACT', 'FINANCIAL', 'BEHAVIORAL';

-- 2. Apply tags to columns
ALTER TABLE customers
  MODIFY COLUMN email
    SET TAG pii_level = 'HIGH', data_domain = 'CONTACT';

ALTER TABLE customers
  MODIFY COLUMN ssn
    SET TAG pii_level = 'HIGH', data_domain = 'IDENTITY';

-- 3. Create a masking policy
CREATE OR REPLACE MASKING POLICY mask_high_pii
  AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN CURRENT_ROLE() IN ('SYSADMIN','ACCOUNTADMIN','PII_READER_ROLE') THEN val
    ELSE '*** REDACTED ***'
  END;

-- 4. Associate policy with the tag (tag-based masking)
ALTER TAG pii_level
  SET MASKING POLICY mask_high_pii
  USING ('HIGH');  -- only applies when tag value = 'HIGH'

-- 5. Inspect: what tags are on this table?
SELECT * FROM TABLE(
  INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS(
    'MYDB.PUBLIC.CUSTOMERS', 'table'
  )
);

-- 6. Inspect: which columns have pii_level = 'HIGH'?
SELECT object_name, column_name, tag_value
FROM SNOWFLAKE.ACCOUNT_USAGE.TAG_REFERENCES
WHERE tag_name = 'PII_LEVEL'
  AND tag_value = 'HIGH'
ORDER BY object_name, column_name;

Interview trap — tag propagation

Tags applied to a table propagate to its columns only if the tag was created with ALLOWED_VALUES and propagation is configured. Tags applied directly to a column override table-level tags for that column. Test this with TAG_REFERENCES_ALL_COLUMNS to avoid surprises.

Chapter 07

SYSTEM$CLASSIFY — Automatic PII Detection

01

What is it

A Snowflake system function that uses ML models to analyze column names, data types, and sample values to automatically classify columns as containing personal data (PII/PHI) and suggest classification tags.

02

Why it matters

In a large enterprise with thousands of tables, manual PII discovery is infeasible. SYSTEM$CLASSIFY accelerates the discovery phase of a governance programme and surfaces columns engineers might have missed.

03

How it works

Runs sampling queries against the table, applies ML classifiers, returns a JSON result with suggested tags and confidence scores. You review and accept/reject. Can auto-apply tags with 'auto_tag': true.

-- Classify a single table (review-only, no auto-tagging)
SELECT SYSTEM$CLASSIFY(
  'MYDB.PUBLIC.CUSTOMERS',
  {'auto_tag': false}
);

-- Classify and automatically apply Snowflake system tags
SELECT SYSTEM$CLASSIFY(
  'MYDB.PUBLIC.CUSTOMERS',
  {'auto_tag': true}
);

-- Classify all tables in a schema
SELECT SYSTEM$CLASSIFY_SCHEMA(
  'MYDB.PUBLIC',
  {'auto_tag': true}
);

-- Review what classifications were applied
SELECT
  object_name,
  column_name,
  tag_name,
  tag_value
FROM SNOWFLAKE.ACCOUNT_USAGE.TAG_REFERENCES
WHERE tag_database = 'SNOWFLAKE'  -- system tags live in SNOWFLAKE database
ORDER BY object_name, column_name;

Classification categories

CategoryExamples detectedDefault system tag applied
IDENTIFIERSSN, passport number, credit card, email, phoneSNOWFLAKE.CORE.PRIVACY_CATEGORY = 'IDENTIFIER'
QUASI_IDENTIFIERDate of birth, ZIP code, gender, age, raceSNOWFLAKE.CORE.PRIVACY_CATEGORY = 'QUASI_IDENTIFIER'
SENSITIVESalary, medical condition, religion, political opinionSNOWFLAKE.CORE.SEMANTIC_CATEGORY = 'SALARY' etc.

Senior workflow — classify → review → enforce

1. Run SYSTEM$CLASSIFY_SCHEMA with auto_tag: false. 2. Review results in a Snowsight worksheet. 3. Reject false positives (e.g., product_code misclassified as IDENTIFIER). 4. Re-run with auto_tag: true. 5. Attach masking policies to the system tags via ALTER TAG ... SET MASKING POLICY. This two-pass approach avoids masking columns incorrectly.

Chapter 08

Compliance Certifications

01

What Snowflake provides

Snowflake holds SOC 2 Type II, ISO 27001, PCI-DSS (Level 1), HIPAA BAA, FedRAMP (Gov), and HITRUST certifications at the platform level. You inherit these controls but must still configure your side correctly.

02

Shared responsibility

Snowflake secures the platform (physical infrastructure, encryption at rest/in transit, platform availability). You are responsible for access control, data classification, audit logging, network policies, and incident response.

03

What you must configure

Role-based access (least privilege), column masking for PII, row access policies, network policies, MFA enforcement, audit log retention (ACCESS_HISTORY), and incident runbooks.

HIPAA — what you must configure in Snowflake

-- 1. Sign a BAA with Snowflake (contractual, not SQL)

-- 2. Classify and tag PHI columns
ALTER TABLE patient_records
  MODIFY COLUMN diagnosis SET TAG pii_level = 'HIGH';

-- 3. Enable column masking on PHI
ALTER TABLE patient_records
  MODIFY COLUMN diagnosis
  SET MASKING POLICY phi_mask;

-- 4. Enable ACCESS_HISTORY for audit trail
-- (enabled by default on Business Critical; verify via:)
SELECT * FROM SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY
WHERE query_start_time >= DATEADD('day', -7, CURRENT_DATE())
  AND objects_modified IS NOT NULL
ORDER BY query_start_time DESC
LIMIT 100;

ALTER ACCOUNT SET MULTI_FACTOR_AUTHENTICATION_ENROLLMENT_STATUS = 'REQUIRED';

Senior angle — compliance as code

Treat compliance controls as infrastructure: define masking policies, row access policies, tags, and network rules in Terraform or via dbt post-hooks, so they are version-controlled, peer-reviewed, and re-applied automatically when environments are promoted. A manual compliance checklist breaks down at scale.

7

Simulate late-arriving events with watermark MERGE

CREATE OR REPLACE TABLE events_raw (
  event_id   VARCHAR,
  event_ts   TIMESTAMP_NTZ,
  user_id    NUMBER,
  event_type VARCHAR,
  loaded_at  TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
);

CREATE OR REPLACE TABLE events_curated (
  event_id   VARCHAR PRIMARY KEY,
  event_ts   TIMESTAMP_NTZ,
  user_id    NUMBER,
  event_type VARCHAR,
  updated_at TIMESTAMP_NTZ
);

-- Load initial batch
INSERT INTO events_raw VALUES
  ('E001', '2024-03-01 10:00:00', 1, 'PAGE_VIEW',  CURRENT_TIMESTAMP()),
  ('E002', '2024-03-01 10:05:00', 2, 'CLICK',      CURRENT_TIMESTAMP()),
  ('E003', '2024-03-01 10:10:00', 1, 'PURCHASE',   CURRENT_TIMESTAMP());

-- Run the watermark MERGE
MERGE INTO events_curated tgt
USING (
  SELECT event_id, event_ts, user_id, event_type,
         ROW_NUMBER() OVER(PARTITION BY event_id ORDER BY loaded_at DESC) rn
  FROM   events_raw
  WHERE  event_ts >= DATEADD('hour', -72, CURRENT_TIMESTAMP())
  QUALIFY rn = 1
) src ON tgt.event_id = src.event_id
WHEN MATCHED AND src.event_ts > tgt.event_ts THEN
  UPDATE SET event_ts = src.event_ts, event_type = src.event_type,
             updated_at = CURRENT_TIMESTAMP()
WHEN NOT MATCHED THEN
  INSERT (event_id,event_ts,user_id,event_type,updated_at)
  VALUES (src.event_id,src.event_ts,src.user_id,src.event_type,CURRENT_TIMESTAMP());
SELECT COUNT(*) FROM events_curated = 3. Now INSERT a "late" duplicate of E001 with a corrected event_type, re-run the MERGE, and verify the curated table reflects the correction.

-- See what was accessed in the last hour (latency ~3h on Enterprise)
SELECT
  query_start_time,
  user_name,
  query_text,
  direct_objects_accessed
FROM SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY
WHERE query_start_time >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
ORDER BY query_start_time DESC
LIMIT 20;
Your MERGE and SELECT queries appear in ACCESS_HISTORY with the objects accessed listed in the VARIANT column.

Chapter 10

Interview Q&A

What is Tri-secret Compose and when is it required? TRICKY
An encryption architecture where data at rest requires both a Snowflake-managed key and a customer-managed key (CMK) in your own KMS to decrypt. Neither party alone can read your data. Required for PCI-DSS Level 1 and HIPAA workloads, and available only on Business Critical edition. The key operational risk: if your KMS key is unavailable, Snowflake cannot process queries. Always version-rotate rather than delete CMK keys.
Explain the difference between Object Tagging and column masking policies. FUNDAMENTAL
Tags are metadata labels; masking policies are the enforcement rules. You can apply a masking policy directly to a column (column-level masking), or you can associate a masking policy with a tag so that any column with that tag automatically gets the policy applied (tag-based masking). Tag-based masking is preferred at scale because adding a new PII column just needs a tag — no separate ALTER TABLE to attach a policy.
A new table with 200 columns lands in production. How do you govern it? SCENARIO
1. Run SYSTEM$CLASSIFY with auto_tag: false — review the JSON output for false positives. 2. Accept correct classifications (re-run with auto_tag: true) or apply custom tags manually for edge cases. 3. Verify tag-based masking policies already attached to those system tags are now enforced automatically — no additional ALTER TABLE needed. 4. Add the table to a row access policy if the data is multi-tenant. 5. Update TASK_HISTORY / data quality DMFs for the new table's freshness SLA.
How does PrivateLink interact with network policies in Snowflake? TRICKY
They work at different layers. PrivateLink controls how traffic reaches Snowflake — it removes the public internet path. Network policies control who can connect once traffic arrives — by IP range. You typically use PrivateLink AND a network policy together: PrivateLink forces all traffic to come via your VPC, and the network policy allows only the VPC's private IP range, blocking any connection that somehow bypasses PrivateLink.
What is Snowflake Horizon and how does it differ from just using RBAC? FUNDAMENTAL
RBAC controls who can access objects. Horizon adds what within those objects is visible (masking), which rows (row access policies), what it is (classification), where it flows (lineage), and how healthy it is (data quality monitoring). Horizon is the governance layer on top of access control — you need both.
A mobile app sends events that can arrive up to 6 hours late. How do you design the pipeline? SCENARIO
1. Land all events in a raw table (append-only). 2. Run a MERGE task every 15 minutes that processes events from the past 8 hours (6-hour SLA + 2-hour buffer) using QUALIFY ROW_NUMBER()=1 to dedup. 3. Use WHEN MATCHED AND src.event_ts > tgt.event_ts THEN UPDATE so a corrected late arrival overwrites. 4. For daily aggregations, schedule a nightly INSERT OVERWRITE for yesterday AND the day before (to catch 6-hour-late events that cross midnight). 5. Alert if the late-arrival rate exceeds the SLA threshold using a Task that queries loaded_at vs event_ts gaps.
What does SYSTEM$CLASSIFY return and how do you reject false positives? TRICKY
It returns a VARIANT JSON with an array of classification results per column: column name, suggested privacy_category (IDENTIFIER / QUASI_IDENTIFIER), semantic_category (EMAIL, PHONE, etc.), and a confidence score. To reject false positives: run with auto_tag: false first, parse the JSON output, identify columns with wrong classifications (e.g., "product_code" classified as IDENTIFIER), then run a selective auto_tag: true or manually apply tags only to correct columns. You can also unset a system tag: ALTER TABLE t MODIFY COLUMN c UNSET TAG SNOWFLAKE.CORE.PRIVACY_CATEGORY.
Explain the multi-account promotion strategy for a dbt project. SCENARIO
Dev, Test, and Prod are three separate Snowflake accounts. The dbt project uses profiles targeting each account. Promotion flow: (1) Developer merges PR to main — GitHub Actions runs dbt build --target dev (cloned from prod on PR open). (2) On merge, pipeline runs dbt build --target test against a zero-copy clone of prod, runs all dbt tests. (3) On manual approval, pipeline runs dbt build --target prod. Terraform manages the warehouse, role, and database objects in each account, ensuring parity. Secrets (account identifiers, passwords) are stored in GitHub/HashiCorp Vault and injected at runtime.
What is ACCESS_HISTORY and how does it differ from QUERY_HISTORY? TRICKY
QUERY_HISTORY records every SQL statement executed — it is the operational log (real-time, 365-day retention in ACCOUNT_USAGE). ACCESS_HISTORY records which specific columns were accessed or modified in each query — it is the compliance-grade audit trail required for HIPAA/PCI. ACCESS_HISTORY has up to 3 hours of latency and 365-day retention. Only Business Critical and above record column-level detail in ACCESS_HISTORY. Use QUERY_HISTORY for debugging; ACCESS_HISTORY for audits.
What is the shared responsibility model for HIPAA in Snowflake? FUNDAMENTAL
Snowflake's responsibility: physical infrastructure security, encryption at rest (AES-256) and in transit (TLS 1.2+), platform availability, disaster recovery at the infrastructure level, and passing the HIPAA BAA. Your responsibility: signing the BAA, classifying PHI columns, applying masking policies to PHI, enforcing least-privilege RBAC, enabling MFA, configuring network policies (preferably PrivateLink), retaining ACCESS_HISTORY for audit, and having an incident response plan.

Quiz

1. Tri-secret Compose is available on which Snowflake edition?

✓ Business Critical. Tri-secret Compose (customer-managed keys) requires the Business Critical edition and a signed agreement with Snowflake.

2. You run SYSTEM$CLASSIFY with auto_tag: true. What risk must you manage?

✓ False positives. Always run with auto_tag: false first to review suggestions before applying. A false positive that activates masking can break downstream reports.

3. What is the main difference between Secure Data Sharing and Database Replication?

✓ Replication creates a physical copy (storage cost). Sharing is a live reference — the consumer queries the provider's data with zero storage cost and near-real-time freshness.

4. You apply a masking policy to a tag. A new column is added to a table with that tag. What happens automatically?

✓ Tag-based masking automatically applies the associated policy to any column carrying that tag, including new columns — this is the key benefit over column-level masking.

5. What does SYSTEM$GET_PRIVATELINK_CONFIG() return?

✓ It returns a JSON object containing the privatelink-account-name, privatelink-vpce-id (the endpoint service name), and related DNS information needed by your cloud admin to create the VPC interface endpoint.

Cheat sheet

Late-arriving data

MERGE with QUALIFY ROW_NUMBER()=1 and a watermark WHERE clause (event_ts >= DATEADD('hour',-72,...)). WHEN MATCHED AND src.ts > tgt.ts THEN UPDATE to handle corrections.

Multi-account

Dev/Test/Prod = separate accounts. Promote via zero-copy clone + rename (atomic swap). Replicate via DATABASE REPLICATION GROUPS. Share live data via Secure Data Sharing (no copy).

PrivateLink

SYSTEM$GET_PRIVATELINK_CONFIG() → give to AWS/Azure admin → create endpoint → SYSTEM$AUTHORIZE_PRIVATELINK() → update DNS → lock down with network policy.

Tri-secret Compose

Business Critical only. Data requires Snowflake key + your CMK. Disabling your KMS key = no data access. Rotate via versioning, never delete. BCK is a Snowflake fallback key (can disable).

Snowflake Horizon

Governance platform: Trust Center (posture), Classify (SYSTEM$CLASSIFY), Protect (tags + policies), Monitor (ACCESS_HISTORY, DMFs), Comply (Compliance Center).

Object Tagging

CREATE TAG ... ALLOWED_VALUES. ALTER TABLE MODIFY COLUMN ... SET TAG. ALTER TAG ... SET MASKING POLICY. TAG_REFERENCES_ALL_COLUMNS() to audit.

SYSTEM$CLASSIFY

auto_tag:false first (review). auto_tag:true to apply. Returns IDENTIFIER, QUASI_IDENTIFIER, SENSITIVE. Use ACCOUNT_USAGE.TAG_REFERENCES to audit applied system tags.

Compliance
