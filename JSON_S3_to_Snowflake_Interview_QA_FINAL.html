Model answer: STAR timeline

about 2 minutes, spoken
  1. S
    Situation

    ShopStream's order service writes JSON order events to an S3 landing bucket. Analysts need them in Snowflake, typed, deduplicated, and fresh within minutes.

  2. T
    Task

    Build a secure, repeatable S3-to-Snowflake load that survives bad records, schema drift, and reruns, then automate it.

  3. A1
    Connect

    Storage integration S3_LANDING_INT, an IAM role with external ID trust and a least-privilege read policy, and allowed locations scoped to the landing prefix. No access keys.

  4. A2
    Describe

    JSON file formats (NDJSON plus a STRIP_OUTER_ARRAY variant) and an external stage, STG_S3_LANDING. LIST to prove access.

  5. A3
    Land & verify

    VALIDATION_MODE dry run, then COPY INTO ORDERS_RAW (VARIANT + METADATA$FILENAME / ROW_NUMBER). ON_ERROR = CONTINUE on known-dirty feeds, with rejects captured through VALIDATE into ORDERS_LOAD_ERRORS.

  6. A4
    Model

    LATERAL FLATTEN into CURATED.ORDERS and ORDER_ITEMS with TRY_ casts and a WHERE order_id IS NOT NULL rule.

  7. A5
    Automate

    Snowpipe auto-ingest (S3 event to SQS) into RAW, an append-only stream, and a 5-minute task that MERGEs by key with dedupe.

  8. R
    Result

    Loads verified by reconciliation: 60 orders and 111 items from the bulk files, 9 of 11 rows from the dirty file with 2 rejects quarantined, and the update applied as an upsert. Reruns are no-ops, and new fields like loyalty_tier flow through without code changes.

Main question1 question

Q01 Intermediate Main question

You have data in JSON format. Load it into Snowflake using S3.

Say this

I land the JSON in S3 and connect Snowflake through a storage integration, which is an IAM role with an external ID, so there are no keys. On top of that I put a JSON file format and an external stage, then COPY INTO a raw table with a VARIANT column and capture the file name and row number for lineage. I validate first, use ON_ERROR to control bad records, and flatten into typed curated tables. For ongoing files, Snowpipe auto-ingest plus a stream and a task keeps it incremental and idempotent.

Click to reveal answer
Red flag answers to avoid
  • "I'd put the AWS access key and secret in the CREATE STAGE." That works, but it's the legacy approach and the keys leak into DDL history.
  • "I'd create a column for every JSON field up front." That's brittle under schema drift. Land the raw data first.
  • Never mentioning validation, error handling, or what happens when someone runs it twice.
Deep diveSQL + visual

Structure the answer as connect → describe → land → verify → model → automate. The STAR timeline at the top of the page is the spoken version. Here is the full happy path using the ShopStream objects.

SQLEnd-to-end bulk load
-- 1) Connect: storage integration (ACCOUNTADMIN or a role with CREATE INTEGRATION)
USE ROLE ACCOUNTADMIN;
CREATE STORAGE INTEGRATION S3_LANDING_INT
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::111122223333:role/snowflake-s3-access-role'
  STORAGE_ALLOWED_LOCATIONS = ('s3://shopstream-raw-landing/landing/');
DESC INTEGRATION S3_LANDING_INT;   -- copy STORAGE_AWS_IAM_USER_ARN + STORAGE_AWS_EXTERNAL_ID into the IAM trust policy
GRANT USAGE ON INTEGRATION S3_LANDING_INT TO ROLE LAB_ENGINEER;

-- 2) Describe: file format + external stage
USE ROLE LAB_ENGINEER;
USE WAREHOUSE LAB_WH;
USE DATABASE SHOPSTREAM_LAB;
CREATE FILE FORMAT RAW.FF_JSON_NDJSON
  TYPE = JSON
  STRIP_OUTER_ARRAY = FALSE
  COMPRESSION = AUTO;
CREATE STAGE RAW.STG_S3_LANDING
  URL = 's3://shopstream-raw-landing/landing/'
  STORAGE_INTEGRATION = S3_LANDING_INT
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON');
LIST @RAW.STG_S3_LANDING/orders/;

-- 3) Land: raw VARIANT table + COPY with lineage columns
CREATE TABLE RAW.ORDERS_RAW (
  raw       VARIANT,
  src_file  STRING,
  src_row   NUMBER,
  loaded_at TIMESTAMP_LTZ DEFAULT CURRENT_TIMESTAMP()
);
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
FROM (
  SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
  FROM @RAW.STG_S3_LANDING/orders/
)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
PATTERN = '.*orders_.*[.]json'
ON_ERROR = ABORT_STATEMENT;

-- 4) Verify: expect 50 rows from the two orders/ files
SELECT src_file, COUNT(*) FROM RAW.ORDERS_RAW GROUP BY src_file;

Fundamentals6 questions

Q02 Basic Fundamentals

What stage types does Snowflake have, and which one would you use here?

Say this

There are user stages (@~), table stages (@%table), named internal stages, and named external stages. Since the files already live in S3, I use a named external stage on the landing prefix, backed by a storage integration. That makes it grantable, reusable, and keeps the file format attached. A named internal stage plus PUT is the fallback when there's no cloud bucket.

Click to reveal answer
Red flag answers to avoid
  • Confusing a stage with a table. A stage is only a pointer to files, plus some metadata.
Deep diveSQL + visual

User and table stages can't be granted to other roles, and a table stage can't hold a file format object. Named stages can do both. External stages never copy data into Snowflake storage until you run COPY.

SQLExternal vs internal fallback
-- External (preferred here)
LIST @RAW.STG_S3_LANDING/orders/;

-- Internal fallback: upload from SnowSQL, then load the same way
CREATE STAGE RAW.STG_INTERNAL_LANDING
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON');
PUT file:///<local_dir>/orders_*.json @RAW.STG_INTERNAL_LANDING/orders/ AUTO_COMPRESS = TRUE;
LIST @RAW.STG_INTERNAL_LANDING/orders/;
Q03 Basic Fundamentals

What is a file format object, and which JSON options actually matter?

Say this

A file format is a reusable named object that tells COPY, stages, and pipes how to parse files. For JSON the options that matter are STRIP_OUTER_ARRAY, STRIP_NULL_VALUES, COMPRESSION, IGNORE_UTF8_ERRORS or REPLACE_INVALID_CHARACTERS, and ALLOW_DUPLICATE. I keep two formats, one for NDJSON and one for array files, so the choice is explicit.

Click to reveal answer
Deep diveSQL

Precedence: options set directly in the COPY statement override the stage's format, and the stage's format overrides the defaults. Named formats avoid copy-paste drift between COPY, pipes, and external tables.

SQLTwo named formats
CREATE OR REPLACE FILE FORMAT RAW.FF_JSON_NDJSON
  TYPE = JSON
  STRIP_OUTER_ARRAY = FALSE
  COMPRESSION = AUTO
  IGNORE_UTF8_ERRORS = FALSE;

CREATE OR REPLACE FILE FORMAT RAW.FF_JSON_ARRAY
  TYPE = JSON
  STRIP_OUTER_ARRAY = TRUE
  COMPRESSION = AUTO;

-- Peek at staged files without loading them
SELECT $1:order_id::STRING, METADATA$FILENAME
FROM @RAW.STG_S3_LANDING/orders_array/ (FILE_FORMAT => 'RAW.FF_JSON_ARRAY')
LIMIT 5;
Q04 Basic Fundamentals

Why load JSON into a VARIANT column instead of typed columns straight away?

Say this

VARIANT stores any JSON value losslessly, and Snowflake still columnarizes common paths underneath, so queries on it are fast. Landing raw first separates ingestion from modeling. New fields don't break the load, and I can re-derive curated tables without going back to S3. Then I project typed columns in a curated layer.

Click to reveal answer
Red flag answers to avoid
  • "VARIANT is just a text blob, so it's slow." It's stored in an optimized columnar form for consistent paths.
Deep diveSQL

Typed-on-load (MATCH_BY_COLUMN_NAME or INFER_SCHEMA) is fine for stable, flat feeds. For evolving event payloads, the raw VARIANT plus curated pattern is the safer default and gives you replay.

SQLRaw vs projected
SELECT raw:order_id::STRING             AS order_id,
       raw:customer.address.city::STRING AS city,
       raw:payment.amount::NUMBER(12,2)  AS amount
FROM RAW.ORDERS_RAW
LIMIT 10;
Q05 Intermediate Fundamentals

What is the VARIANT size limit, and what happens when a record exceeds it?

Say this

The classic limit is 16 MB uncompressed per VARIANT value, which means per JSON document or row. Newer Snowflake releases raised the maximum for VARIANT, ARRAY, and OBJECT to around 128 MB, but I confirm it on the account and still design for 16 MB. If one document is too big, the row errors out and COPY reports that the document is too large. The fix is to split the outer array or restructure the producer's output.

Click to reveal answer
Red flag answers to avoid
  • Saying the limit is per file. It applies per value, which is why STRIP_OUTER_ARRAY rescues big array files.
Deep diveSQL

A 500 MB NDJSON file is fine because each line is its own value. A 500 MB file that is one big array is a single value unless you strip the outer array. Sizes are measured on the parsed representation, so a document that's close to the limit on disk can still exceed it.

SQLFind the largest documents
SELECT src_file,
       MAX(LENGTH(TO_JSON(raw))) AS max_doc_chars
FROM RAW.ORDERS_RAW
GROUP BY src_file
ORDER BY max_doc_chars DESC;
Q06 Basic Fundamentals

NDJSON vs. a JSON array. What does STRIP_OUTER_ARRAY do?

Say this

NDJSON has one complete object per line, so every line becomes a row. An array file is one document wrapping many objects. Without STRIP_OUTER_ARRAY = TRUE, the whole array lands as one row, and it can blow the size limit. Stripping the array turns each element into its own row.

Click to reveal answer
Deep diveSQL + visual

The ShopStream export file is a pretty-printed outer array with 10 orders. Loaded with the array format it gives 10 rows, which takes the raw total from 50 to 60. Pretty-printing doesn't matter, because JSON parsing ignores whitespace between tokens.

SQLLoad the array file
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
FROM (
  SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
  FROM @RAW.STG_S3_LANDING/orders_array/
)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_ARRAY');
Q07 Basic Fundamentals

How does compression work for JSON files from S3?

Say this

COMPRESSION = AUTO detects gzip, bzip2, zstd, and deflate from the file, so gzipped NDJSON loads with no extra settings. Brotli is the exception, and you have to declare it explicitly. Compressed files also mean less S3 transfer and faster loads, so I ask producers for gzip.

Click to reveal answer
Deep diveSQL

Load sizing guidance (about 100 to 250 MB per file) refers to compressed size. PUT to an internal stage gzips by default (AUTO_COMPRESS = TRUE). Unloads to S3 default to gzip as well.

SQLExplicit compression
CREATE OR REPLACE FILE FORMAT RAW.FF_JSON_NDJSON_BR
  TYPE = JSON
  COMPRESSION = BROTLI;   -- AUTO cannot detect Brotli

Security6 questions

Q08 Intermediate Security

Storage integration vs. access keys in CREATE STAGE. Which, and why?

Say this

A storage integration. Snowflake assumes an IAM role in my account through STS, so no long-lived secret is stored in Snowflake or written into DDL. Rotation is a non-issue, access is revocable on the AWS side, and admins can restrict which buckets stages may point at with STORAGE_ALLOWED_LOCATIONS. Keys in CREATE STAGE CREDENTIALS still work but are legacy, and many accounts block them by policy.

Click to reveal answer
Red flag answers to avoid
  • Hard-coding AWS_KEY_ID / AWS_SECRET_KEY "just for now".
  • "Make the bucket public so Snowflake can read it."
Deep diveSQL

One integration can back many stages. Only the integration knows the role ARN, and stage creators only need USAGE on it. Account parameters such as REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_CREATION let you enforce this.

SQLEnforce integrations
-- Legacy (avoid):
-- CREATE STAGE s URL='s3://...' CREDENTIALS = (AWS_KEY_ID='...' AWS_SECRET_KEY='...');

USE ROLE ACCOUNTADMIN;
ALTER ACCOUNT SET REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_CREATION = TRUE;
ALTER ACCOUNT SET REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_OPERATION = TRUE;
Q09 Intermediate Security

Walk me through the external ID and trust policy handshake.

Say this

I create the integration with my role ARN, then run DESC INTEGRATION to get STORAGE_AWS_IAM_USER_ARN and STORAGE_AWS_EXTERNAL_ID. In the role's trust policy I allow that IAM user to call sts:AssumeRole, but only when the external ID matches. That external ID prevents the confused-deputy problem, where another Snowflake customer tries to point at my role.

Click to reveal answer
Red flag answers to avoid
  • Forgetting that CREATE OR REPLACE on the integration gives it a new external ID, which breaks the trust policy.
Deep diveSQL + visual

Order of operations: create the role with a placeholder trust policy, create the integration, describe it, then update the trust policy. The Snowflake IAM user ARN is shared across your account, and the external ID is what makes the link unique to you.

SQLGet the values
DESC INTEGRATION S3_LANDING_INT;
-- property STORAGE_AWS_IAM_USER_ARN -> Principal
-- property STORAGE_AWS_EXTERNAL_ID  -> sts:ExternalId
JSONIAM role trust policy
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "<STORAGE_AWS_IAM_USER_ARN>" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "sts:ExternalId": "<STORAGE_AWS_EXTERNAL_ID>" } }
  }]
}
Q10 Intermediate Security

What does a least-privilege IAM policy for loading look like?

Say this

For read-only loading: s3:GetObject and s3:GetObjectVersion on the prefix objects, plus s3:ListBucket and s3:GetBucketLocation on the bucket. I scope ListBucket to the landing prefix with an s3:prefix condition. I add s3:DeleteObject only if we use PURGE, and s3:PutObject only if we unload.

Click to reveal answer
Red flag answers to avoid
  • Granting s3:* on * "to get it working".
Deep diveSQL

A common mistake is attaching ListBucket to bucket/*. ListBucket is a bucket-level action, so its Resource must be the bucket ARN itself. Object actions go on bucket/prefix/*.

JSONshopstream-snowflake-s3-read
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion"],
      "Resource": "arn:aws:s3:::shopstream-raw-landing/landing/*" },
    { "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::shopstream-raw-landing",
      "Condition": { "StringLike": { "s3:prefix": ["landing/*"] } } },
    { "Effect": "Allow",
      "Action": "s3:GetBucketLocation",
      "Resource": "arn:aws:s3:::shopstream-raw-landing" }
  ]
}
Q11 Intermediate Security

What do STORAGE_ALLOWED_LOCATIONS and STORAGE_BLOCKED_LOCATIONS do?

Say this

They're guardrails on the integration itself. A stage built on the integration can only point at URLs under an allowed location and never under a blocked one. So even with a broad IAM role, a stage creator can't wander into other prefixes. Snowflake enforces this before any AWS call is made.

Click to reveal answer
Deep diveSQL

Allowed locations can be '*' (every location the role can reach), which is fine in a sandbox and a smell in production. Blocked wins over allowed, which is useful for carving out a pii/ prefix.

SQLTighten the integration
ALTER STORAGE INTEGRATION S3_LANDING_INT SET
  STORAGE_ALLOWED_LOCATIONS = ('s3://shopstream-raw-landing/landing/')
  STORAGE_BLOCKED_LOCATIONS = ('s3://shopstream-raw-landing/landing/pii/');
Q12 Basic Security

Which role creates the integration, and how do engineers use it?

Say this

Creating an integration needs the account-level CREATE INTEGRATION privilege, which ACCOUNTADMIN has by default. I create it once as an admin, then grant USAGE on it to the engineering role. That role needs CREATE STAGE on the schema to build stages, and consumers get USAGE on the external stage.

Click to reveal answer
Red flag answers to avoid
  • Running the whole pipeline as ACCOUNTADMIN.
Deep diveSQL

This is separation of duties. The cloud trust lives with admins, and stages and pipes live with the data team. Ownership of pipes and tasks belongs to a functional role, not a person.

SQLGrants
USE ROLE ACCOUNTADMIN;
GRANT USAGE ON INTEGRATION S3_LANDING_INT TO ROLE LAB_ENGINEER;
GRANT CREATE STAGE ON SCHEMA SHOPSTREAM_LAB.RAW TO ROLE LAB_ENGINEER;
GRANT CREATE PIPE  ON SCHEMA SHOPSTREAM_LAB.RAW TO ROLE LAB_ENGINEER;
-- optional: delegate integration creation without full ACCOUNTADMIN
-- GRANT CREATE INTEGRATION ON ACCOUNT TO ROLE <platform_admin_role>;
Q13 Advanced Security

The bucket uses SSE-KMS, and security wants private connectivity. What changes?

Say this

For reading SSE-S3 objects nothing changes. For SSE-KMS the IAM role needs kms:Decrypt on the key, and the key policy has to allow that role, otherwise you get Access Denied even though the S3 permissions are correct. The stage ENCRYPTION setting mostly matters when Snowflake writes, as in an unload. For private networking on AWS, Business Critical accounts can route S3 traffic over PrivateLink, and the bucket policy can be restricted to a VPC endpoint.

Click to reveal answer
Red flag answers to avoid
  • Assuming PrivateLink is available on every edition. It's a Business Critical feature, so check the current docs.
Deep diveSQL

Snowflake's outbound private connectivity to S3 is enabled with USE_PRIVATELINK_ENDPOINT = TRUE on the integration, after provisioning an endpoint. Details evolve, so confirm against current docs before you commit to a design in the interview.

SQLKMS on the stage (writes/unloads)
CREATE OR REPLACE STAGE RAW.STG_S3_LANDING
  URL = 's3://shopstream-raw-landing/landing/'
  STORAGE_INTEGRATION = S3_LANDING_INT
  FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
  ENCRYPTION = (TYPE = 'AWS_SSE_KMS' KMS_KEY_ID = '<kms_key_arn_or_alias>');
JSONAdd to the IAM role policy
{ "Effect": "Allow",
  "Action": ["kms:Decrypt"],
  "Resource": "<kms_key_arn>" }

Loading6 questions

Q14 Basic Loading

Which COPY INTO options do you reach for most?

Say this

FILE_FORMAT, PATTERN or FILES to target files, ON_ERROR for error tolerance, and VALIDATION_MODE for dry runs. FORCE and PURGE control reloads and cleanup. MATCH_BY_COLUMN_NAME handles typed loads, and SIZE_LIMIT caps a run. I also check the COPY result columns, meaning status, rows parsed, rows loaded, and first error, on every run.

Click to reveal answer
Deep diveSQL

RETURN_FAILED_ONLY = TRUE trims the output to problem files. TRUNCATECOLUMNS / ENFORCE_LENGTH apply to string targets. LOAD_UNCERTAIN_FILES deals with the 64-day edge case.

SQLA well-dressed COPY
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
FROM (
  SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
  FROM @RAW.STG_S3_LANDING/orders/
)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
PATTERN = '.*orders_2026-11-18_.*[.]json'
ON_ERROR = 'SKIP_FILE_5%'
RETURN_FAILED_ONLY = TRUE;
Q15 Intermediate Loading

What transformations can you do during COPY, and which METADATA$ columns are available?

Say this

COPY can run a simple SELECT over the staged files. That covers column reordering, casting, path extraction, and functions like CURRENT_TIMESTAMP. JOINs, GROUP BY, and filtering WHERE clauses aren't allowed. The metadata columns are METADATA$FILENAME, METADATA$FILE_ROW_NUMBER, METADATA$FILE_CONTENT_KEY, METADATA$FILE_LAST_MODIFIED, and METADATA$START_SCAN_TIME. I always keep file name and row number for lineage and dedup.

Click to reveal answer
Red flag answers to avoid
  • Not knowing that VALIDATION_MODE and VALIDATE() don't support transforming COPYs.
Deep diveSQL

Keep transforms light at load time, like extracting a key or two for clustering, and do business logic downstream. Heavy transforms in COPY make reprocessing harder.

SQLTransform + metadata
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row, loaded_at)
FROM (
  SELECT $1,
         METADATA$FILENAME,
         METADATA$FILE_ROW_NUMBER,
         METADATA$START_SCAN_TIME
  FROM @RAW.STG_S3_LANDING/orders/
)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON');
Q16 Basic Loading

PATTERN vs. FILES. When do you use each?

Say this

FILES is an explicit list of up to 1,000 file names, which is precise and good for reruns of known files. PATTERN is a regex that matches paths under the stage location, which is good for daily or hourly prefixes. Prefer a precise path in the FROM clause plus a narrow pattern, because listing a huge prefix is slow.

Click to reveal answer
Red flag answers to avoid
  • Writing glob syntax (*.json) instead of a regex (.*[.]json).
Deep diveSQL

The regex is applied to the path below the location in FROM, plus the file name, so lead with .*. Escape a literal dot as [.] or \..

SQLBoth forms
-- explicit
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
FROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER FROM @RAW.STG_S3_LANDING/orders/)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
FILES = ('orders_2026-11-18_part1.json', 'orders_2026-11-18_part2.json');

-- regex
LIST @RAW.STG_S3_LANDING/orders/ PATTERN = '.*part[0-9]+[.]json';
Q17 Intermediate Loading

How do load metadata, FORCE, and PURGE make COPY idempotent, or not?

Say this

Each table remembers which files it loaded for 64 days, tracked by path plus checksum or ETag, so rerunning the same COPY skips those files. That's built-in idempotency. FORCE = TRUE ignores the metadata and reloads, which creates duplicates. PURGE = TRUE deletes successfully loaded files from the stage, needs s3:DeleteObject, and fails silently if it can't delete.

Click to reveal answer
Red flag answers to avoid
  • "Just rerun with FORCE = TRUE." That silently doubles rows.
  • Not knowing that CREATE OR REPLACE TABLE or TRUNCATE resets the load metadata.
Deep diveSQL + visual

Changed content under the same name gets a new checksum, so COPY loads it again. That's correct for corrections but can duplicate data. After 64 days a file with an old LAST_MODIFIED has uncertain status and is skipped unless LOAD_UNCERTAIN_FILES = TRUE. For true idempotency, dedupe downstream on a business key too.

SQLRerun safely
-- second run: 0 new rows, files reported as already loaded
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
FROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER FROM @RAW.STG_S3_LANDING/orders/)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON');

-- deliberate replay of one file (expect duplicates; dedupe downstream)
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)
FROM (SELECT $1, METADATA$FILENAME, METADATA$FILE_ROW_NUMBER FROM @RAW.STG_S3_LANDING/orders/)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
FILES = ('orders_2026-11-18_part1.json')
FORCE = TRUE;
Q18 Advanced Loading

How do MATCH_BY_COLUMN_NAME and INFER_SCHEMA / USING TEMPLATE fit in?

Say this

INFER_SCHEMA scans staged files and returns column names, types, and expressions. CREATE TABLE ... USING TEMPLATE builds a typed table from that output. MATCH_BY_COLUMN_NAME then maps top-level JSON keys to columns of the same name, with no SELECT needed, and INCLUDE_METADATA can add the file name. With schema evolution enabled, new keys can add columns automatically.

Click to reveal answer
Red flag answers to avoid
  • Forgetting that nested objects still arrive as VARIANT columns. This only flattens the top level.
Deep diveSQL

Gotcha: inferred names keep the file's case and get created as quoted identifiers. Use IGNORE_CASE => TRUE to get uppercase names. MATCH_BY_COLUMN_NAME can't be combined with a transforming SELECT, which is why INCLUDE_METADATA exists.

SQLTyped table from the files
SELECT *
FROM TABLE(INFER_SCHEMA(
  LOCATION    => '@RAW.STG_S3_LANDING/orders/',
  FILE_FORMAT => 'RAW.FF_JSON_NDJSON',
  IGNORE_CASE => TRUE));

CREATE OR REPLACE TABLE RAW.ORDERS_TYPED
  USING TEMPLATE (
    SELECT ARRAY_AGG(OBJECT_CONSTRUCT(*)) WITHIN GROUP (ORDER BY order_id)  -- ORDER_ID = INFER_SCHEMA output column
    FROM TABLE(INFER_SCHEMA(
      LOCATION    => '@RAW.STG_S3_LANDING/orders/',
      FILE_FORMAT => 'RAW.FF_JSON_NDJSON',
      IGNORE_CASE => TRUE)));

ALTER TABLE RAW.ORDERS_TYPED ADD COLUMN src_file STRING;
ALTER TABLE RAW.ORDERS_TYPED SET ENABLE_SCHEMA_EVOLUTION = TRUE;

COPY INTO RAW.ORDERS_TYPED
FROM @RAW.STG_S3_LANDING/orders/
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
INCLUDE_METADATA = (src_file = METADATA$FILENAME);
Q19 Intermediate Loading

External tables vs. loading. When would you not load at all?

Say this

An external table queries the files in place as a VALUE VARIANT column with metadata, so it's good for rarely queried archives, exploration, or keeping S3 as the system of record. Loading wins on performance, caching, clustering, time travel, and streams for CDC. For ShopStream orders, which are queried constantly, I load. For a cold history bucket, an external table with partition columns is fine.

Click to reveal answer
Deep diveSQL

External table partition columns must be derived from METADATA$FILENAME. AUTO_REFRESH uses the same S3 event to SQS plumbing as Snowpipe. Iceberg tables are the modern middle ground if open format is a requirement.

SQLPartitioned external table
CREATE OR REPLACE EXTERNAL TABLE RAW.ORDERS_EXT (
  order_id  STRING AS (value:order_id::STRING),
  file_date DATE   AS (TO_DATE(REGEXP_SUBSTR(METADATA$FILENAME, '[0-9]{4}-[0-9]{2}-[0-9]{2}')))
)
PARTITION BY (file_date)
LOCATION = @RAW.STG_S3_LANDING/orders/
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_NDJSON')
AUTO_REFRESH = TRUE;

SELECT file_date, COUNT(*) FROM RAW.ORDERS_EXT GROUP BY file_date;

Q20 Intermediate Errors & data quality

How do you dry-run a load with VALIDATION_MODE?

Say this

VALIDATION_MODE = RETURN_ERRORS, RETURN_ALL_ERRORS, or RETURN_n_ROWS parses the files and returns problems or sample rows without loading anything. It doesn't support transforming COPYs, so I point it at a plain COPY into a one-column VARIANT probe table. On the ShopStream bad file it surfaces the two malformed lines before anything touches RAW.

Click to reveal answer

Q21 Intermediate Errors & data quality

Explain ON_ERROR and its defaults.

Say this

Bulk COPY defaults to ABORT_STATEMENT, so one bad record fails the whole statement. Snowpipe defaults to SKIP_FILE. The alternatives are CONTINUE, which loads good rows and skips bad ones, and SKIP_FILE_n or SKIP_FILE_n%, which use a threshold. For the ShopStream bad file, CONTINUE loads 9 rows and rejects the 2 malformed lines, and I capture those rejects rather than ignoring them.

Click to reveal answer
Red flag answers to avoid
  • "I always use CONTINUE." That's silent data loss unless you also capture and alert on errors.
Deep diveSQL + visual

ON_ERROR only catches parse and load errors. A record that parses but is semantically wrong, like a missing order_id or the amount "forty-two", loads successfully into VARIANT. Those are caught by data-quality rules in the curated layer.

Q24 Advanced Errors & data quality

Design a quarantine for malformed JSON, missing keys, and type mismatches.

Say this

I handle it in two tiers. Parse failures are caught at load with ON_ERROR plus VALIDATE, or by reading lines as text and testing them with TRY_PARSE_JSON. Semantic failures are caught in the curated build with explicit rules: order_id must be present, and amount must cast through TRY_TO_NUMBER. Failing rows go to a quarantine with a reason code instead of disappearing. That makes it measurable, alertable, and replayable.

Click to reveal answer
Red flag answers to avoid
  • Using a hard ::NUMBER cast in the curated build. One bad value like "forty-two" fails the whole job.
Deep diveSQL

The ShopStream bad file shows each case. The two malformed lines are rejected at load. The record with no order_id is filtered by WHERE raw:order_id IS NOT NULL. For "forty-two", TRY_TO_NUMBER returns NULL, and that row is flagged.

SQLText-line quarantine + rule checks
-- Read each line as raw text so nothing is lost, then test it
CREATE OR REPLACE FILE FORMAT RAW.FF_JSON_AS_TEXT
  TYPE = CSV FIELD_DELIMITER = NONE ESCAPE_UNENCLOSED_FIELD = NONE;

SELECT METADATA$FILENAME AS file, METADATA$FILE_ROW_NUMBER AS line,
       $1 AS raw_text, TRY_PARSE_JSON($1) AS parsed
FROM @RAW.STG_S3_LANDING/orders_bad/ (FILE_FORMAT => 'RAW.FF_JSON_AS_TEXT')
WHERE parsed IS NULL;   -- the 2 malformed lines

-- Semantic rules on loaded rows
SELECT src_file, src_row,
       IFF(raw:order_id IS NULL, 'MISSING_ORDER_ID',
       IFF(TRY_TO_NUMBER(raw:payment.amount::STRING, 12, 2) IS NULL, 'BAD_AMOUNT', NULL)) AS reason
FROM RAW.ORDERS_RAW
WHERE src_file ILIKE '%orders_bad/%'

Q27 Intermediate Querying JSON

Explain FLATTEN: LATERAL, OUTER, and RECURSIVE.

Say this

FLATTEN turns an array or object into rows, with INDEX, KEY, VALUE, and PATH columns. LATERAL lets each row's array be flattened against that row. OUTER => TRUE keeps parents whose array is empty or missing, like a left join. RECURSIVE => TRUE walks every nested level, which is great for schema discovery and too noisy for production models.

Click to reveal answer
Red flag answers to avoid
  • Forgetting OUTER and silently dropping orders with no tags or items.
Deep diveSQL + visual

CURATED.ORDER_ITEMS is ORDERS_RAW × LATERAL FLATTEN(raw:items). The expected counts are 91 item rows from the two NDJSON files, and 111 after the array file. Use f.index + 1 as a stable line number for merge keys.

SQLThree flavors
-- items -> rows
SELECT o.raw:order_id::STRING AS order_id, i.index + 1 AS line_no,
       i.value:sku::STRING AS sku, i.value:qty::NUMBER AS qty
FROM RAW.ORDERS_RAW o, LATERAL FLATTEN(input => o.raw:items) i;

-- optional tags, keep orders without tags
SELECT o.raw:order_id::STRING AS order_id, t.value::STRING AS tag
FROM RAW.ORDERS_RAW o, LATERAL FLATTEN(input => o.raw:tags, OUTER => TRUE) t;

Q28 Advanced Querying JSON

SQL NULL vs. JSON null. How does STRIP_NULL_VALUES help?

Say this

A missing key returns SQL NULL. An explicit "key": null is stored as a VARIANT null, which is a value, so IS NULL is false. IS_NULL_VALUE() detects it, and casting it with ::STRING gives SQL NULL. STRIP_NULL_VALUES = TRUE in the file format drops null-valued keys at load, so both cases behave the same and storage shrinks.

Click to reveal answer
Deep diveSQL + visual

Choose deliberately. Stripping loses the difference between "explicitly cleared" and "not sent", which some CDC feeds rely on. TYPEOF() returns NULL_VALUE for JSON null.

SQLDetect both
SELECT raw:order_id::STRING AS order_id,
       raw:shipping IS NULL          AS sql_null,
       IS_NULL_VALUE(raw:shipping)   AS json_null,
       TYPEOF(raw:shipping)          AS t
FROM RAW.ORDERS_RAW;

CREATE OR REPLACE FILE FORMAT RAW.FF_JSON_NDJSON
  TYPE = JSON STRIP_OUTER_ARRAY = FALSE STRIP_NULL_VALUES = TRUE;

Q31 Advanced Continuous ingestion

How does Snowpipe deduplicate, and how does that differ from bulk COPY?

Say this

Snowpipe keeps load history on the pipe for 14 days and skips a file path it has already loaded in that window. Bulk COPY keeps its metadata on the table for 64 days. The two histories are separate, so loading the same file with a manual COPY and with the pipe produces duplicates. Recreating the pipe wipes its history, so a later REFRESH can replay files.

Click to reveal answer
Red flag answers to avoid
  • "Snowpipe guarantees exactly-once." It dedupes files within a window. Rows still need a key-based MERGE downstream.
Deep diveSQL + visual

Snowpipe identifies files by path, so re-uploading changed content under the same name in that window is generally not reloaded. Use new, immutable file names such as timestamped or UUID names. Events can also arrive more than once, and the history is what absorbs that.

SQLInspect what the pipe has done

FROM TABLE(SHOPSTREAM_LAB.INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'RAW.ORDERS_RAW',
  START_TIME => DATEADD(DAY, -1, CURRENT_TIMESTAMP())))
WHERE pipe_name = 'PIPE_ORDERS_INCREMENTAL';

Q35 Intermediate CDC & modeling

Say this

A standard stream tracks inserts, updates, and deletes as net changes. An append-only stream tracks inserts only and is cheaper to compute. ORDERS_RAW is insert-only, because corrections arrive as new events, so STRM_ORDERS_RAW is append-only. The stream offset advances only when a DML statement that reads it commits.

Click to reveal answer
Red flag answers to avoid
  • Thinking a SELECT from the stream consumes it. Only a committed DML statement does.
Deep diveSQL + visual

Streams can go stale if they aren't consumed within the table's retention, extended up to MAX_DATA_EXTENSION_TIME_IN_DAYS (default 14). Insert-only streams exist for external tables. Wrap multiple consumers in one explicit transaction so they see the same rows.

SQLStream + peek

  ON TABLE RAW.ORDERS_RAW APPEND_ONLY = TRUE;

FROM RAW.STRM_ORDERS_RAW;
Q36 Advanced CDC & modeling

Show the task that MERGEs new raw rows into curated tables.

Say this

A task runs every 5 minutes, but only when SYSTEM$STREAM_HAS_DATA is true, so idle runs cost nothing. Inside one transaction it MERGEs orders and then order items from the same stream snapshot. The source is deduped with QUALIFY ROW_NUMBER() so each key appears once. ORD-100003 moves from SHIPPED to DELIVERED as an update, not a duplicate.

Click to reveal answer
Red flag answers to avoid
  • MERGE without deduping the source. You get nondeterministic-merge errors or flip-flopping rows.
Deep diveSQL

Without the explicit transaction, the first MERGE would commit and advance the offset, and the second MERGE would see an empty stream. Resume the task after creating it, because tasks start suspended.

SQLCURATED.TSK_MERGE_ORDERS
CREATE OR REPLACE TASK CURATED.TSK_MERGE_ORDERS
  WAREHOUSE = LAB_WH
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('RAW.STRM_ORDERS_RAW')
AS
EXECUTE IMMEDIATE
$$
BEGIN
  BEGIN TRANSACTION;

  MERGE INTO CURATED.ORDERS t
  USING (
    SELECT raw:order_id::STRING                              AS order_id,
           raw:order_ts::TIMESTAMP_TZ                        AS order_ts,
           raw:status::STRING                                AS status,
           raw:channel::STRING                               AS channel,
           raw:customer.customer_id::STRING                  AS customer_id,
           raw:customer.loyalty_tier::STRING                 AS loyalty_tier,
           TRY_TO_NUMBER(raw:payment.amount::STRING, 12, 2)  AS amount,
           raw:payment.currency::STRING                      AS currency,
           COALESCE(raw:delivered_ts, raw:shipping.shipped_ts, raw:order_ts)::TIMESTAMP_TZ AS event_ts,
           src_file
    FROM RAW.STRM_ORDERS_RAW
    WHERE raw:order_id IS NOT NULL
    QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY event_ts DESC, src_file DESC) = 1
  ) s
  ON t.order_id = s.order_id
  WHEN MATCHED AND s.event_ts >= t.event_ts THEN UPDATE SET
    status = s.status, loyalty_tier = s.loyalty_tier, amount = s.amount,
    event_ts = s.event_ts, src_file = s.src_file, updated_at = CURRENT_TIMESTAMP()
  WHEN NOT MATCHED THEN INSERT
    (order_id, order_ts, status, channel, customer_id, loyalty_tier, amount, currency, event_ts, src_file, updated_at)
  VALUES
    (s.order_id, s.order_ts, s.status, s.channel, s.customer_id, s.loyalty_tier, s.amount, s.currency, s.event_ts, s.src_file, CURRENT_TIMESTAMP());

  MERGE INTO CURATED.ORDER_ITEMS t
  USING (
    SELECT o.raw:order_id::STRING             AS order_id,
           i.index + 1                        AS line_no,
           i.value:sku::STRING                AS sku,
           i.value:product_name::STRING       AS product_name,
           i.value:category::STRING           AS category,
           i.value:qty::NUMBER                AS qty,
           i.value:unit_price::NUMBER(12,2)   AS unit_price,
           i.value:discount::NUMBER(5,4)      AS discount
    FROM RAW.STRM_ORDERS_RAW o,
         LATERAL FLATTEN(input => o.raw:items) i
    WHERE o.raw:order_id IS NOT NULL
    QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id, line_no ORDER BY o.loaded_at DESC) = 1
  ) s
  ON t.order_id = s.order_id AND t.line_no = s.line_no
  WHEN MATCHED THEN UPDATE SET
    sku = s.sku, qty = s.qty, unit_price = s.unit_price, discount = s.discount
  WHEN NOT MATCHED THEN INSERT
    (order_id, line_no, sku, product_name, category, qty, unit_price, discount)
  VALUES
    (s.order_id, s.line_no, s.sku, s.product_name, s.category, s.qty, s.unit_price, s.discount);

  COMMIT;
END;
$$;

ALTER TASK CURATED.TSK_MERGE_ORDERS RESUME;
EXECUTE TASK CURATED.TSK_MERGE_ORDERS;   -- manual test run

Search optimization vs. clustering for JSON-heavy tables?

Say this

Clustering co-locates rows by a key such as order date, so range filters prune micro-partitions. It's worth it on large tables with stable filter patterns. Search optimization builds a lookup structure for selective point lookups, including equality on VARIANT paths like raw:order_id. Both add background maintenance cost, so I justify them with query history.

Click to reveal answer
Red flag answers to avoid
  • Clustering a small table, or clustering by a high-cardinality ID like order_id.
Deep diveSQL

Search optimization is an Enterprise-edition feature. Check SYSTEM$CLUSTERING_INFORMATION before and after. Curated tables are usually the right place for clustering keys.

SQLBoth
ALTER TABLE CURATED.ORDERS CLUSTER BY (TO_DATE(order_ts));
SELECT SYSTEM$CLUSTERING_INFORMATION('CURATED.ORDERS');

ALTER TABLE RAW.ORDERS_RAW ADD SEARCH OPTIMIZATION ON EQUALITY(raw:order_id);

Say this

The usual causes, in order: key case (raw:Order_ID vs order_id). Wrong nesting, where it's really raw:customer.address.city. The value is inside an array and needs an index or FLATTEN. Q46 Scenario Scenarios & troubleshooting

You receive a single 2 GB JSON file that is one big array. What now?

Say this

Without STRIP_OUTER_ARRAY it fails, because the whole array is one value far over the size limit. With STRIP_OUTER_ARRAY = TRUE it can load as long as each element fits, but one file is still one thread, so it's slow and fragile. The real fix is upstream: have the producer write gzipped NDJSON split into files of about 100 to 250 MB, or pre-split with a small job before staging.

Click to reveal answer
Red flag answers to avoid
  • "Scale the warehouse to 4XL." One file can't use the extra threads.
Deep diveSQL + visual

A typical pre-split is a stream-parsing job, such as jq in compact mode or a Lambda, that emits one object per line into chunked gzip files under a new prefix. Then load those normally or let Snowpipe pick them up.

SQLStopgap load
COPY INTO RAW.ORDERS_RAW (raw, src_file, src_row)

  FROM @RAW.STG_S3_LANDING/orders_array/
)
FILE_FORMAT = (FORMAT_NAME = 'RAW.FF_JSON_ARRAY')
ON_ERROR = ABORT_STATEMENT;
Q47 Scenario Scenarios & troubleshooting

After a rerun, the curated table has duplicates. How did that happen and how do you fix it?

Say this

Common causes: someone used FORCE, or the table was recreated or truncated, which wipes load metadata. A producer may have re-uploaded changed files under the same names, or the same file went in through both a manual COPY and the pipe. To fix it, dedupe on order_id keeping the latest event, then make the curated load a key-based MERGE so the problem can't recur.

Click to reveal answer
Red flag answers to avoid
  • "DELETE the duplicates and move on" without fixing the cause.
Deep diveSQL

Use src_file and src_row to see which load introduced the duplicates. Rebuilding curated from RAW with QUALIFY is safe, because RAW is the replayable record.

SQLFind & fix
-- where did they come from?
SELECT raw:order_id::STRING AS order_id, src_file, src_row, loaded_at
FROM RAW.ORDERS_RAW
QUALIFY COUNT(*) OVER (PARTITION BY raw:order_id::STRING) > 1
ORDER BY order_id, loaded_at;

-- rebuild latest-state curated table
CREATE OR REPLACE TABLE CURATED.ORDERS_DEDUP AS
SELECT *
FROM CURATED.ORDERS
QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY event_ts DESC, updated_at DESC) = 1;
Q48 Scenario Scenarios & troubleshooting

There's a nested array inside an array. How do you flatten it?

Say this

Chain LATERAL FLATTENs. Flatten the outer array, then flatten each element's inner array using the first flatten's VALUE as input. I use OUTER => TRUE on the inner flatten so items without children aren't dropped, and I state the resulting grain explicitly. For an array of arrays, the inner input is just the element value itself.

Click to reveal answer
Red flag answers to avoid
  • Using RECURSIVE in production models. The grain becomes unpredictable.
Deep diveSQL + visual

Keep both indexes, outer and inner, in the output. Together with order_id they form the natural key for MERGE.

SQLTwo-level flatten
SELECT o.raw:order_id::STRING   AS order_id,
       i.index                  AS item_idx,
       i.value:sku::STRING      AS sku,
       c.index                  AS component_idx,
       c.value:sku::STRING      AS component_sku
FROM RAW.ORDERS_RAW o,
     LATERAL FLATTEN(input => o.raw:items) i,
     LATERAL FLATTEN(input => i.value:components, OUTER => TRUE) c;

-- array of arrays, e.g. "matrix": [[1,2],[3]]
SELECT a.index AS row_idx, b.index AS col_idx, b.value::NUMBER AS v
FROM RAW.ORDERS_RAW o,
     LATERAL FLATTEN(input => o.raw:matrix) a,
     LATERAL FLATTEN(input => a.value) b;
Q49 Scenario Scenarios & troubleshooting

The pipe exists, but new files aren't loading. Troubleshoot it.

Say this

I start with SYSTEM$PIPE_STATUS. Is it RUNNING or paused, and is lastReceivedMessageTimestamp moving? If messages arrive but nothing loads, I check COPY_HISTORY and VALIDATE_PIPE_LOAD for errors, then file format mismatches, ownership or privileges, and whether the files are duplicates the pipe already saw.
