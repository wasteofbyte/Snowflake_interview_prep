MODULE 07 · DATA PROTECTION

Nothing is overwritten.
So almost anything can be undone.

Module 1 taught you that Snowflake stores table data in immutable micro-partitions: files that are written once and never edited. This module shows the payoff. Because old files are kept instead of overwritten, Snowflake can rewind tables (Time Travel), keep a last-resort copy (Fail-safe), copy terabytes in seconds (zero-copy cloning), and ship only the changed files to another region (replication).

Four everyday analogies for this module:

TIME TRAVEL
Google Docs version history

You deleted a paragraph by mistake? Open the history and pick the version from 10 minutes ago. You can do it yourself, for a limited number of days.

FAIL-SAFE
The bank's back-room vault

After your own history expires, the bank still keeps a copy for 7 days. You can't open the vault yourself. Only bank staff (Snowflake Support) can, and only in an emergency.

ZERO-COPY CLONE
A playlist, not a CD burn

Making a new playlist doesn't copy the songs. It points at the same songs. Only songs you add or change are new.

REPLICATION
A second kitchen in another city

The same recipes and stock, kept in sync on a schedule. If the first kitchen floods, you open the second one and send the customers there.

01 · WHAT IS IT

Data protection in Snowflake is a set of features that keep your data recoverable after human mistakes, bad code, or a whole-region outage. Snowflake calls the built-in part Continuous Data Protection (CDP): Time Travel + Fail-safe, which are on by default for permanent tables.

Every version of a table's data moves through the same lifecycle: Active → Time Travel → Fail-safe → purged.

02 · WHY WE USE IT
  • People make mistakes: an UPDATE without a WHERE, a DROP in the wrong schema, a buggy dbt model.
  • No backup jobs to run: traditional databases need nightly dumps. Here, history is kept automatically.
  • Cheap dev/test copies: clone production in seconds without doubling storage.
  • Business continuity: replicate to another region or cloud and fail over when needed.
03 · HOW IT WORKS · FOLLOW ONE MICRO-PARTITION (click Next)

The key idea: a table is just metadata pointing at a list of micro-partition files. Changing data never edits a file; it writes new files and moves the pointers. The old files become history. Step through it:

SENIOR ANGLE
When an interviewer asks "how can Snowflake offer Time Travel, cloning and incremental replication so cheaply?", the one-line answer is: immutable micro-partitions plus versioned metadata. Time Travel = keep old files and old metadata versions. Clone = new metadata pointing at the same files. Replication = copy only the files the secondary doesn't have yet.
CHAPTER 01

Time Travel · query and restore the past

01 · WHAT IS IT

Time Travel lets you read, clone, or restore data as it was at an earlier point within a retention window. You use it in three ways:

  • Query the past: SELECT … FROM orders AT(OFFSET => -3600)
  • Clone the past: CREATE TABLE orders_fix CLONE orders BEFORE(STATEMENT => '<query_id>')
  • Bring back dropped objects: UNDROP TABLE | SCHEMA | DATABASE

The point in time is given with AT (inclusive) or BEFORE (just before), using one of: TIMESTAMP =>, OFFSET => (seconds back from now, negative), or STATEMENT => (a query ID).

02 · WHY WE USE IT
  • Undo mistakes without a restore ticket: bad UPDATE, accidental DELETE, wrong DROP.
  • Audit and debugging: "what did this row look like before last night's job ran?"
  • Reproducibility: rerun a report on yesterday's exact data.
  • Safe deployments: note the time before a release, and roll back data if it goes wrong.
03 · HOW IT WORKS · IN THE BACKEND
1 · Every commit is a version

Each committed DML creates a new table version in the metadata store (cloud services): a list of the micro-partitions that make up the table at that moment. Replaced partitions are not deleted; they are marked as historical.

2 · AT / BEFORE picks a version

Cloud services finds the version that was current at your timestamp, offset or statement, and hands that list of partitions to the warehouse. Pruning works as normal, using the old version's min/max metadata.

3 · Retention decides how far back

Historical partitions stay queryable for DATA_RETENTION_TIME_IN_DAYS. After that a background process moves them into Fail-safe (permanent tables) or removes them.

Querying Time Travel needs a warehouse (it is a normal read). Cloning and UNDROP are metadata operations handled by cloud services, so they don't scan data.

How long can you go back?

DATA_RETENTION_TIME_IN_DAYS

Set at account, database, schema or table level. The lowest level that sets it explicitly wins (table beats schema beats database beats account). Setting it to 0 turns Time Travel off for that object.

MIN_DATA_RETENTION_TIME_IN_DAYS

An account-level safety floor set by ACCOUNTADMIN. Effective retention = MAX(DATA_RETENTION_TIME_IN_DAYS, MIN_DATA_RETENTION_TIME_IN_DAYS), so a developer can't quietly set a table to 0. It doesn't apply to transient or temporary objects.

INTERVIEW TRAP
AT vs BEFORE with STATEMENT. AT(STATEMENT => id) includes the changes made by that statement. BEFORE(STATEMENT => id) shows the table just before it ran. To undo a bad UPDATE, you want BEFORE.
INTERVIEW TRAP
Timestamps and time zones. AT(TIMESTAMP => '2024-06-01 09:00') may be parsed as a different type than you expect. Cast explicitly, e.g. '2024-06-01 09:00:00 -0700'::TIMESTAMP_TZ or ::TIMESTAMP_LTZ. If you ask for a time before the table existed or older than retention, the query errors.
INTERVIEW TRAP
CREATE OR REPLACE then UNDROP. CREATE OR REPLACE TABLE orders … silently drops the old table. To get it back, first rename the new one (ALTER TABLE orders RENAME TO orders_new), then UNDROP TABLE orders. UNDROP fails if an object with the same name already exists. If a name was dropped several times, UNDROP restores the most recently dropped version first (SHOW TABLES HISTORY shows them all).
SENIOR ANGLE
Parent retention wins on drop. If you drop a database or schema, its child tables are retained for the parent's retention period, even if a child had a longer retention set explicitly. Critical tables in a schema with 1-day retention can therefore only be UNDROPped for 1 day if the whole schema is dropped. Also: changing retention is not retroactive in the way people think. Increasing it extends history that is still in Time Travel; decreasing it pushes history older than the new limit into Fail-safe (permanent tables).
CHAPTER 02

Fail-safe · the last-resort safety net

01 · WHAT IS IT

Fail-safe is a fixed 7-day period that starts after Time Travel ends, for permanent tables only. During this time Snowflake still keeps the historical micro-partitions, but you can't query, clone or UNDROP them. Only Snowflake Support can recover the data, on a best-effort basis.

Transient and temporary tables have no Fail-safe.

02 · WHY IT EXISTS

It protects against disasters that Time Travel doesn't cover: for example someone sets retention to 0 and drops a table, or a mistake is noticed only after the retention window has passed. It is Snowflake's internal safety net, not a backup feature you operate.

The catch: you pay for its storage, and you can't turn it off for permanent tables. That is the main reason transient tables exist.

03 · HOW IT WORKS

When a historical micro-partition ages out of Time Travel, a background service re-tags it as Fail-safe instead of deleting it. Seven days later it is permanently purged and the storage is freed. Recovery from Fail-safe means opening a support case; Snowflake documents that it can take from hours to days and is not guaranteed for any particular scenario. You can see the bytes per table in TABLE_STORAGE_METRICS (columns ACTIVE_BYTES, TIME_TRAVEL_BYTES, FAILSAFE_BYTES, RETAINED_FOR_CLONE_BYTES).

INTERVIEW TRAP
"Fail-safe is our backup strategy." Wrong. You can't access it, can't test a restore, and recovery isn't guaranteed. It is a safety net for Snowflake to use in rare cases. Your real recovery tools are Time Travel, clones, replication, and (where available) Snowflake's backup features.
SENIOR ANGLE
High-churn tables are expensive. A 1 TB table fully reloaded every day with 1-day retention can carry around 1 TB of Time Travel plus up to 7 TB of Fail-safe. Make staging and reload-every-run tables transient, and keep permanent + longer retention for curated, hard-to-rebuild data.
CHAPTER 03

Table types · permanent, transient, temporary

01 · WHAT IS IT

Snowflake has three table types that differ only in how much protection they get (and therefore how much history storage they cost). Data is stored the same way, query speed is the same.

  • Permanent (default): Time Travel up to 90 days (Enterprise+) + 7 days Fail-safe.
  • Transient: CREATE TRANSIENT TABLE. Persists until dropped, visible to anyone with privileges, but Time Travel 0 or 1 day and no Fail-safe.
  • Temporary: CREATE TEMPORARY TABLE. Exists only in your session, invisible to other sessions, dropped automatically when the session ends. Time Travel 0 or 1 day, no Fail-safe.
02 · WHY WE USE IT

Protection costs storage. Data you can easily rebuild (staging copies of files still sitting in S3, intermediate ETL results, scratch work) doesn't need 7 days of Fail-safe. Making those tables transient or temporary can cut a large part of the storage bill on high-churn pipelines.

Analogy: permanent = a signed contract in the office safe; transient = a whiteboard in the team room; temporary = a sticky note on your own screen that goes in the bin when you leave.

INTERVIEW TRAP
You can't ALTER a table's type. There is no ALTER TABLE … SET TRANSIENT. To change it, create a new table of the right type (CTAS or CREATE TRANSIENT TABLE … LIKE + INSERT), then swap names with ALTER TABLE … SWAP WITH. Also, every table created inside a transient database or schema is transient.
INTERVIEW TRAP
Temporary tables shadow permanent ones. A temporary table can have the same name as an existing table in the same schema; inside your session the temporary one wins. That can make a script silently read the wrong data. Use distinct names (e.g. a tmp_ prefix).
CHAPTER 04

Zero-copy cloning · a full copy in seconds, for free (at first)

01 · WHAT IS IT

CREATE TABLE orders_dev CLONE orders; creates a new, independent object that initially contains exactly the same data as the source, without copying any data. You can clone tables, schemas and whole databases (and some other objects, below), optionally as of a point in time with AT / BEFORE.

After cloning, the two objects are independent: changes to one never appear in the other.

02 · WHY WE USE IT
  • Dev / test / QA environments with real production-shaped data, created in seconds.
  • Safe experiments: clone before a risky migration or backfill; if it goes wrong, swap back.
  • Point-in-time snapshots: "month-end close as of 23:59" kept as a table.
  • Recovery: clone a table BEFORE a bad statement, then swap it in.
03 · HOW IT WORKS · METADATA POINTERS + COPY-ON-WRITE

A clone is a new metadata entry in cloud services that points at the same immutable micro-partitions as the source. No warehouse is needed and no bytes are copied. When either side later changes data, Snowflake writes new micro-partitions for that side only (copy-on-write); the other side keeps pointing at the old ones. Storage cost therefore grows only with the divergence. Shared partitions are billed to the table that originally wrote them; if the source later drops a partition the clone still needs, the source keeps paying for it as RETAINED_FOR_CLONE_BYTES.

What gets cloned, and what doesn't

Cloneable

Databases, schemas, tables (including clones of clones), and several schema objects such as streams, tasks, sequences, file formats and external stages. A cloned database/schema clones its child objects. Check the docs for the current list (it grows over time).

Be careful with

Internal named stages and staged files are not copied the way tables are (rules have evolved, check current docs). Pipes are only cloned when they reference external stages. Tasks in a clone start suspended. Streams in a cloned schema/database lose their unconsumed records.

Privileges

Cloning a single table does not copy grants unless you add COPY GRANTS. Cloning a database or schema keeps the grants on the child objects, but not the grants on the database/schema itself. The clone is owned by the role that created it.

INTERVIEW TRAP
Load history is not cloned. A cloned table has no COPY load metadata, so running the same COPY INTO against the clone can load files again and create duplicates. Same for a cloned pipe.
SENIOR ANGLE
Clone + Time Travel = point-in-time environments. CREATE DATABASE qa_db CLONE prod_db AT(TIMESTAMP => …). If some child tables don't have enough retention for that time, the clone errors; the IGNORE TABLES WITH INSUFFICIENT DATA RETENTION option skips them. Long-lived dev clones diverge over time, so refresh them (re-clone) on a schedule rather than letting them become a second copy of prod.
CHAPTER 05

Replication & failover · surviving a region outage

01 · WHAT IS IT

Replication keeps a read-only copy (secondary) of databases, and optionally account objects, in another Snowflake account in the same organization, which can be in a different region or even a different cloud. Failover promotes that secondary to be the writable primary when the original region is down.

  • Replication group: a set of objects replicated together, point-in-time consistent. Secondaries are read-only.
  • Failover group: a replication group that can also be promoted (failed over). Requires Business Critical edition or higher.
  • Connection object (client redirect): a stable URL that you can re-point to the new primary account. Business Critical or higher.
02 · WHY WE USE IT
  • Disaster recovery for region- or cloud-level outages.
  • Meet RPO / RTO targets: RPO = how much data you can afford to lose; RTO = how long you can afford to be down.
  • Data locality: serve read-only copies close to users in other regions.
  • Migrations between regions or clouds.

Database (and share) replication is available on all editions. Replicating other account objects and failover/failback require Business Critical or higher.

03 · HOW IT WORKS
1 · Initial refresh

The first refresh copies all micro-partitions of the group's databases to the target account's storage. This can take a long time for large data.

2 · Incremental refreshes

On each refresh (REPLICATION_SCHEDULE, e.g. every 10 minutes, or manual REFRESH), Snowflake compares metadata and copies only new micro-partitions. Immutability makes the diff cheap: unchanged files never move again.

3 · Failover + redirect

On the target account: ALTER FAILOVER GROUP … PRIMARY makes it writable. ALTER CONNECTION … PRIMARY points the connection URL at it, so clients reconnect without config changes.

Cost: data transfer (especially cross-region / cross-cloud), serverless compute for each refresh, and storage of the secondary copy. More frequent refreshes = lower RPO but more refresh compute.

INTERVIEW TRAP
Replication is not a backup. A bad UPDATE or DROP on the primary is replicated to the secondary at the next refresh. Replication protects against losing a region; Time Travel, clones and backups protect against bad changes. You need both.
SENIOR ANGLE
Run DR drills. Fail over to the secondary, run smoke tests, then fail back. Things that commonly break: integrations, external stages and pipes pointing at region-specific buckets, tasks that must be resumed on the new primary, and clients using the account URL instead of the connection URL. Monitor lag with REPLICATION_GROUP_REFRESH_HISTORY.
CHAPTER 06

Backups & protection strategy · putting it all together

01 · WHAT IS IT

Besides Time Travel, Fail-safe, clones and replication, Snowflake has added dedicated backup features: point-in-time, read-only copies of tables, schemas or databases created on a schedule by a backup policy, kept for a retention period you choose, and optionally protected by a retention lock so nobody, not even an admin, can delete them early (useful for ransomware protection and WORM-style compliance). These features were introduced recently and earlier previews used the name "snapshots", so check current docs for names, syntax and edition requirements.

02 · WHY IT MATTERS

Time Travel tops out at 90 days, and anyone with enough privileges can lower retention or drop objects. Regulated data often needs longer, tamper-proof history. Before dedicated backups, teams kept dated clones (e.g. finance_db_2024_06_30) via a scheduled task, which works but relies on everyone not dropping them.

03 · HOW TO DESIGN A STRATEGY · PICK A DATA TIER

A good answer in an interview is tiered: match protection (and cost) to how hard the data is to rebuild and how critical it is.

INTERVIEW TRAP
Protection against whom? Time Travel protects against accidents but not against a malicious admin who sets retention to 0 and drops everything. Defences: MIN_DATA_RETENTION_TIME_IN_DAYS at account level, tightly controlled ACCOUNTADMIN / OWNERSHIP, replication to another account, and immutable backups with a retention lock.
