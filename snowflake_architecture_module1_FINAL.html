MODULE 01 · ARCHITECTURE

How Snowflake
actually works.

Almost every Snowflake interview question traces back to this module, whether it's about performance, cost, caching, cloning or Time Travel. If you understand the three layers and micro-partitions, the rest of Snowflake starts to make sense.

Every chapter follows the same pattern: What is it, then Why we use it, then How it works. Each one also has a simulator to play with. Throughout the module we'll use one analogy: Snowflake is a restaurant.

CLOUD SERVICES = THE MANAGER
Front desk & manager

Checks your reservation (login), reads the order (parses the SQL), decides the cooking plan (optimizer) and keeps the inventory book (metadata). Never cooks.

COMPUTE = KITCHENS
Independent kitchens

Each kitchen (virtual warehouse) has its own chefs. Bigger kitchen = more chefs. More kitchens = more orders cooked at the same time. You pay only while a kitchen is open.

STORAGE = THE PANTRY
One shared pantry

A single, effectively unlimited pantry (cloud object storage) where ingredients sit in small labelled boxes (micro-partitions). Every kitchen takes from the same pantry.

WHAT 6-YR CANDIDATES MUST SHOW
At this level, being able to recite the three layers isn't enough. You need to explain trade-offs: why a query was slow, why a bill went up, why the cache didn't help, and which knob you'd change. Every chapter ends with the interview angle for that topic.
CHAPTER 01

The big picture · three layers

01 · WHAT IS IT

Snowflake is a fully managed cloud data platform (a data warehouse delivered as SaaS). It runs on AWS, Azure or Google Cloud. There's nothing for you to install, tune, patch or index. You write SQL and Snowflake handles the infrastructure.

Its design is called multi-cluster shared data: three independent layers (storage, compute and cloud services), each of which scales on its own.

02 · WHY WE USE IT

Traditional warehouses (Teradata, Oracle, on-prem Hadoop) lock storage and compute together. That caused three problems:

  • Contention: the 9 AM dashboards and the nightly ETL fight over the same CPUs.
  • Paying for peak: you buy hardware for your busiest hour and it sits idle the rest of the time.
  • Slow scaling: adding nodes means reshuffling data, which can take days.

Snowflake separates storage from compute, so each team gets its own compute, you pay per second, and resizing takes seconds.

03 · HOW IT WORKS · COMPARE THE THREE DESIGNS

Click through the three architectures. Snowflake's design is described as a hybrid: it takes the "one central copy of data" idea from shared-disk and the "independent nodes doing the work in parallel" idea from shared-nothing.

Good

A single copy of the data, so it's simple to manage.

Bad

Every node competes for the same disk. Adding nodes increases contention instead of fixing it.

Good

Each node reads its own disk, so it scales well for parallel scans (e.g. Teradata, Redshift classic).

Bad

Storage and compute are locked together. You can't add CPU without adding disk, scaling means reshuffling the data, and all workloads share the same nodes.

Shared-disk idea

All warehouses read one central copy of the data, so there are no data silos and no copies to keep in sync.

Shared-nothing idea

Inside each warehouse, the nodes split the work and process micro-partitions in parallel. Warehouses don't slow each other down.

INTERVIEW TRAP
"Does the warehouse store data?" No. A warehouse only caches data on its local SSD while it's running. The permanent copy always lives in the storage layer. That's why you can drop or resize a warehouse without losing a single row.
CHAPTER 02

Storage layer & micro-partitions

01 · WHAT IS IT

When you load data, Snowflake automatically cuts every table into small, immutable files called micro-partitions. Each one holds 50–500 MB of uncompressed data (much smaller once compressed), stored column by column (columnar), compressed and encrypted, in cloud object storage (S3, Azure Blob or GCS).

You never see these files. You can't define, name or size them. You only interact with tables through SQL.

02 · WHY WE USE IT
  • Pruning: skip files that can't contain your data. This is how Snowflake gets fast without indexes.
  • Columnar: read only the columns your query mentions.
  • Immutable: files are never edited in place, which is what makes Time Travel, zero-copy cloning and consistent reads possible.
  • Zero maintenance: no partitions to declare, no VACUUM, no index rebuilds.
03 · HOW IT WORKS

For every micro-partition, the cloud services layer records metadata: the MIN and MAX value of each column, the number of distinct values, the NULL count and more. When your query has a filter like WHERE order_date = '2024-03-15', the optimizer checks that metadata before reading anything. Any partition whose range can't include March 15 is skipped. This is partition pruning.

How well pruning works depends on how the data is physically ordered. If the data was loaded day by day, each file covers a narrow date range and pruning is excellent. If the data is jumbled, every file covers January to December and nothing can be skipped. Try it below.

Immutability: what an UPDATE really does

Micro-partitions are never modified. Changing one row makes Snowflake write a new copy of the entire micro-partition that contains it. The old file is kept for Time Travel and Fail-safe, and the table's metadata then points to the new set of files.

INTERVIEW TRAP
"Does Snowflake have indexes?" Not in the traditional sense (hybrid tables are the exception). For standard tables, Snowflake relies on micro-partition metadata + pruning, optional clustering keys, and the Search Optimization Service for point lookups.
SENIOR ANGLE
Because of copy-on-write, frequent single-row UPDATEs or DELETEs are expensive: each one rewrites a whole micro-partition, and Time Travel storage grows with it. Batch your changes and use MERGE.
CHAPTER 03

Compute: virtual warehouses & scaling up

01 · WHAT IS IT

A virtual warehouse is a named cluster of compute (CPU, memory and local SSD) that runs your queries, DML and loads. It holds no permanent data. Sizes go from X-Small to 6X-Large. Each size up doubles the compute and the credits per hour.

credits/hr1248163264128256512

Rates shown are for standard (Gen1) warehouses. Gen2 and Snowpark-optimized warehouses use different rates.

02 · WHY WE USE IT
  • Workload isolation: ETL, BI and data science each get their own warehouse, so they never slow each other down.
  • Elasticity: resize in seconds with no data movement.
  • Cost control: a warehouse auto-suspends when idle (costing nothing) and auto-resumes when the next query arrives.
  • Chargeback: one warehouse per team makes it easy to see who spent what.
03 · HOW IT WORKS · SCALING UP

Scaling up (resizing, e.g. M to L) gives a single query more parallel workers, memory and SSD. For big scans and joins, runtime roughly halves each step up while the cost per hour doubles, so the total cost stays about the same but you get the answer faster. That only holds while the query has enough work to split up. A small query can't use 64 workers, so it doesn't get faster but it does get more expensive.

Spilling is the other reason to scale up. When a join or sort doesn't fit in memory, Snowflake spills to local SSD (slower) and then to remote storage (much slower). A bigger warehouse has more memory, so the spilling stops. Look for Bytes spilled to remote storage in the Query Profile.

Resizing affects only new and queued queries. Queries already running finish on the old size.

CHAPTER 04

Scale out: multi-cluster warehouses

01 · WHAT IS IT

A multi-cluster warehouse (Enterprise edition and above) is a single warehouse name backed by several clusters of the same size. You set MIN_CLUSTER_COUNT and MAX_CLUSTER_COUNT, and Snowflake starts or stops clusters automatically as concurrency changes.

  • Auto-scale mode: MIN < MAX (most common).
  • Maximized mode: MIN = MAX, so all clusters run whenever the warehouse is running.
02 · WHY WE USE IT

Each cluster runs only a limited number of queries at once (controlled by MAX_CONCURRENCY_LEVEL, default 8). At 9 AM, when 100 analysts open dashboards, the extra queries queue. A bigger warehouse doesn't fix queuing well. More clusters do.

Rule: scale up for slow queries, scale out for too many queries at once.

03 · HOW IT WORKS · SCALING POLICIES
STANDARD (default): favours speed

Starts a new cluster as soon as a query queues, or when the system detects there's one more query than the running clusters can handle. Each extra cluster starts about 20 s after the previous one. Clusters shut down after 2–3 consecutive checks (one minute apart) show the load can fit on fewer clusters.

ECONOMY: favours credits

Starts a new cluster only if there's enough queued work to keep it busy for at least 6 minutes. Short spikes just queue. Shuts clusters down after 5–6 consecutive checks. Good for batch work where a little waiting is fine.

INTERVIEW TRAP
"Will a multi-cluster warehouse make my single slow query faster?" No. A query runs on one cluster. Extra clusters only absorb more queries. To make one query faster, scale up or fix the query (pruning, joins, spilling).
CHAPTER 05

Cloud services layer · the brain

01 · WHAT IS IT

A set of always-on services, run by Snowflake across multiple availability zones, that coordinate everything: logins, query planning, metadata, transactions and security. It runs on compute that Snowflake manages, not on your warehouses.

02 · WHY WE USE IT

Separating the "thinking" from the "doing" means some work happens without a warehouse at all: metadata queries, result-cache hits, SHOW and DESCRIBE commands, and creating objects. It's also what lets many warehouses work on the same data consistently.

The three caches · asked in almost every interview

01 · WHAT IS IT
CACHELIVES INSTORESLIFETIME
Result cacheCloud servicesFinal result sets of queries24 h, reset on each reuse, max 31 days
Warehouse cacheWarehouse local SSD/RAMRaw micro-partition column dataUntil the warehouse suspends or is resized
MetadataCloud servicesRow counts, MIN/MAX, distinct counts per partitionAlways current
02 · WHY WE USE IT
  • Speed: a result-cache hit returns in milliseconds.
  • Cost: result-cache and metadata answers need no running warehouse, so they cost no warehouse credits.
  • Less I/O: the warehouse cache avoids re-downloading the same micro-partitions from S3 for every query.

Picture a dashboard where 50 people open the same chart. Only the first query actually runs.

03 · HOW IT WORKS · THE LOOKUP ORDER

1. Metadata: can the query be answered from metadata alone? (e.g. COUNT(*), or MIN/MAX on number or date columns). The Query Profile shows METADATA-BASED RESULT.

2. Result cache: is there a saved result for this exact query? It's reused only if all of these are true: the query text matches exactly (adding a table alias, for example, counts as a different query); the underlying data hasn't changed; the query has no non-deterministic functions such as CURRENT_TIMESTAMP(), RANDOM() or UUID_STRING(), and no external functions; the role running it has the required privileges on the objects; and USE_CACHED_RESULT is TRUE. The result can be reused by other users too, as long as their role has the right privileges.

3. Warehouse cache: the warehouse runs the query. Columns from micro-partitions it already read are served from local SSD, and everything else is fetched from remote storage. The Query Profile shows Percentage scanned from cache.

INTERVIEW TRAP
"How do you benchmark a query fairly?" Run ALTER SESSION SET USE_CACHED_RESULT = FALSE; so the result cache doesn't hide the real runtime. Remember the warehouse cache can still be warm, so either suspend and resume the warehouse or compare the warm and cold runs.
SENIOR ANGLE
Auto-suspend vs. cache trade-off: suspending after 60 s saves credits but throws away the warehouse cache. For BI warehouses that serve repeated queries, a longer auto-suspend (e.g. 5–10 min) can be cheaper overall because queries stay fast. For ad-hoc or ETL warehouses, short auto-suspend usually wins.
CHAPTER 07

How billing works · per second, 60 s minimum

01 · WHAT IS IT

Snowflake bills three things separately:

  • Compute: warehouse credits/hour × time running (not time querying). Per-second billing with a 60-second minimum every time a warehouse starts or resumes.
  • Storage: average compressed TB per month, including Time Travel and Fail-safe data.
  • Serverless & cloud services: Snowpipe, automatic clustering, materialized view maintenance, serverless tasks, plus cloud services above the 10% allowance. Data transfer between regions or clouds is billed too.
02 · WHY IT MATTERS

Credit price depends on edition, cloud and region. A warehouse that's running but idle still burns credits. Most surprise bills come from warehouses that never suspend, oversized warehouses, and lots of resumes caused by a query every 50 seconds. Senior engineers are expected to explain and reduce cost.

03 · HOW IT WORKS · TIMELINE

The warehouse resumes when a query arrives, stays running while queries execute, and then waits AUTO_SUSPEND seconds of idle time before suspending. You pay for that idle wait. If a run lasts less than 60 s, you're still billed for 60 s. Click anywhere on the timeline to add a 20-second query and watch the bill change.

CHAPTER 08

Editions · what you get at each tier

01 · WHAT IS IT

Snowflake comes in four editions: Standard, Enterprise, Business Critical and Virtual Private Snowflake (VPS). Each tier includes everything in the tier below it, adds more features, and costs more per credit.

02 · WHY IT MATTERS

Interviewers ask questions like "we need 30-day Time Travel and masking for PII — which edition?" or "we handle healthcare data (HIPAA) — which edition?". Edition choice drives both compliance and cost.
