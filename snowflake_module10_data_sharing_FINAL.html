MODULE 10 · DATA SHARING & COLLABORATION

Share the data.
Never the copy.

Every company needs to give data to someone: a partner, a customer, a supplier, another business unit. The old way was to export a file, send it, and let them load it. This module shows how Snowflake lets another account query your data live, in place, with no copy and no pipeline, and how the same idea grows into listings, the Marketplace, clean rooms and Native Apps.

01 · WHAT IS THE PROBLEM?

Think about sending a report to a colleague. You can email the file as an attachment: they get a copy, it's out of date the moment you change your version, and you've lost control of who forwards it. Or you can share a Google Doc link: there's only one document, they always see the latest version, and you can remove their access whenever you want.

Traditional data exchange is the email attachment: FTP/SFTP drops, CSV extracts, S3 bucket copies, API pulls. Snowflake Secure Data Sharing is the Google Doc link.

02 · WHY SHARING WITHOUT COPYING MATTERS
  • No ETL: no export job, no file transfer, no load job on the other side. Nothing to schedule, monitor or fix at 3 a.m.
  • No stale copies: the consumer reads the same data you see, as soon as your transaction commits.
  • No duplicate storage: the bytes stay in your account. Ten consumers do not mean ten copies.
  • Governance stays with the owner: you choose exactly which tables, columns and rows go out, and you can revoke access instantly.
03 · HOW IS THAT EVEN POSSIBLE?

Remember Module 1: Snowflake separates storage (micro-partitions in cloud object storage), compute (virtual warehouses) and cloud services (metadata, security, optimizer). Because the data files are immutable and the "which files make up this table" list is just metadata, Snowflake can let another account's warehouse read your micro-partitions. All that's actually shared is a set of permissions recorded in cloud services. The consumer brings their own compute, so their queries never slow down your warehouses.

CHAPTER 01

Secure Data Sharing · providers, consumers and the share object

01 · WHAT IS IT

Secure Data Sharing lets one Snowflake account (the provider) give another account (the consumer) read-only access to selected objects without copying or moving any data.

  • A share is a named Snowflake object (CREATE SHARE). Think of it as an envelope of privileges: "USAGE on this database, USAGE on this schema, SELECT on these tables and secure views", plus the list of consumer accounts allowed to open it.
  • The consumer turns the share into a read-only database in their account with CREATE DATABASE … FROM SHARE, then queries it with their own warehouse like any other database.
  • A share points at objects from one database. Secure views in that database can still reference other databases if you grant REFERENCE_USAGE on those databases to the share.
02 · WHY WE USE IT
  • Live data: provider DML is visible to consumers as soon as it commits.
  • Zero copy: no storage is duplicated and nothing has to be kept in sync.
  • Clear cost split: the provider pays storage (it's their data), the consumer pays compute (their warehouse runs the queries). Sharing itself has no extra charge for direct shares in the same region.
  • Fine-grained and revocable: share only a secure view with some columns and rows, and remove a grant or an account at any time with immediate effect.
  • Typical uses: sending data to customers and partners, sharing between business units that have separate accounts, and receiving third-party data (weather, financial, demographic) without building ingestion.
03 · HOW IT WORKS IN THE BACKEND
1 · Metadata, not data

When you GRANT SELECT ON TABLE orders TO SHARE s, cloud services records a privilege. No micro-partition is touched. Creating a share and adding a 50 TB table takes about the same time as adding a 5 MB one.

2 · Consumer compiles, provider's files are read

When the consumer queries, their cloud services layer compiles the plan using the provider's table metadata (partition list, min/max stats), prunes, and their warehouse reads the provider's micro-partitions directly from storage in the same region.

3 · Always the latest version

Every committed DML creates a new table version (new micro-partition list). The consumer's next query simply resolves to the newest version, which is why updates show up "instantly" without any refresh job.

What can go into a share? Databases, schemas, tables (including external, Iceberg and dynamic tables in current releases), secure views, secure materialized views and secure UDFs. Snowflake keeps extending this list, so phrase it as "tables and secure objects, check the current docs for newer object types" in an interview. By default a share accepts only secure views and functions, which leads to the next point.

STEPPER · FROM CREATE SHARE TO THE FIRST CONSUMER QUERY

Why must shared views be secure views?

1 · The definition is hidden

For a regular view, anyone with access can run GET_DDL or look at SHOW VIEWS and read the SQL, including your table names, join logic and the WHERE tenant = … filter. For a secure view, only the owning role sees the definition. Consumers see columns, not logic.

2 · The optimizer can't leak hidden rows

With a regular view the optimizer may push a consumer's filter or function below the view's own filter for speed. A cleverly written function (for example, one that raises an error on certain values) could then reveal rows the view should hide. Secure views block those optimizations, so the view's filter is always applied first.

INTERVIEW TRAP
"Secure views are always slower." Not always, but they can be, because some optimizations are disabled. Use them where hiding logic or rows matters (sharing, row-level filters), not everywhere. Also: a consumer cannot do Time Travel, cloning or DML on a shared database. It's read-only, and history stays with the provider.
SENIOR ANGLE
Database roles in shares. Granting IMPORTED PRIVILEGES on a shared database gives a consumer role everything in it. For finer control, the provider creates database roles inside the shared database (for example sales_db.analyst_r and sales_db.finance_r), grants different objects to each, and grants the database roles to the share. The consumer admin then maps each database role to their own account roles (GRANT DATABASE ROLE partner_sales.finance_r TO ROLE fin_team). One share, different access levels in the consumer account.
CHAPTER 02

Reader accounts · sharing with someone who has no Snowflake

01 · WHAT IS IT

A reader account (also called a managed account) is a small Snowflake account that the provider creates and owns for a consumer who isn't a Snowflake customer. The provider creates it with CREATE MANAGED ACCOUNT … TYPE = READER, adds it to a share, and hands the login details to the consumer.

Inside the reader account the consumer can log in with Snowsight or connect a BI tool, and query the shared data, using warehouses that are set up in that account (usually by the provider).

02 · WHY WE USE IT
  • The partner is a small company, a regulator or an internal team that will never sign a Snowflake contract.
  • You still want the benefits of sharing (live, no files) instead of falling back to CSV exports.
  • You control the whole environment: users, warehouses and spend limits.
03 · HOW IT WORKS · WHO PAYS FOR WHAT

The reader account belongs to the provider's organization billing-wise: all compute used in the reader account is billed to the provider, on top of the storage the provider already pays for. That's the big difference from a full consumer account, where the consumer pays for their own queries. So providers usually create a small warehouse with a short auto-suspend and attach a resource monitor to cap spend.

Read-mostly by design

A reader account exists to query data shared by the provider that created it. It can't load its own data or modify shared data, and it can't become a provider and share data onward.

Admin tasks still exist

Someone has to create users, roles and warehouses inside it. Usually the provider does this with the admin user it created, or delegates it to the consumer admin.

A stepping stone

If the consumer later buys Snowflake, add their full account to the share and drop the reader account. Their queries then run on their own bill.

Exact reader-account restrictions and per-provider limits can change. Check the current docs before quoting a specific number.

CHAPTER 03

Cross-region & cross-cloud · when the consumer lives somewhere else

01 · WHAT IS IT

A Snowflake account lives in one cloud and one region, for example AWS us-east-1 or Azure West Europe. A direct share only works between accounts in the same region of the same cloud, because the consumer's warehouse reads the provider's files directly from that region's storage.

To reach a consumer in another region or another cloud, the data has to be replicated there first. Snowflake gives you two ways to do it:

  • Replication + share: replicate the database to another account you own (same organization) in the target region, then share from that account.
  • Listing with Cross-Cloud Auto-Fulfillment: publish a listing and let Snowflake replicate the data to the consumer's region automatically when needed.
02 · WHY IT WORKS THIS WAY

Reading micro-partitions across continents for every query would be slow, expensive (egress on every scan) and could break data-residency rules. Replicating once and refreshing incrementally keeps queries local and makes the cost predictable.

The trade-off: a replicated share is not instant any more. Consumers see data as of the last refresh, and the provider pays for the data transfer and for storage and refresh compute in the second region.

Replication + share (you control it)

Create a replication group (or use database replication) from the source account to a secondary account in the target region, schedule refreshes, then CREATE SHARE in the secondary account on the replica database. Good for one or a few known partners, or for sharing between your own business units across regions.

Listing + Cross-Cloud Auto-Fulfillment (Snowflake handles it)

You publish the data as a listing and enable auto-fulfillment. When a consumer in another region gets the listing, Snowflake replicates the data product to that region for you and keeps it refreshed on the schedule you set. Good for many consumers, or ones you don't know yet (Marketplace).

INTERVIEW TRAP
"Can I share directly from AWS us-east-1 to an Azure account in the same city?" No. Snowflake regions are cloud-specific, so AWS us-east-1 and Azure East US 2 are different regions. Any cross-cloud or cross-region consumer needs replication or an auto-fulfilled listing.
SENIOR ANGLE
Mention residency and cost governance: replicating customer data to another region can break data-residency commitments, so share only a filtered secure view. Also set the refresh frequency to what the consumer really needs: hourly refreshes of a large, frequently changing table can cost more than the consumer's queries.
CHAPTER 04

Listings & Marketplace · data as a product

01 · WHAT IS IT

A listing wraps a share (or a Native App) in a product page: title, description, data dictionary, sample SQL, refresh frequency, terms of use, and optionally a price. Providers create listings in Provider Studio in Snowsight.

  • Private listing: offered only to specific accounts you name, such as your customers or partners. It's like a direct share with extra polish, plus cross-region auto-fulfillment.
  • Public listing on the Snowflake Marketplace: anyone with a Snowflake account can discover it. Providers have to be approved for public listings.
02 · WHY WE USE IT
  • Self-service: consumers find it, read the docs and click "Get" without a ticket to your team.
  • Reach other regions without managing replication yourself (auto-fulfillment).
  • Monetize: eligible providers can sell data or apps through the Marketplace.
  • Usage insight: providers get analytics on who requested, got and queried their listing.
03 · HOW IT WORKS

Under the hood it's still Secure Data Sharing: the consumer clicks Get, chooses a database name, and Snowflake creates a read-only database from the listing's share in their account (replicated to their region first if needed). Access types you'll hear about:

Free

Instant access once the consumer accepts the terms.

Limited trial / paid

Trial access or paid plans billed through Snowflake. Availability depends on provider eligibility and region.

Personalized / by request

The consumer requests access, and the provider approves and may prepare consumer-specific data, such as their own records only.

Usage metrics: providers can see listing analytics in Provider Studio and query views in the SNOWFLAKE.DATA_SHARING_USAGE schema, such as LISTING_ACCESS_HISTORY and listing consumption views. These give counts and which objects were accessed by which consumer account. They don't give the consumer's query text. View names and latency evolve, so say "data sharing usage views" if you're unsure of the exact name.

    CHAPTER 05

    Data Clean Rooms · collaborate without revealing raw rows

    01 · WHAT IS IT

    A data clean room is a controlled environment where two or more parties can analyze their combined data (for example "how many of my customers also saw your ad?") while neither side can see the other's raw rows. Only approved, aggregated results come out.

    Snowflake offers Snowflake Data Clean Rooms as a managed product (built on the Native App Framework), and the building blocks underneath are features you can also use yourself: secure sharing, secure views and functions, and privacy policies such as aggregation policies and projection policies.

    02 · WHY WE USE IT
    • Advertising and media: audience overlap, campaign reach and attribution between an advertiser and a publisher.
    • Retail and CPG: a brand and a retailer measure joint customers without exchanging customer lists.
    • Healthcare and finance: joint research or fraud signals where raw records can't legally leave the owner.
    • It replaces the risky old method of sending hashed email lists to a third party.
    03 · HOW IT WORKS (CONCEPTUALLY)
    • Data stays put: each party's data stays in its own account. The clean room uses sharing, so there's no bulk copy.
    • Only approved queries run: analyses are defined as templates (parameterized SQL that both sides approve), such as an overlap count or reach by segment. Free-form SELECT * against the other party's data is not allowed.
    • Aggregation thresholds: results are returned only for groups with at least k individuals. Small groups are suppressed, because a group of one is just a person.
    • Join keys are protected: joins typically use hashed or tokenized identifiers, and policies can prevent the join key itself from being projected in output.
    • Some offerings add extra techniques such as differential privacy noise. Details vary by product and release, so describe them as optional.

    "Hashing the emails is enough, so why do we need a clean room?" Because hashes of emails are easy to reverse by hashing a list of known emails and matching. And even with perfect hashing, an unrestricted query like "overlap where zip = 94105 and age = 37" can single out one person. Clean rooms combine restricted templates + thresholds + no raw output.
    CHAPTER 06

    Native Apps · sharing logic, not just data

    01 · WHAT IS IT

    The Snowflake Native App Framework lets a provider package code plus (optionally) data into an application that consumers install inside their own Snowflake account. The app can contain stored procedures, UDFs, views, tasks, a Streamlit UI and, in newer releases, containers.

    • Application package: the provider-side container holding versions of the app.
    • Manifest file (manifest.yml): describes the app, its setup script, and the privileges or references it will ask the consumer for.
    • Setup script (setup.sql): runs in the consumer account when the app is installed or upgraded, and creates the app's objects.
    • Versions and patches plus a release directive: which version consumers get.
    02 · WHY WE USE IT
    • Bring the code to the data: the consumer's sensitive data never leaves their account. The app runs next to it.
    • Protect the provider's IP: the consumer can use the app without reading its source (depending on how objects are exposed).
    • One distribution channel: publish through private listings or the Marketplace, with versioned upgrades.
    • Examples: a data-quality scanner, a forecasting tool, an identity-resolution engine, or the managed clean room product itself.

    CHAPTER 07

    Governance in sharing · who sees which rows, and for how long

    01 · WHAT IS IT

    Sharing doesn't switch off your security. The provider's masking policies, row access policies and secure-view filters are enforced when consumers query the shared objects, because the policy belongs to the object, not to the account that queries it.

    The classic pattern is the multi-tenant share: one table holds data for many customers, one secure view filters rows by CURRENT_ACCOUNT(), and every consumer account automatically sees only its own rows.

    02 · WHY WE USE IT
    • One object for 500 customers instead of 500 views or 500 shares, so onboarding a customer is just one row in an entitlements table plus ADD ACCOUNTS.
    • Defence in depth: PII stays masked even if a view is granted by mistake.
    • Instant off-boarding: remove an account or revoke a grant and access stops on the next query.
    • Audit: show regulators exactly what each consumer can see.
    03 · HOW IT WORKS

    In the consumer's session, CURRENT_ACCOUNT() returns the consumer's account locator, so a secure view can join to an entitlements table: WHERE e.consumer_account = CURRENT_ACCOUNT(). The provider can test this without a real consumer with ALTER SESSION SET SIMULATED_DATA_SHARING_CONSUMER = '<account>'.

    Careful with role-based logic: your account's role names mean nothing in the consumer account, so policies written as CURRENT_ROLE() IN ('PII_READER') won't behave as you expect for consumers (they typically fall through to the masked branch). Base sharing logic on CURRENT_ACCOUNT(), or on shared database roles checked with IS_DATABASE_ROLE_IN_SESSION(). Check the docs for the exact behaviour of context functions in shared queries.

    Revoking and monitoring

    Revoke

    REVOKE SELECT ON VIEW … FROM SHARE s removes one object, ALTER SHARE s REMOVE ACCOUNTS = … removes one consumer, and DROP SHARE s removes everyone. Changes take effect on the consumer's next query. There's no copy left behind to chase.

    Inspect

    SHOW SHARES (outbound and inbound), DESC SHARE s and SHOW GRANTS TO SHARE s list exactly what's exposed and to whom. Review them periodically, like access reviews for users.

    Monitor

    For listings, providers get consumer-level usage through the data sharing usage views and Provider Studio. For direct shares, visibility into consumer queries is limited, since the consumer's query history is theirs. Consumers audit their own reads with ACCOUNT_USAGE.ACCESS_HISTORY.

    INTERVIEW TRAP
    "Can the consumer re-share my data to a third account?" No. Objects in a database created from a share can't be added to the consumer's own shares. The consumer could still copy the data with CTAS into their own table (and then share that), so contracts and masking still matter. Sharing controls access, not what a legitimate user does with results.
    SENIOR ANGLE
    Business Critical caveat: by default, a provider on Business Critical edition can't share to a consumer on a lower edition. This can be overridden per consumer with the SHARE_RESTRICTIONS option on ADD ACCOUNTS, which needs a special privilege. Mention it as a compliance decision, not a technical shortcut.
