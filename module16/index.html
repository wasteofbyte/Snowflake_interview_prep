Chapter 01

Terraform for Snowflake

01

What is it

Using HashiCorp Terraform with the snowflake-labs/snowflake provider to define and manage Snowflake objects (warehouses, databases, schemas, roles, grants, users, resource monitors) declaratively in .tf files.

02

Why it matters

Without IaC, Snowflake object creation is undocumented, manual, and environment-inconsistent. Terraform makes infrastructure peer-reviewed, version-controlled, auditable, and idempotent — the same terraform apply can be run repeatedly without side effects.

03

How it works

Terraform reads .tf files, computes a diff against the last known state (stored in a state file), and applies only the changes. The Snowflake provider translates each resource block into Snowflake DDL/DML operations via the Snowflake REST API.

Provider configuration

# versions.tf
terraform {
  required_providers {
    snowflake = {
      source  = "snowflake-labs/snowflake"
      version = "~> 0.90"
    }
  }
  # Store state remotely — never commit state files to git
  backend "s3" {
    bucket = "my-terraform-state"
    key    = "snowflake/prod/terraform.tfstate"
    region = "us-east-1"
  }
}

# provider.tf — credentials via environment variables
provider "snowflake" {
  account  = var.snowflake_account   # e.g. "myorg-prod"
  username = var.snowflake_user
  # Prefer key-pair auth — set SNOWFLAKE_PRIVATE_KEY_PATH env var
  role     = "TERRAFORM_ROLE"         # a role with SYSADMIN + SECURITYADMIN delegated
}

Core resources

# warehouses.tf
resource "snowflake_warehouse" "transform_wh" {
  name           = "TRANSFORM_WH"
  warehouse_size = "MEDIUM"
  auto_suspend   = 120
  auto_resume    = true
  initially_suspended = true
  comment        = "dbt transformation warehouse"
}

# databases.tf
resource "snowflake_database" "analytics" {
  name                        = "ANALYTICS"
  data_retention_time_in_days = 7
}

resource "snowflake_schema" "gold" {
  database = snowflake_database.analytics.name
  name     = "GOLD"
}

# roles.tf
resource "snowflake_role" "analyst_role" {
  name = "ANALYST_ROLE"
}

resource "snowflake_grant_privileges_to_role" "analyst_usage_db" {
  privileges = ["USAGE"]
  role_name  = snowflake_role.analyst_role.name
  on_account_object {
    object_type = "DATABASE"
    object_name = snowflake_database.analytics.name
  }
}

resource "snowflake_grant_privileges_to_role" "analyst_select_gold" {
  privileges = ["SELECT"]
  role_name  = snowflake_role.analyst_role.name
  on_schema_object {
    all {
      object_type_plural = "TABLES"
      in_schema          = "ANALYTICS.GOLD"
    }
  }
}

# resource_monitors.tf
resource "snowflake_resource_monitor" "prod_monitor" {
  name         = "PROD_CREDIT_MONITOR"
  credit_quota = 1000
  frequency    = "MONTHLY"
  start_timestamp = "2024-01-01 00:00"
  notify_triggers = [75, 90]
  suspend_triggers         = [100]
  suspend_immediate_triggers = [110]
  notify_users = ["data_eng_lead"]
}

Future grants (for new objects automatically)

# Grant SELECT on all FUTURE tables in the schema to analyst role
resource "snowflake_grant_privileges_to_role" "analyst_future_tables" {
  privileges = ["SELECT"]
  role_name  = snowflake_role.analyst_role.name
  on_schema_object {
    future {
      object_type_plural = "TABLES"
      in_schema          = "ANALYTICS.GOLD"
    }
  }
}

Interview trap — Terraform state drift

If someone manually runs an ALTER WAREHOUSE in Snowflake after the last terraform apply, the Terraform state is stale. The next terraform plan will show a diff and terraform apply will revert the manual change. Discipline: all Snowflake object changes must go through Terraform. For one-off emergency changes, run terraform import immediately after to sync state.

Senior angle — TERRAFORM_ROLE design

Terraform needs a role with SYSADMIN (create databases, schemas, tables, warehouses) + SECURITYADMIN (create roles, grant privileges) + ACCOUNTADMIN (resource monitors, network policies). Create a dedicated TERRAFORM_ROLE and grant it those inherited roles. The Terraform service user should use key-pair auth, have no interactive login rights, and be rotated on a schedule. Store the private key in Vault or AWS Secrets Manager — inject via environment variable at pipeline runtime, never hardcode in .tf files.

Chapter 02

Snowflake Native Git Integration

01

What is it

A Snowflake object (GIT REPOSITORY) that connects Snowflake to a GitHub, GitLab, or Bitbucket repository. Files in the repo — SQL scripts, Python scripts, Snowpark code — can be fetched and executed directly inside Snowflake without staging.

02

Why it matters

Closes the loop between source control and execution. You can run a .sql file from your GitHub repo in a Snowflake Task or Stored Procedure without copying it to a stage first — the git object handles the fetch.

03

How it works

Snowflake holds a periodic or on-demand clone of the repo. Files are accessed via the special @<repo_name>/branches/<branch>/<path> stage syntax. Changes are pulled in with ALTER GIT REPOSITORY ... FETCH.

Setup: Git Integration from GitHub

-- Step 1: Create a secret to hold your GitHub PAT (Personal Access Token)
USE ROLE SYSADMIN;
CREATE OR REPLACE SECRET github_pat
  TYPE = PASSWORD
  USERNAME = 'sf-svc-account'          -- GitHub username
  PASSWORD = 'ghp_xxxxxxxxxxxxxxxxxxxx';  -- GitHub PAT with repo:read scope

-- Step 2: Create an API Integration for GitHub
USE ROLE ACCOUNTADMIN;
CREATE OR REPLACE API INTEGRATION github_integration
  API_PROVIDER = git_https_api
  API_ALLOWED_PREFIXES = ('https://github.com/my-org/')
  ALLOWED_AUTHENTICATION_SECRETS = (github_pat)
  ENABLED = TRUE;

-- Step 3: Create the Git Repository object
USE ROLE SYSADMIN;
CREATE OR REPLACE GIT REPOSITORY snowflake_pipelines
  API_INTEGRATION = github_integration
  GIT_CREDENTIALS = github_pat
  ORIGIN = 'https://github.com/my-org/snowflake-pipelines.git';

-- Step 4: Fetch the latest commits
ALTER GIT REPOSITORY snowflake_pipelines FETCH;

-- Step 5: List files in the repo
LS @snowflake_pipelines/branches/main/;

-- Step 6: Execute a SQL file from the repo directly
EXECUTE IMMEDIATE FROM
  @snowflake_pipelines/branches/main/sql/transforms/curate_sales.sql;

Use in a Task (automated nightly run from git)

CREATE OR REPLACE TASK nightly_transform
  WAREHOUSE = TRANSFORM_WH
  SCHEDULE = 'USING CRON 0 2 * * * America/New_York'
AS
  EXECUTE IMMEDIATE FROM
    @snowflake_pipelines/branches/main/sql/transforms/nightly_rollup.sql;

ALTER TASK nightly_transform RESUME;

Interview trap — branch vs tag

Pointing a production Task at branches/main means every FETCH brings in the latest commits — including bad ones. For production stability, point Tasks at a tagged release: @snowflake_pipelines/tags/v1.4.2/sql/.... Promote a tag as part of your release process, not a floating branch reference.

Chapter 03

dbt + Airflow / Prefect / Dagster

01

What is it

Using an orchestrator (Airflow, Prefect, or Dagster) to schedule, sequence, and monitor dbt runs against Snowflake — combining dbt's SQL transform logic with an orchestrator's dependency management, alerting, and observability.

02

Why it matters

dbt Cloud Scheduler is simple but limited: it cannot coordinate dbt with upstream ingestion jobs, branch on conditions, fan out/in, or react to external events. Orchestrators unlock full DAG control over the entire data pipeline.

03

Key patterns

Trigger dbt after a Snowpipe/Kafka ingestion succeeds. Run dbt tests after models complete; fail the DAG if tests fail. Parameterise dbt runs by date range for backfills. Alert on model latency or test failures via Slack/PagerDuty.

Airflow + dbt (using the dbt CLI operator)

# dags/dbt_snowflake_pipeline.py
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.sensors.external_task import ExternalTaskSensor
from datetime import datetime, timedelta

with DAG(
    'dbt_snowflake',
    schedule_interval='0 4 * * *',
    start_date=datetime(2024, 1, 1),
    catchup=False,
    default_args={'retries': 1, 'retry_delay': timedelta(minutes=5)},
) as dag:

    # Wait for the ingestion DAG to complete
    wait_ingestion = ExternalTaskSensor(
        task_id='wait_for_ingestion',
        external_dag_id='kafka_to_snowflake',
        external_task_id='validate_load',
        timeout=3600,
    )

    # Run dbt staging models
    dbt_stage = BashOperator(
        task_id='dbt_run_staging',
        bash_command='cd /opt/dbt && dbt run --select staging --target prod',
    )

    # Run dbt mart models after staging
    dbt_marts = BashOperator(
        task_id='dbt_run_marts',
        bash_command='cd /opt/dbt && dbt run --select marts --target prod',
    )

    # Run dbt tests — fail the DAG if any test fails
    dbt_test = BashOperator(
        task_id='dbt_test',
        bash_command='cd /opt/dbt && dbt test --target prod',
    )

    wait_ingestion >> dbt_stage >> dbt_marts >> dbt_test

Senior angle — Cosmos (Airflow + dbt)

Astronomer's Cosmos library automatically converts each dbt model into an individual Airflow task, preserving the dbt DAG topology. This means per-model retries, per-model run time visibility, and dependency-aware partial re-runs — without maintaining a separate Airflow DAG definition. For large dbt projects (100+ models), Cosmos is the recommended Airflow approach over calling dbt run as a single BashOperator.

Interview trap — dbt run vs dbt build

dbt run materialises models only. dbt build runs models, tests, seeds, and snapshots in DAG order — a single command for a full pipeline. In production CI/CD, dbt build --select state:modified+ runs only the modified models and their downstream dependents, reducing run time dramatically for large projects.

Chapter 04

CI/CD Pipelines for Schema Migrations

01

What is it

Automating the testing and deployment of Snowflake schema changes (new tables, model changes, grants, dbt model updates) through a Git-based pipeline — PR open → CI → merge → CD.

02

Why it matters

Manual DDL deployments are error-prone and hard to audit. A CI/CD pipeline ensures every change is tested, peer-reviewed, and applied consistently across dev/test/prod accounts without human error.

03

Pattern overview

PR opens → CI builds a zero-copy clone of prod, runs dbt build --defer, runs dbt test → merge to main → CD applies to prod via Terraform plan/apply + dbt build. Infrastructure changes and model changes in the same PR.

Full GitHub Actions CI/CD pipeline

# .github/workflows/snowflake_ci_cd.yml
name: Snowflake CI/CD

on:
  pull_request:
    branches: [ main ]
  push:
    branches: [ main ]

env:
  SNOWFLAKE_ACCOUNT:  ${{ secrets.SNOWFLAKE_ACCOUNT }}
  SNOWFLAKE_USER:     ${{ secrets.SNOWFLAKE_USER }}
  SNOWFLAKE_PRIVATE_KEY: ${{ secrets.SNOWFLAKE_PRIVATE_KEY }}

jobs:
  ci:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python + dbt
        run: |
          pip install dbt-snowflake==1.8.0

      - name: Terraform init + validate (infrastructure changes)
        run: |
          terraform -chdir=infra init
          terraform -chdir=infra validate
          terraform -chdir=infra plan -out=tfplan

      - name: Create PR clone (zero-copy clone of prod for testing)
        run: |
          snowsql -q "
            CREATE OR REPLACE DATABASE PR_${{ github.event.number }}_ANALYTICS
              CLONE ANALYTICS;
          "

      - name: dbt build on clone (CI target points to PR clone)
        run: |
          dbt build --target ci \
                    --vars '{"database": "PR_${{ github.event.number }}_ANALYTICS"}' \
                    --select state:modified+

      - name: Cleanup PR clone
        if: always()
        run: |
          snowsql -q "DROP DATABASE IF EXISTS PR_${{ github.event.number }}_ANALYTICS;"

  cd:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Terraform apply (infrastructure to prod)
        run: |
          terraform -chdir=infra init
          terraform -chdir=infra apply -auto-approve

      - name: dbt build to prod
        run: |
          dbt build --target prod

      - name: Fetch git repository in Snowflake
        run: |
          snowsql -q "ALTER GIT REPOSITORY snowflake_pipelines FETCH;"

Blue/green deployment for zero-downtime schema changes

-- Blue is PRODUCTION (live traffic hits this)
-- Green is STAGING (new version deployed and tested here)

-- Step 1: Clone blue to green
CREATE DATABASE ANALYTICS_GREEN CLONE ANALYTICS;

-- Step 2: Run dbt build against green
-- dbt build --target prod --vars '{"database": "ANALYTICS_GREEN"}'

-- Step 3: Run validation queries against green
-- SELECT COUNT(*) FROM ANALYTICS_GREEN.GOLD.SALES_FACT = expected

-- Step 4: Atomic swap (rename = zero downtime)
ALTER DATABASE ANALYTICS RENAME TO ANALYTICS_OLD;
ALTER DATABASE ANALYTICS_GREEN RENAME TO ANALYTICS;

-- Step 5: Rollback if needed (reverse swap)
ALTER DATABASE ANALYTICS RENAME TO ANALYTICS_GREEN;
ALTER DATABASE ANALYTICS_OLD RENAME TO ANALYTICS;

-- Step 6: Drop old database after confidence period
DROP DATABASE ANALYTICS_OLD;

Interview trap — dbt state:modified+ in CI

dbt build --select state:modified+ selects the modified models and all their downstream dependents. It requires a manifest.json from the last successful prod run to compare against. In CI, download the prod manifest artifact (stored in S3 or dbt Cloud) and pass it via --state /path/to/prod/manifest/. Without the prod manifest, the state selector falls back to running everything.

Chapter 05 · Lab

Hands-on: Terraform Snowflake objects + CI/CD flow

This lab walks through the Terraform file structure for a production Snowflake account, and the SQL steps that mirror what a CI/CD pipeline does (clone → test → swap).

1

Understand the Terraform file structure

A well-organised Terraform repo for Snowflake follows this layout:

snowflake-iac/
├── environments/
│   ├── dev/
│   │   ├── main.tf         # calls modules with dev-sized warehouses
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   └── prod/
│       ├── main.tf
│       ├── variables.tf
│       └── terraform.tfvars
├── modules/
│   ├── warehouse/          # reusable warehouse module
│   ├── database/           # reusable database + schema module
│   ├── role/               # reusable role + grant module
│   └── resource_monitor/   # reusable monitor module
└── versions.tf
The key principle: environments/ are thin wrappers that pass environment-specific variables (account, warehouse size, credit quota) to shared modules/. Modules are reused across dev and prod without duplication.
2

Write a reusable warehouse module

# modules/warehouse/main.tf
variable "name"           {}
variable "size"           { default = "XSMALL" }
variable "auto_suspend"   { default = 120 }
variable "max_cluster_count" { default = 1 }

resource "snowflake_warehouse" "this" {
  name                = var.name
  warehouse_size      = var.size
  auto_suspend        = var.auto_suspend
  auto_resume         = true
  initially_suspended = true
  max_cluster_count   = var.max_cluster_count
  min_cluster_count   = 1
}

output "name" { value = snowflake_warehouse.this.name }

# environments/prod/main.tf
module "transform_wh" {
  source         = "../../modules/warehouse"
  name           = "PROD_TRANSFORM_WH"
  size           = "LARGE"
  max_cluster_count = 3
}

module "adhoc_wh" {
  source       = "../../modules/warehouse"
  name         = "PROD_ADHOC_WH"
  size         = "MEDIUM"
  auto_suspend = 60
}
terraform plan shows 2 warehouse resources to be created with the prod-specific sizes.
Renaming a Terraform resource block (e.g., "transform_wh" → "prod_transform_wh") causes Terraform to plan a destroy + create, which triggers a brief outage if the warehouse is in use. Use terraform state mv to rename in state without touching Snowflake.
3

Simulate CI: PR clone → test → cleanup (SQL steps)

USE ROLE SYSADMIN;
USE WAREHOUSE COMPUTE_WH;

-- CI Step 1: Create PR clone (simulating PR #42)
CREATE OR REPLACE DATABASE PR_42_ANALYTICS
  CLONE ANALYTICS;

-- CI Step 2: Run your dbt models against the clone
-- (In real CI: dbt build --target ci --vars '{"database":"PR_42_ANALYTICS"}')
-- For this lab, manually create a test table in the clone
CREATE TABLE PR_42_ANALYTICS.PUBLIC.test_new_model AS
  SELECT 1 AS id, 'test' AS label;

-- CI Step 3: Run validation checks
SELECT COUNT(*) FROM PR_42_ANALYTICS.PUBLIC.test_new_model; -- expect 1

-- CI Step 4: Cleanup clone (always, even on failure)
DROP DATABASE IF EXISTS PR_42_ANALYTICS;
PR_42_ANALYTICS drops cleanly. Zero orphaned clones means zero ongoing storage cost.
4

Simulate CD: blue/green deployment

-- Set up two databases representing blue (prod) and green (new version)
CREATE OR REPLACE DATABASE ANALYTICS_BLUE;
CREATE TABLE ANALYTICS_BLUE.PUBLIC.sales_fact (id INT, amount FLOAT);
INSERT INTO ANALYTICS_BLUE.PUBLIC.sales_fact VALUES (1, 100), (2, 200);

-- Step 1: Clone blue to green and deploy new version
CREATE OR REPLACE DATABASE ANALYTICS_GREEN
  CLONE ANALYTICS_BLUE;

-- Simulate deploying a new model column in green
ALTER TABLE ANALYTICS_GREEN.PUBLIC.sales_fact
  ADD COLUMN region VARCHAR;
UPDATE ANALYTICS_GREEN.PUBLIC.sales_fact SET region = 'EAST';

-- Step 2: Validate green
SELECT * FROM ANALYTICS_GREEN.PUBLIC.sales_fact;

-- Step 3: Atomic swap — zero downtime
ALTER DATABASE ANALYTICS_BLUE  RENAME TO ANALYTICS_OLD;
ALTER DATABASE ANALYTICS_GREEN RENAME TO ANALYTICS_BLUE;

-- Step 4: Confirm production is now the new version
SELECT * FROM ANALYTICS_BLUE.PUBLIC.sales_fact;
-- Should now include the region column

-- Step 5: Cleanup
DROP DATABASE IF EXISTS ANALYTICS_OLD;
DROP DATABASE IF EXISTS ANALYTICS_BLUE;
After the swap, ANALYTICS_BLUE.PUBLIC.sales_fact has the region column. ANALYTICS_OLD is the rollback option until dropped.
Chapter 06

Interview Q&A

What is Terraform state and why must you never commit it to git? FUNDAMENTAL
Terraform state (terraform.tfstate) is a JSON file mapping your .tf resource definitions to real Snowflake objects. It contains the current attribute values of every managed resource. It must NOT be in git because: (1) it may contain sensitive values (passwords, private keys) in plaintext, (2) concurrent team members will conflict on the file, causing state corruption. Store state remotely in S3 (with DynamoDB locking), Azure Blob, or Terraform Cloud. Use state encryption at rest.
How does dbt --select state:modified+ work and what does it need? TRICKY
It selects models whose compiled SQL has changed since the last run, plus all their downstream dependents (the + suffix). It requires a manifest.json from the last successful run as the baseline for comparison — passed via --state /path/to/baseline/. In CI/CD: download the prod manifest from S3 (or dbt Cloud artifact) before running dbt, so CI only tests what actually changed. Without the baseline manifest, the selector falls back to running all models.
What happens if you run terraform apply and someone has manually changed a Snowflake warehouse size? SCENARIO
Terraform plan will show a drift: "warehouse_size: LARGE → MEDIUM (config) = change". Terraform apply will revert the warehouse to MEDIUM as defined in the .tf file, overwriting the manual change. This is intentional — Terraform is the source of truth. To prevent this in emergency scenarios: make the emergency change, immediately run terraform import to sync state, then update the .tf file and commit via PR. Never leave state and code out of sync.
Compare Airflow, Prefect, and Dagster for orchestrating a dbt Snowflake pipeline. SCENARIO
Airflow: most widely adopted, best ecosystem, Cosmos library makes dbt integration first-class with per-model tasks. Requires infrastructure management (Kubernetes). Prefect: Python-native, easy local development, dynamic task mapping, good cloud option. Best for Python-heavy teams. Dagster: asset-based model aligns perfectly with dbt's declarative approach; best lineage visualization; @dbt_assets decorator maps every dbt model to a Dagster asset automatically. Recommend: Dagster for new data platform projects; Airflow+Cosmos for teams already on Airflow; Prefect for smaller teams wanting low ops overhead. All three support Snowflake natively via dbt's Snowflake adapter.
What is the Snowflake Git Integration and when would you use it? FUNDAMENTAL
A GIT REPOSITORY object that connects Snowflake to a GitHub/GitLab repo. Use it to: (1) EXECUTE IMMEDIATE FROM @repo/branches/main/sql/transform.sql — run SQL scripts directly from git without staging. (2) Run Snowpark Python scripts from git in a Task. (3) Reference dbt or migration SQL scripts in a Snowflake-native workflow. Best suited for Snowflake-centric teams who want to manage SQL pipelines without an external orchestrator. For cross-system pipelines (Kafka + Snowflake + downstream APIs), an external orchestrator is still better.
What is the blue/green deployment pattern and what makes it safe? TRICKY
Blue = production (live). Green = new version being deployed. Steps: (1) Clone blue to green (zero-copy, instant). (2) Deploy and test new code against green. (3) Atomic rename: blue → old, green → blue. Downstream tools continue pointing to ANALYTICS (which is now the new version). Rollback: reverse the rename in seconds. What makes it safe: (a) the rename is atomic — no partial state visible to queries, (b) zero-copy cloning means no data duplication cost, (c) the old database persists for rollback with no extra storage until deleted. The only window of risk is the rename itself, which is a metadata operation (sub-second).
How do you manage secrets (Snowflake passwords, private keys) in GitHub Actions? TRICKY
Store secrets in GitHub Actions Secrets (Settings → Secrets and variables → Actions). Reference as ${{ secrets.SNOWFLAKE_PRIVATE_KEY }} in the workflow YAML — GitHub never logs these values. For the RSA private key: generate the key pair, add the public key to the Snowflake service user, store the private key PEM string as a GitHub secret. In the workflow step, write it to a temp file: echo "$SNOWFLAKE_PRIVATE_KEY" > /tmp/sf_key.pem. At the enterprise level, prefer AWS Secrets Manager or HashiCorp Vault with OIDC federated auth — the pipeline gets a short-lived token, not a stored credential.
Chapter 07

Quiz

1. Why must Terraform state files never be committed to git?

✓ State files may contain plaintext secrets and cause team conflicts. Store remotely in S3/Azure Blob/Terraform Cloud with locking.

2. In a blue/green deployment, what does the atomic rename step achieve?

✓ ALTER DATABASE RENAME is a metadata-only, sub-second operation. Tools pointing to the original name instantly see the new version. The old database remains for rollback.

3. dbt build --select state:modified+ requires which file from the previous run?

✓ manifest.json is the compilation artifact that describes all models, their compiled SQL, and DAG dependencies. The state selector diffs the new manifest against it.

4. What is Astronomer Cosmos used for?

✓ Cosmos parses your dbt project and renders each model as a task in Airflow, inheriting dbt dependencies. This enables per-model retries, run-time visibility, and partial re-runs in Airflow.

5. In Snowflake's Git Integration, pointing a production Task at branches/main creates what risk?

✓ A floating branch reference means untested commits go straight to prod. Use tagged releases (@repo/tags/v1.4.2/...) and promote tags as part of your release process.

snowflake-labs/snowflake provider. Resources: snowflake_warehouse, snowflake_database, snowflake_role, snowflake_grant_privileges_to_role, snowflake_resource_monitor. State in S3 + DynamoDB lock. Never commit state to git.

Git Integration

CREATE GIT REPOSITORY → FETCH to sync. Access via @repo/branches/main/ or @repo/tags/v1.2.0/. EXECUTE IMMEDIATE FROM @repo/... to run SQL from git. Point prod Tasks at tags, not branches.

dbt + Airflow

BashOperator(dbt run/build) or Cosmos (per-model tasks). dbt build = run + test + seed + snapshot in DAG order. state:modified+ for CI efficiency — requires manifest.json baseline.

Orchestrator choice

Dagster = best dbt native UX + asset lineage. Airflow+Cosmos = most ecosystem. Prefect = easiest Python dev. dbt Cloud = no infra, limited cross-system dependencies.

CI pipeline

PR open → clone prod → dbt build --select state:modified+ → dbt test → drop clone. Store PR clone cost: zero (metadata only until writes). Always drop in finally/always step.

CD pipeline

Merge to main → terraform apply → dbt build --target prod. Optionally: blue/green swap (clone → deploy → rename → keep old for rollback).

Blue/green

Clone PROD → PROD_GREEN. Deploy to green. Validate. ALTER DATABASE PROD RENAME TO PROD_OLD; ALTER DATABASE PROD_GREEN RENAME TO PROD. Rollback = reverse rename. Drop old after confidence period.
