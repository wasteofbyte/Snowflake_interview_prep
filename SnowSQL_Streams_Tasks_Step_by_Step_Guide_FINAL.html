What you'll build

  • A least-privilege lab environment: role, XSMALL warehouse, STAGING + ANALYTICS schemas.
  • A SnowSQL workflow: connect, !set/!define, PUT hourly CSVs into an internal stage, batch-run a script with -f.
  • Idempotent loads with COPY INTO, lineage columns, validation, schema drift (MATCH_BY_COLUMN_NAME) and a corrupt row handled by ON_ERROR = 'CONTINUE'.
  • CDC with a standard, an append-only and a downstream stream; offsets that move only on COMMIT.
  • A 3-task DAG: TSK_MERGE_INVENTORY → TSK_LOAD_PRICE_HISTORY, plus fan-in TSK_SNAPSHOT — monitored with TASK_HISTORY.

Prerequisites

  • The simulator file of this kit (runs offline in any modern browser) — or a Snowflake trial account with ACCOUNTADMIN and SnowSQL installed.
  • Comfortable with basic SQL: SELECT, JOIN, GROUP BY, window functions.
  • Know the difference between a role, a warehouse and a database (step 1 recaps it).
  • Optional: a terminal you are comfortable in, for running the same commands against a real account.

The big picture

Architecture overview

Hourly CSV exports leave a laptop through SnowSQL, land in an internal stage, and are copied into a raw table. Streams record what changed; a task graph turns those changes into clean analytics tables — and only spends compute when there is something to do.

Setup

Goal

Create a least-privilege role LAB_ANALYST, an XSMALL warehouse LAB_WH, and the RETAILPULSE_LAB database with a STAGING (raw landing) and ANALYTICS (clean, typed) schema. Then switch your session to that context.

Why it matters

Production pipelines never run as ACCOUNTADMIN. A dedicated role owns the objects, and a small warehouse with AUTO_SUSPEND = 60 only bills while queries run (per second, 60 s minimum on resume). Splitting STAGING from ANALYTICS is the classic medallion split: raw stays replayable, consumers only see curated tables.

Pitfalls & hint

Run the whole script, not just one line. IF NOT EXISTS makes it safe to re-run. Pitfalls: GRANT ... ON ALL SCHEMAS only covers schemas that exist now (use ON FUTURE SCHEMAS in real life), and EXECUTE TASK is an account-level privilege — without it, ALTER TASK ... RESUME fails later.

GRANT ROLE LAB_ANALYST TO USER lets you USE ROLE it; every object you create afterwards is owned by that role. The session context (role, warehouse, database, schema) is what unqualified names resolve against.

Pitfalls & hint

-a is the account identifier (orgname-account or locator.region), not a URL. In real life store credentials in ~/.snowsql/config under a named connection and use snowsql -c retailpulse. Prefer key-pair auth (private_key_path) for automation. Never pass a password on the command line. !-commands like !set are handled by SnowSQL and never reach the server. The session token stays alive while the terminal is open, and the connection can now push files with PUT.

Pitfalls & hint

Try PUT in the worksheet once: it fails because PUT is client-side and only works from SnowSQL or a driver. AUTO_COMPRESS=FALSE keeps the name .csv. With the default (TRUE) the file is gzipped to .csv.gz and your FILES = (...) list must use that name. Without OVERWRITE=TRUE, re-putting a file with the same MD5 is SKIPPED.

Under the hood

Nothing has been loaded into a table yet. The file just sits in the stage. LIST reads the stage directory metadata: name (prefixed with the stage path), size, md5 and last_modified. The MD5 lets PUT skip unchanged files and lets COPY recognise which files it already loaded.

Goal

Define a reusable CSV file format STAGING.FF_CSV_INVENTORY and an all-VARCHAR raw table STAGING.INVENTORY_RAW with lineage columns _src_file, _src_row, _loaded_at.

Why it matters

A raw layer typed as strings never rejects a row because of a bad number or date. You land everything and cast later with TRY_ functions. Lineage columns answer "which file and line did this come from?" during incidents, and let you reprocess a single file.

Pitfalls & hint

(a) returns zero rows, which means zero errors, and loads nothing. VALIDATION_MODE doesn't support transform COPYs, which is why (a) is a plain COPY. Run (b) twice: the second run says Copy executed with 0 files processed. FORCE = TRUE would override that and duplicate your 30 rows, so don't.

Under the hood

A re-run skips files whose metadata says LOADED, so the statement returns "0 files processed". Changing the file content (new MD5) or using FORCE = TRUE loads it again. METADATA$FILE_ROW_NUMBER is the 1-based data-row number, which gives you exact line-level lineage.

Goal

Create the clean, typed ANALYTICS.INVENTORY table with CTAS. Cast with TRY_TO_NUMBER / TRY_TO_TIMESTAMP and keep exactly one row per product with QUALIFY ROW_NUMBER().

Why it matters

Consumers (BI, replenishment models) need real numeric and timestamp types and one current row per product. TRY_ casts turn bad values into NULL instead of failing the whole pipeline. You can then find those NULLs with data-quality checks.

Pitfalls & hint

Check the DESC TABLE output: NUMBER(10,2) for prices, NUMBER(38,0) for quantity, TIMESTAMP_NTZ(9) for last_updated. QUALIFY filters on a window function the way HAVING filters on aggregates. Ordering by a VARCHAR timestamp only works because the format is ISO (YYYY-MM-DD HH24:MI:SS).

Under the hood

CTAS infers column types from the expressions: TRY_TO_NUMBER(x, 10, 2) becomes NUMBER(10,2), the ::TIMESTAMP_NTZ cast becomes TIMESTAMP_NTZ(9), and passed-through strings stay VARCHAR(16777216). That length costs nothing, because Snowflake stores only the actual bytes. The window function partitions by product and the QUALIFY keeps the newest row, so the table holds 30 unique products. The result is written as brand-new micro-partitions in a single transaction. Readers see either the old table or the new one, never a half-built state.

Checkpoint

Pitfalls & hint

A plain SELECT from a stream does not consume it. Only a DML statement that reads it (INSERT/MERGE/...) advances the offset when it commits. P001 existed before the stream's offset, so its UPDATE appears as a DELETE + INSERT pair with METADATA$ISUPDATE = TRUE. Streams return the net change: updating P901 (inserted after the offset) would still show a single INSERT carrying the new value.

Under the hood

Creating the stream turns on change tracking on the table, which adds hidden row-ID and version columns, and stores an offset: a pointer to the current table version. Querying the stream compares the table's current version with that offset and returns the net row-level delta, plus METADATA$ACTION, METADATA$ISUPDATE and a stable METADATA$ROW_ID. No data is copied. Because micro-partitions are immutable, an UPDATE rewrites P001's partition, so the stream reports the old image as DELETE and the new image as INSERT. SYSTEM$STREAM_HAS_DATA answers from metadata without a warehouse. That's why it's the ideal guard condition for tasks.

Goal

Why it matters

This is the core CDC pattern. The stream offset moves forward atomically with the DML that consumed it. If the MERGE fails or you ROLLBACK, the offset doesn't move, so changes are never lost and never applied twice.

Pitfalls & hint

Expect 3 inserted (P901–P903) and 1 updated (P001) from the MERGE. Snippet (b) still returns TRUE, because offsets advance only on commit. WHERE METADATA$ACTION = 'INSERT' keeps the new image of updates and drops the old DELETE image. QUALIFY guards against two rows for the same product. Under the hood

The MERGE reads the stream at its current offset and writes new micro-partitions to the target. Inside the explicit transaction, Snowflake stages the offset advance together with the DML. At COMMIT both become visible atomically and the offset jumps to the table version the MERGE read. Rows added to the source during the transaction are not lost. They stay beyond the new offset for the next run. A ROLLBACK discards the DML and the offset move, which makes stream-driven pipelines exactly-once at the transaction level.

Append-only stream, schema drift & bad rows

Goal

PUT batch2 and batch3, create an APPEND_ONLY stream, then load both files. Batch3 has a new reorder_point column in the middle, so evolve the table (as a typed NUMBER column) and load it with MATCH_BY_COLUMN_NAME. Batch3 also contains one corrupt row (P038, reorder_point = 'TBD'): dry-run it with VALIDATION_MODE, then load with ON_ERROR = 'CONTINUE' so the 20 good rows land and the bad one is skipped. Correct an old row, then compare the two streams.

Why it matters

Upstream exports change shape without warning, and a positional load would silently shift reorder_point into unit_cost. Loading by column name is robust to column order. One bad record must not block an hourly feed, yet it must not slip in silently either: ON_ERROR = 'CONTINUE' loads what is valid and reports what was rejected. Append-only streams are cheaper and fit insert-only feeds, because they ignore UPDATE/DELETE noise.

Pitfalls & hint

Under the hood

Offset & transaction rules

  • A stream stores an offset, not data. SELECT from a stream never consumes it.
  • A DML statement that reads the stream advances the offset when its transaction commits (autocommit = per statement).
  • Inside BEGIN … COMMIT every statement sees the same snapshot; ROLLBACK leaves the offset where it was.
  • Several consumers need several streams on the same table (one offset each) — that is why this lab has three.
  • SYSTEM$STREAM_HAS_DATA('s') is cheap (no warehouse) — use it in a task's WHEN.
  • CHANGES clause (SELECT … FROM t CHANGES(INFORMATION => DEFAULT) AT(OFFSET => -3600)) reads change data without a stream.

Staleness

  • A stream becomes stale when its offset falls outside the table's retention: DATA_RETENTION_TIME_IN_DAYS, automatically extended up to MAX_DATA_EXTENSION_TIME_IN_DAYS (default 14) for unconsumed streams.
  • Check SHOW STREAMS columns stale and stale_after; consume (or recreate) before that time. A stale stream must be recreated — and you lose the gap.

Appendix E

Interview prep

The 60-second answer

about 60 seconds out loud
I stage CSV files using SnowSQL PUT to an internal stage, then COPY them into a raw VARIANT or typed raw table with lineage columns. A standard stream on that table does CDC — it captures every INSERT, UPDATE (as DELETE+INSERT) and DELETE, exposing the change type through METADATA$ACTION and METADATA$ISUPDATE. For append-only sources I use APPEND_ONLY = TRUE to skip the overhead. A parent task on a 5-minute schedule runs a MERGE into the clean table, gated by SYSTEM$STREAM_HAS_DATA so it spends compute only when there is work. A child task (AFTER the parent) writes price changes to an audit table. The stream offset advances on COMMIT, so the DAG is naturally idempotent. I monitor with TASK_HISTORY and check the STALE flag in SHOW STREAMS to catch streams that fell behind the 14-day retention window.

Likely follow-up questions

Q01When would you use SnowSQL rather than Snowsight?
Anything client-side or automated: PUT/GET of local files, cron/CI jobs with -f and exit_on_error=true, piping CSV output (-o output_format=csv -o header=false), and parameterised scripts via -D/!define. Snowsight is for interactive work and dashboards.
Q02How do you authenticate SnowSQL in an unattended job?
A named connection in ~/.snowsql/config (chmod 600) with key-pair auth (authenticator = snowflake_jwt, private_key_path) for a service user, least-privilege role and its own warehouse. Never passwords in scripts.
Q03What does PUT actually do?
Client-side: reads the file, computes MD5, optionally gzips (AUTO_COMPRESS), encrypts, and uploads in parallel to the internal stage. A file with the same name and checksum is SKIPPED unless OVERWRITE=TRUE.
Q04Why is COPY INTO idempotent, and how do you override it?
Load metadata per table records file name + checksum for 64 days; already-loaded files are skipped ("0 files processed"). FORCE = TRUE reloads; LOAD_UNCERTAIN_FILES covers files older than the metadata window.
Q05How do you handle a bad row in a CSV load?
Validate first (VALIDATION_MODE = RETURN_ERRORS), then choose ON_ERROR: ABORT_STATEMENT (default for COPY), CONTINUE (skip bad rows → PARTIALLY_LOADED) or SKIP_FILE. Afterwards inspect with VALIDATE(table, JOB_ID => '_last'). Or land everything as VARCHAR and cast with TRY_ functions.
Q06Standard vs append-only stream?
Standard computes the net delta, including updates as DELETE+INSERT pairs (ISUPDATE=TRUE) and deletes. Append-only only returns inserts, is cheaper, and fits insert-only feeds. Insert-only is for external tables.
Q07When does a stream offset move?
Only when a DML statement that reads the stream commits. SELECT never consumes. In an explicit transaction the offset advances at COMMIT; ROLLBACK keeps it. Two consumers → two streams.
Q08What is a stale stream and how do you prevent it?
Its offset is older than the table retention (extended up to MAX_DATA_EXTENSION_TIME_IN_DAYS, default 14). Consume regularly, monitor stale_after in SHOW STREAMS, and alert on it. Once stale it must be recreated.
Q09Why put WHEN SYSTEM$STREAM_HAS_DATA on a task?
The condition is evaluated in cloud services without starting a warehouse; if FALSE the run is SKIPPED and you pay no warehouse credits. It makes a 5-minute schedule cheap.
Q10How do you change a running task DAG?
Suspend the root (otherwise 091092), alter/create children, resume children then root — or call SYSTEM$TASK_DEPENDENTS_ENABLE on the root. Children have no schedule and run only when all predecessors succeed in the same graph run.
Q11Serverless or warehouse tasks?
Serverless for small, frequent, variable jobs: Snowflake sizes compute and bills per second, no idle warehouse. User-managed warehouses when you need a specific size, share a warehouse that is already running, or want predictable cost controls via resource monitors.
Q12How do you monitor and debug tasks?
INFORMATION_SCHEMA.TASK_HISTORY() for recent runs (ERROR_ONLY => TRUE), ACCOUNT_USAGE.TASK_HISTORY for long-term, COMPLETE_TASK_GRAPHS for DAG runs, plus error notifications (ERROR_INTEGRATION) and SUSPEND_TASK_AFTER_NUM_FAILURES.
